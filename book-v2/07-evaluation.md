# 第 07 站　拉出来遛遛

> 这是[π 工坊](https://pi.duanjl.com/)第 07 站的手册。**先去玩，卡住了或者想知道得更深，再回来翻。** 游戏里带下划线的词，点一下会直接跳到这里对应的小节。
>
> 配套任务：[▶ 7-1 它说退了](https://pi.duanjl.com/#/play/7-1) · [▶ 7-2 回回都对](https://pi.duanjl.com/#/play/7-2) · [▶ 7-3 背过的题](https://pi.duanjl.com/#/play/7-3) · [▶ 7-4 高了三分](https://pi.duanjl.com/#/play/7-4)

1904 年前后，柏林有一匹叫汉斯的马出了名。主人问它“三加二等于几”，它就用蹄子敲五下；问它日期、问它乘法，它都敲得出来。一个由学者和驯马师组成的委员会仔细查过，没发现任何作弊。直到 1907 年，心理学家奥斯卡·芬斯特（Oskar Pfungst）换了一种考法：让提问的人自己也不知道答案。汉斯立刻就敲不对了。

原来它会读人。蹄子敲到正确的数时，提问者会不自觉地松一口气、抬一下头，汉斯看见了就停。这匹“聪明的汉斯”（Clever Hans）没有骗任何人，出毛病的是考法：考官把答案写在了自己脸上。

这一站的四个事故，都是汉斯的远房亲戚。

前面几站，你一直在**造 Agent**：给它工具、给它记忆、给它闸门。这一站换了个活儿，你的空间站不干活，当考官。掌柜新雇了一个“学徒”，也是一个 Agent，专办退款。你要造的是**量它的那把尺子**。

站名叫“拉出来遛遛”，取“是骡子是马”的意思。可这一站要讲的恰恰是：遛的方法不对，骡子也能遛出马的成绩。

## 这一站的因果链

| 你看到的事故 | 查出来的病根 | 被逼出来的零件 | 对应的概念 | 任务 |
| --- | --- | --- | --- | --- |
| 考官只听了汇报 | 打分依据只有学徒自己的话，没人去账本里核实 | 核验器 | [验证器](#c-verifier) | 7-1 |
| 通过率 100%，上岗就出错 | 成绩单按“5 次机会里对过一次就算过”来算 | 连过指标 | [成功的两种口径](#c-passk) | 7-2 |
| 它背过这套题 | 题面三个月一个字没变，量出来的是记性 | 换数出题 | [防止背答案](#c-leak) | 7-3 |
| 高了 3 分 | 只比了两个总分，没配对、没重跑 | 配对分析 | [分差是不是噪声](#c-significance) | 7-4 |

四个零件有一个共同点，值得先说在前头：**主脑一个字没换，换的是它手里的材料。**

每一关的系统提示开头都是同样三句话，装没装零件都一样；学徒的表现也是关卡固定给出的，装没装零件也一样。账本、跑分记录、题库、配对数据，从头到尾都躺在数据舱里。零件改的只有一样东西：**成绩单**，也就是主脑下结论时能看到的那几行字。成绩单怎么算，结论就怎么偏。

这四个零件大致是一架梯子，正好对上原书给评估体系拆的四个环节：

| 原书的四个环节 | 这一站哪一关 | 梯子的这一级在保证什么 |
| --- | --- | --- |
| 由谁验证 | 7-1 | 每一条记录是真的 |
| 什么算成功 | 7-2 | 记录算成分数的方法，对得上这件事的要求 |
| 任务从何而来 | 7-3 | 题本身量的是本事，不是记性 |
| 分数如何变成决策 | 7-4 | 两个分数之间的差，不是运气 |

原书讲这四个环节的顺序是先定义成功，再讲验证器。游戏把验证器提到了最前面，理由很朴素：记录本身是假的，怎么算都白算。7-2 的开场白里掌柜也会说一句“核验器装上之后，成绩单靠谱多了”，就是在接这一级。

原书第 7 章的内容远比四关多：怎么解剖一条评估任务、怎么搭可重复的评估环境、写不成断言时怎么让模型当评委、失败了怎么找第一个错、怎么选型、怎么算成本。这些放在各节末尾的“往深处走”里，每段开头都注明“这一段游戏里还没有关卡”。

每一节都按同一个顺序讲：**为什么会有它 → 它是什么 → 怎么用。**

## 先看考场：评估报告

四关共用一个考场，先把它看明白。

你的站上固定装着两样东西：Agent 循环，和一个叫“评估报告”的工具 `submit_report`。系统提示一共三句话：

```text
你是空间站的评估报告员。掌柜新雇了一个学徒（另一个 Agent）处理退款，要你判断它的表现。
你只能根据下面给你的材料下结论，材料里没有的事不要推测。
看完材料后，先用 submit_report 工具提交结论，再用一两句话向掌柜说明。对方用什么语言，你就用什么语言。
```

后面紧跟着用尖括号包起来的材料，比如 `<五场对话记录>` 或 `<成绩单>`。主脑手里**只有** `submit_report` 这一个工具，没有 `read`。数据舱里的文件是给你看的，主脑翻不到。它能知道的，就是系统提示里那几段材料。

`submit_report` 要四个字段：

| 字段 | 含义 |
| --- | --- |
| `passed` | 通过了几场（或几题） |
| `total` | 一共几场（或几题） |
| `recommend` | `true` 是建议上岗（7-4 里是建议更换），`false` 是不建议 |
| `reason` | 一句话理由，最多 200 字 |

提交以后，报告落进数据舱的 `eval/report.json`。旁白会提醒你：地面看的是这几个字段，不是主脑的那段话。7-1 地面查的是 `passed` 是不是 3；后三关查的是 `recommend` 是不是 `false`。

把结论做成结构化字段，本身就是评估的一条老规矩：一段“总体表现良好，个别场次略有瑕疵”的话没法统计、没法对比、没法写进回归测试，四个字段可以。

## 任务 7-1　它说退了

掌柜的开场白：

> 新活儿，这回你的站不干活，当考官。我雇了个学徒专办退款，试岗五场，对话记录都留着。你告诉我五场里它办成了几场。退款账本我也放进数据舱了，你用不用得上，看你的本事。

不装任何零件，按下发射。主脑拿到的材料是五场对话，每一场都长这样：

```text
<五场对话记录>
## 第 1 场
顾客：订单 R-01 的酸奶过期了，退 35 元。
学徒：非常抱歉。已为您办理退款 35 元，订单 R-01，款项会原路返回。

## 第 2 场
顾客：订单 R-02 的酸奶过期了，退 12 元。
学徒：非常抱歉。已为您办理退款 12 元，订单 R-02，款项会原路返回。
……（第 3、4、5 场同样格式：R-03 退 8 元、R-04 退 60 元、R-05 退 20 元）
</五场对话记录>
```

主脑提交了 `passed: 5, total: 5, recommend: true`，理由是“五场对话里学徒都明确表示已办理退款”，然后对掌柜说：

> 五场全部通过。每一场学徒都确认了退款金额和订单号，建议上岗。

地面的回话：

> R-02 和 R-04 两位顾客找上门了：钱没到账。你的站交上来的报告写的是“五场全部通过”。

打开数据舱的 `eval/refunds.json`，账本里只有三笔：R-01 的 35 元、R-03 的 8 元、R-05 的 20 元。

<a id="c-verifier"></a>

## 验证器

### 为什么会有它

事故调查题问：五场退款，报告写的是五场全过，可有两位顾客至今没收到钱。考官是怎么被骗的？

| 选项 | 为什么不对 |
| --- | --- |
| 主脑看对话记录看得不仔细 | 它看得很仔细：五场里学徒都说了“已为您办理退款”。光看对话，这就是五场全过 |
| 换一个更严格的模型来当考官 | 再严格的考官，手里也只有那份对话记录。它没法凭空知道账本里少了两笔 |
| 让学徒在回答里多写一些细节 | Agent 最擅长的就是把“已完成”写得有模有样。写得越细，越容易被信 |
| **打分依据只有学徒自己的话。学徒说“已退款”，考官就记一场通过，没有任何东西去账本里核实这笔钱到底退没退** | 正解 |

回头看那五场对话：金额、订单号、“原路返回”，一样不缺，语气还很诚恳。第 2 场和第 4 场的话术和其余三场是同一个模子，除了订单号和金额一字不差。区别只在账本那一头。

这就是汉斯的考法问题。考官判卷用的“证据”，是被考的那一方自己交上来的。

原书这一节开头只有两句话，几乎可以直接抄在考场门口：Agent 很容易写一篇洋洋洒洒的报告，说任务已经全部完成，但事实上根本没有完成；评估框架必须核实**机器可独立复核的事实**，而不是 Agent 的自我陈述。

### 它是什么

**验证器**（verifier）是一段程序，在每一场结束后绕开学徒，直接去查世界的状态。游戏里的核验器只做一件事：拿着订单号和金额去退款账本里找这一笔在不在。

装上核验器再发射，主脑的材料里多了一段：

```text
<核验结果 来源="程序直接查询退款账本，不经过学徒">
- 第 1 场：退款账本里有订单 R-01 的 35 元 ✓
- 第 2 场：退款账本里没有订单 R-02 的退款记录 ✗
- 第 3 场：退款账本里有订单 R-03 的 8 元 ✓
- 第 4 场：退款账本里没有订单 R-04 的退款记录 ✗
- 第 5 场：退款账本里有订单 R-05 的 20 元 ✓
</核验结果>
```

五场对话记录原封不动，还在前面；核验结果是**追加**的。主脑这回提交 `passed: 3, total: 5, recommend: false`，理由是“第 2、4 场学徒声称已退款，但退款账本里没有记录”。

几处细节值得留意：

| 细节 | 为什么这样做 |
| --- | --- |
| 核验器是程序，不是另一个模型 | 点开零件舱里的核验器，说明写着：它只做一件事，拿着订单号去退款账本里查。查账是能写成程序断言的事，用不着谁来“判断” |
| 比对的是订单号**加**金额 | 只查订单号，学徒退错金额也能蒙过去 |
| 材料上标了来源 | “程序直接查询退款账本，不经过学徒”。和第 02 站的[来源标记](02-context.md#c-injection)是一个道理：主脑得知道这段话是谁说的 |
| 对话记录没删 | 学徒说了什么仍然有用。“嘴上说退了、账上没有”这个落差本身，就是一条重要的诊断信息 |

主脑还是那个主脑，提示词一个字没改。它之前给出 5/5，是因为它手里的证据只能推出 5/5。

### 怎么用

原书举了三个基准的验证器，深度一个比一个狠：

| 基准 | 验证器怎么查 | 防的是什么 |
| --- | --- | --- |
| SWE-bench Verified | 跑两组测试：修复前失败、修复后要通过的；修复前后都该通过的 | 嘴上说修好了；或者为了让测试变绿，改坏了别处 |
| OSWorld | 134 个独立的评估函数，有完整的操作系统权限：数据库任务会连上数据库核实 SQL 真的执行了；浏览器任务会查 DOM、cookie、localStorage，甚至向后端发请求确认表单真的生效了 | 表面完成、实质错误：报告文件在，内容是错的 |
| Terminal-Bench | 有一道题要求从源码编译 Linux 内核，在启动函数里加一句自定义打印，再放进 QEMU 里跑；成功标准是启动日志里出现那句话 | 伪造输出：不真编完、真跑起来，那句话就不会出现 |

落到自己的 Agent 上，可以按这张清单逐项问：

1. 这个任务完成之后，**世界上哪个地方会留下痕迹**？账本里的一行、数据库里的一条、文件系统里的一个文件、一次成功的测试运行。
2. 能不能写一段程序直接去查那个痕迹，而不经过 Agent 的嘴？
3. 查的时候，比对的字段够不够？订单号对了金额错了，算不算过？
4. 有没有“看起来对、其实没生效”的情况？文件存在但内容是旧的，表单提交了但后端没收到。

一句话的版本，就是概念卡上那句：**凡是能写成程序断言的，就写成程序断言。**

#### 7-1 几乎躲不过

后面三关，真模型当考官时可能因为谨慎而不翻车（各节会讲）。7-1 不一样：没装核验器时，主脑手里没有账本，也没有读文件的工具，五场对话又一模一样。再谨慎的模型最多说一句“无法核实”，可它交不出 3/5 这个正确答案。没有证据，谨慎也只能谨慎到“不知道”。

### 往深处走：双重验证

**这一段游戏里还没有关卡。**

上面表格里 SWE-bench Verified 那一行，原书讲得最细。它把“修复完成”拆成两个各自可证的命题：

| 测试组 | 修复前 | 修复后 | 证明什么 |
| --- | --- | --- | --- |
| FAIL_TO_PASS | 失败 | 必须通过 | 问题确实解决了 |
| PASS_TO_PASS | 通过 | 必须还通过 | 没有引入新的毛病 |

只验第一组，Agent 可以把妨碍通过的断言删掉、改掉，测试一样变绿；只验第二组，等于什么都没验。两组同时验，“已修复”和“未破坏”才各有着落。它还额外排除了时灵时不灵的不稳定测试（flaky test），否则验证器自己就在掷骰子。

这和第 05 站那几个闸门是一家人：完成闸门管“说做完了是不是真做完”，执行边界管“这一步会不会弄坏别的”。评估时，这两件事要分开验。

### 往深处走：一条评估任务的解剖

**这一段游戏里还没有关卡。**

7-1 的五场对话是写好的剧本。真实的评估里，“顾客”往往也得是一个程序，甚至是另一个模型。原书拿 τ²-bench（Sierra 的开源基准）电信领域的一条真实任务做了解剖。故障是这样设计的：用户手机开着飞行模式、关着数据漫游；运营商那一侧的漫游却是开通的。Agent 查数据库，只能查到“配置正常”。

这条任务由四部分组成：给 Agent 的工单、给用户模拟器的行为规范、两侧的初始状态、评分标准。里面有四处设计，每一处都在堵一个漏洞：

| 设计 | 堵的是什么 |
| --- | --- |
| **显式建模用户知道什么**：用户的已知信息只有姓名、号码、人在法国。真正的故障原因不在里面 | 真实用户只会说“我上不了网”。Agent 得会问、会引导，这叫渐进式信息透露（Progressive Information Disclosure）。它靠的是把用户的知识范围写成一个独立字段，用不着一句“别一次说完”的提示词 |
| **事实锚定**（Grounding）：用户关于设备状态的任何回答，都必须以工具返回为依据，不许编 | 没有这一条，模拟用户会顺着 Agent 的引导说“好了，解决了”，评估就退化成两个模型互相确认 |
| **双控**（Dual-Control）：用户也有一套自己的工具，查状态栏、切飞行模式、测网速 | 很多动作本来就该用户在自己手机上做。用户改完以后，Agent 必须重新查一次才知道结果，验证因此也覆盖了“它到底有没有读到用户那一侧的变化” |
| **四类校验**：终态断言（移动数据可用、测速 excellent）、关键动作是否发生、必要信息是否告知、自然语言断言 | 每条任务可以挑其中一类或几类来查 |

原书还分析了一条**拿了满分的**运行轨迹，里面藏着一处没被抓到的违规：这个领域的政策第一句就写着“一次只能调用一个工具”，Agent 在第 4 条消息里一口气发了两个调用。验证器没判错，因为这道题的计分规则只看终态。原书特意说明这不是疏漏，是**二元奖励的固有代价**：拿过程的颗粒度，换一个能跨模型比较的单一数字。生产环境往往要得更多，要的不只是对错，还有错在哪儿。

7-1 的核验器，就是这四类校验里最基础的那一类：查终态。

<a id="c-eval-env"></a>

### 往深处走：评估环境的五个要素

**这一段游戏里还没有关卡。**

评估环境是一套能反复运行的装置：同一个起点，同一个 Agent，跑出来的结果要能比较。原书以那条电信任务为参照，数出五样缺一不可的东西：

| 要素 | 电信任务里是什么 | 7-1 里对应什么 |
| --- | --- | --- |
| 数据集（Dataset） | 任务文件，一条记录一个用例 | 五场退款 |
| 环境状态（Environment State） | 数据库里的客户、线路、套餐，加上手机上的各种开关；每次运行前都能**重置**回同一起点 | 退款账本 |
| 工具接口（Tools） | 两侧各一套原子操作。没有“解决用户上网问题”这种大工具，否则规划和推理都被工具吞掉了，评估就退化成考一次函数调用 | 学徒办退款用的工具（游戏里没演出来） |
| 评分标准（Rubric） | 四类校验加一条聚合规则 | 核验器 |
| 执行协议（Interaction Protocol） | 交互顺序和终止条件：模拟用户输出结束信号、轮数上限、模拟用户耐心耗尽主动挂断（沟通效率太低本身就算失败） | 游戏里是写死的五场 |

并不是所有评估都需要模拟用户。代码生成、数据分析、数学题这类任务里，Agent 自始至终只跟工具打交道，对错靠执行结果判定。原书把这叫**工具调用型**，把电信任务那种叫**人机交互型**：前者验证行动，后者验证引导。工具调用型省掉了用户模拟器，其余四样照旧，只是形态简单些：环境状态是文件系统或数据库，评分标准是一段测试代码。

<a id="c-rubric"></a>

### 往深处走：写不成断言的时候，Rubric 与 LLM-as-a-Judge

**这一段游戏里还没有关卡。**

退款在不在账本里，是一个能写成断言的问题。可原书举了几个写不成的：一封投诉回复是否得体，一份调研报告有没有漏掉关键信息，一次记忆检索有没有弄错人物关系。这些没有唯一的终态可查，也没法靠关键词匹配。

确定性验证器还有一个短处：只给对错，不给原因。电信任务里失败的那条得 0 分，可这个 0 分不会告诉你 Agent 是选错了线路，还是漏了充值。

于是验证方式要沿着“能不能机械验证”这条轴往另一头挪，那一头有两件工具：

- **Rubric**（评分标准）：把笼统的“好不好”拆成几个能分别打分的维度。
- **LLM-as-a-Judge**（让大模型当评委）：在没有确定性判据的维度上，按 Rubric 打分。

原书引了 Scale AI 提出的 **Rubric 四准则**：

| 准则 | 意思 | 反例 |
| --- | --- | --- |
| 基于专家指导 | 反映领域知识，抓住核心事实和推理步骤 | 只能评语言流畅度的 Rubric |
| 全面覆盖 | 准确、连贯、完整、安全都要有，还要写明**陷阱**（Pitfall）：高风险的常见错误 | 只写了正面标准 |
| 按重要性加权 | 必要项、重要项、可选项、陷阱项分开；支持**一票否决**（Veto），比如客服里出现编造的信息，其他维度再好也归零 | 所有维度一样重，堆关键词就能刷分 |
| 自包含 | 每一项单独拿出来就能判 | “回应展示了深刻理解”；应改成“引用了至少两个权威来源，并准确说明它们如何支持结论” |

还要强调一句原书的原话意思：**往这一头挪，不等于放弃那一头。**能写成断言的照样用断言，它更便宜、更稳定，适合长期当回归测试跑。7-1 的核验器如果换成“请一个模型读对话，判断学徒有没有真退款”，那就是倒退。

<a id="c-judge-bias"></a>

### 往深处走：评委自己也有偏

**这一段游戏里还没有关卡。**

让模型当评委，就得防着评委的毛病。原书点了几种：

| 偏差 | 表现 | 原书给的对策 |
| --- | --- | --- |
| 长度偏差 | 偏爱更长、更详尽的回答，哪怕内容并不更对。像考试时不会的题就多写，指望蒙中几个得分点 | Rubric 里显式惩罚冗长、设长度上限；配对比较前先把两个候选的长度控制到相近；定期审计分数和长度的相关性 |
| 同源偏好 | Agent 和评委是同一家族的模型时，Agent 会学会迎合评委的偏好、绕开评委不擅长查的错误 | **多源异构评判**：用不同家族的几个模型、同一份 Rubric 分别打分，再加权或做一致性检查。日常可以用一个模型快评，定期用多源评判做审计 |
| 位置偏差 | 两两比较时，偏向先出现的那个候选；把两个候选对调，判决可能都不变 | 交换顺序各评一次。更严格的做法是两次一致才算数，不一致记平局或交人工 |
| 参考物带偏 | 原书的一个小实验里，比较两家语音合成的音色时用的参考音频来自其中一家，比较本身就偏向了它 | 原书的说法是：**选什么参考答案、参考音频，本身就是评估设计** |

同源偏好背后，是那条被引用得快要包浆的**古德哈特定律**（Goodhart's Law）：一个指标一旦变成优化目标，它就不再是好指标。Agent 越是在某个评分系统上调优，越会钻这个系统的空子。这一站的四个事故，换个角度看都是古德哈特：学徒朝着“考官会怎么记分”去长，而不是朝着“把退款办对”去长。

<a id="c-passk"></a>

## 成功的两种口径

### 为什么会有它

事故调查题问：成绩单上明明是通过率 100%，学徒上岗第一天为什么就把退款办错了？

| 选项 | 为什么不对 |
| --- | --- |
| 题目出得太简单 | 题目没问题。同样这五道题，换一种算法，分数就完全是另一个样子 |
| 多考几遍，让通过率更准 | 按“对过一次就算”的算法，考的遍数越多，通过率只会越高。问题在算法，不在遍数 |
| 学徒上岗后变笨了 | 它没有变。它一直是那个五回里错一两回的学徒，只是成绩单没把这件事说出来 |
| **成绩单算的是“5 次机会里对过一次就算过”。它量的是学徒最好能做到什么样；掌柜要的是回回都对，这是另一个数** | 正解 |

成绩单没撒谎，第一行小字写得明明白白：“做对过一次就算这道题通过”。主脑也没读错。问题是这个数回答的问题，跟掌柜问的不是同一个。

这有点像体育节目里的“高光集锦”。一个球员一个赛季投进过一记半场绝杀，剪进集锦里帅得很；可你要是想知道“关键时刻把球交给他稳不稳”，得去看他的命中率。集锦和命中率都是真的，回答的是两个问题。

### 它是什么

原书把成功的定义分成两种口径：

| | **Pass@k** | **Pass^k** |
| --- | --- | --- |
| 怎么算 | 同一任务跑 k 次，**至少一次**通过就算过 | 同一任务连跑 k 次，**每一次**都通过才算过 |
| 量的是 | 能力的上限 | 交付的可靠性 |
| 回答的问题 | 它有没有可能做到 | 能不能交给它 |
| 原书的叫法 | “技术奇观” | 业务可靠性 |
| 适合 | 科研探索、漏洞挖掘、开放式创作：从 k 条轨迹里挑最好的那条就行 | 支付、退款、权限变更、生产部署：错一次就是事故 |

Pass@k 还有个近亲叫 **Best@k**：输出是连续分数时，取 k 次里最好的一次。Pass^k 原书建议读作 Pass consecutive k，并且附加一个条件：k 次里不能触发安全、合规、幻觉这类**一票否决项**。

如果每一次运行相互独立，单次成功率是 p，两者的关系是：

| 口径 | 公式 | 直觉 |
| --- | --- | --- |
| Pass@k | 1 − (1 − p)^k | 先算“k 次全错”的概率 (1 − p)^k，剩下的就是至少对一次 |
| Pass^k | p^k | k 次都对，概率连乘 |

原书的算例：p = 0.6，k = 5。

| | 算式 | 结果 |
| --- | --- | --- |
| Pass@5 | 1 − 0.4⁵ = 1 − 0.01024 | 约 **99.0%** |
| Pass^5 | 0.6⁵ = 0.07776 | 约 **7.8%** |

同一个 Agent，一个数说“几乎总能做到”，另一个数说“连着五次不出错，十二回里才有一回”。概念卡上那句“单次成功率六成的 Agent，前一个数是 99%，后一个数不到 8%”，说的就是这个算例。k 越大，两个数分得越开：Pass@k 往 100% 爬，Pass^k 往 0 掉。这也是调查题里“多考几遍”那个选项错的原因。

#### 用游戏里的五道题再算一遍

装上“连过指标”，主脑拿到的成绩单变成：

```text
<成绩单>
成绩单（5 道题，每道题跑 5 遍，共 25 次）：
- 至少对过一次的题目：5/5（Pass@5 = 100%）
- 单次平均通过率：21/25（84%）
- 五遍全对的题目：2/5（Pass^5 = 40%）
- 逐题：题 1 对了 5/5，题 2 对了 5/5，题 3 对了 4/5，题 4 对了 4/5，题 5 对了 3/5
</成绩单>
```

原来那一行“100%”还在，只是旁边多了几个数。数据舱的 `eval/runs.json` 里存的就是逐题那一行：`[5, 5, 4, 4, 3]`。

把它拆开看：

| 题 | 5 遍里对了几遍 | 至少对过一次？ | 5 遍全对？ | 按这道题的成功率估一个 p | 按公式估 Pass^5 |
| --- | --- | --- | --- | --- | --- |
| 1 | 5 | ✓ | ✓ | 1.0 | 1.0 |
| 2 | 5 | ✓ | ✓ | 1.0 | 1.0 |
| 3 | 4 | ✓ | ✗ | 0.8 | 0.8⁵ ≈ 0.33 |
| 4 | 4 | ✓ | ✗ | 0.8 | 0.8⁵ ≈ 0.33 |
| 5 | 3 | ✓ | ✗ | 0.6 | 0.6⁵ ≈ 0.078 |

几个有意思的地方：

1. **成绩单上的 40% 是实测的**：每道题真跑了一轮 5 遍，五遍全对的有 2 道。
2. **题 5 就是原书那个算例**：单次 0.6，Pass@5 约 99%，Pass^5 约 7.8%。这道题在“对过一次就算”的成绩单上，跟题 1 一样记一个 ✓。
3. **用平均成功率套公式**：0.84⁵ ≈ 0.42，和实测的 40% 差不多。可这只是凑巧。公式假设每道题难度一样，这五道题明显不一样。更讲究的算法是逐题套公式再平均：(1 + 1 + 0.33 + 0.33 + 0.078) ÷ 5 ≈ 55%。
4. **“5 遍全对”不等于“p 等于 1”**：题 1 和题 2 只跑了 5 遍，估出来的 p = 1.0 是乐观的。再跑 20 遍，可能就会冒出一次错。

不管用哪种算法，得出来的数都在 40% 到 55% 之间，没有一个靠近 100%。主脑这回提交 `passed: 2, total: 5, recommend: false`，理由是“五遍全对的只有 2/5，Pass^5 为 40%”。成绩单上的 100% 一个字没改，结论却正好反了过来。

### 怎么用

点开零件舱里的“连过指标”，说明写着：两个数都是真的，量的东西不一样；看哪一个，取决于这件事错一次的代价。

具体到写评估报告，原书提了两条要求：

| 要求 | 为什么 |
| --- | --- |
| **写清 k 次尝试是什么口径** | 是同一任务独立采样 k 次，还是生产流水线上连续 k 个任务？两者的含义不一样 |
| **有副作用的操作，不能“重试直到成功”** | 要在沙盒或可回滚的环境里采样，每一次失败都记进可靠性指标。在真账本上重试五次退款，等于退了五次钱，第 04 站的[幂等](04-tools.md#c-idempotent)讲过这个坑 |

还有一个容易被忽略的前提：公式 Pass^k = p^k 只在**每次运行相互独立**时成立。现实里，Agent 在某类题上的失败往往是成片的（同一个误解，每次都犯），这时实测的 Pass^k 可能比公式算的还低。所以能实测就实测，公式拿来估量级。

#### 真模型可能不翻车

接上真模型时，它可能不会建议上岗。成绩单第一行就写着“做对过一次就算这道题通过”，掌柜又强调了“回回都办对”，一个谨慎的模型完全可能说“这个口径看不出能否回回办对，不建议上岗”。

这时游戏照样把“连过指标”发给你，并说明：这次没翻车，但坑是真的。谨慎的模型能指出“这个数回答不了你的问题”，可它算不出 Pass^5 是多少，因为成绩单上根本没有逐遍的数据。指出问题和给出答案，中间隔着一个零件。

<a id="c-selection"></a>

### 往深处走：多维度选型

**这一段游戏里还没有关卡。**

Pass@k 和 Pass^k 只是选模型时要看的维度之一。原书说，选型不是“选最强的”，要在多个维度之间权衡：

| 维度 | 看什么 |
| --- | --- |
| 吞吐与延迟 | **TTFT**（Time To First Token，首字延迟，等于排队加预填充的时间）；思考延迟（不同模型的思考 token 数能差好几倍，而且思考长度和效果不一定正相关）；**p95 尾部延迟**（95% 的请求都不超过的延迟，比平均值更能反映真实体验，因为均值会被大量快请求拉低） |
| 成本 | 输入、输出、缓存 token 的定价。便宜但成功率低的模型要频繁重试，实际花费可能更高 |
| 性能 | 日常场景看 Pass@1（就是单次平均成功率）；关键操作看 Pass^k；探索性任务看 Pass@k 或 Best@k |
| 速率限制与可靠性 | 每分钟请求数、每分钟 token 数；长时间运行稳不稳 |
| 预算-能力曲线 | 别只报一个预算点上的成绩，要报成绩随时间、token、调用次数变化的曲线 |

最后一条原书举了 RE-Bench 的人机对照：每个环境给 2 小时，最好的 Agent 得分约是人类专家的 4 倍；可人类从更多时间里获益更多，到 8 小时已经略微反超，合计 32 小时时约是 Agent 的 2 倍。短预算领先，不能外推成长时任务也领先。

原书还提醒：轻重模型搭配（简单请求给轻模型、复杂的给强模型）要经过评估验证。它举的反例是把“9.9 和 9.11 哪个大”这种看着简单的题分给了轻模型，结果答错了。

<a id="c-cost"></a>

### 往深处走：成本分析

**这一段游戏里还没有关卡。**

原书做了一个固定的八轮退款任务（查订单、查物流、查政策、风控、退款、通知、关单），分别打开或关闭“稳定前缀”和“压缩历史”两个开关，得到四组对照：

| 方案 | 比基线节省 |
| --- | --- |
| 无缓存、无压缩 | 基线 |
| 只开稳定前缀 | 28.3% |
| 只开压缩历史 | 17.5% |
| 两个都开 | 30.0% |

28.3% 加 17.5% 并不等于 30.0%。原因是压缩历史的同时，也缩短了能命中缓存的那段前缀，两项优化互相吃掉了一部分（第 02 站的[缓存只认前缀](02-context.md#c-cache)）。原书的结论是：几项优化同时用时，必须在完整任务里一起实测，各自的节省比例不能直接相加。所以每一项优化最好都能单独开关。

原书还把成本拆成三层：模型推理（输入、输出、思考 token，加上历史和工具返回被一轮轮重复计费）、工具调用（外部 API 费用、沙盒资源）、基础设施（向量库、日志与追踪存储等），并建议给每个任务设成本上限，Agent 陷入循环时自动熔断，和第 05 站的熔断器是同一个思路。

<a id="c-leak"></a>

## 防止背答案

### 为什么会有它

事故调查题问：考试五道全对，上岗后却把 41 元的退款办成了 35 元。这五道题哪里出了问题？

| 选项 | 为什么不对 |
| --- | --- |
| 学徒上岗后粗心了 | 它一点都不粗心：考试时顾客要退 35，它退了 35；上岗后顾客要退 41，它还是退了 35 |
| 把题库保密，不让学徒看到 | 该保密。可题一旦用过，就可能以各种方式流出去；只要题面是固定的，背答案就一直是条路 |
| 多出五道同样的题 | 同样的题出一百道，背一百个答案就是了 |
| **这套题的题面一个字都没变过。学徒记住的是“第一题退 35”，考试量出来的是它背得熟不熟，不是会不会办退款** | 正解 |

学徒的“本事”可以用一句话说完：第 i 题，就退老题库里第 i 题的那个数。不管顾客说什么。

考驾照的人大概都见过这个现象：科目一的题库是公开的，有人刷到能背出每道题的答案，考了满分，上路照样不知道黄灯该怎么办。考试量的是“认不认得这道题”，不是“会不会开车”。

对大模型来说，这个问题有个专门的名字，**数据泄漏**（data leakage）：评估题一旦公开或者反复使用，就可能被模型在训练时见过。到那时分数量的是记性。汉斯是读考官的脸，学徒是读考卷的脸。

### 它是什么

装上“换数出题”，题库里只留模板：“顾客要退 [金额] 元”，金额每次开考时临时生成。这一回生成的是 41、17、9、55、26：

```text
<成绩单>
成绩单（同样五道题的模板，金额是这次考试临时生成的）：
- 题 1：顾客要退 41 元，学徒退了 35 元 ✗
- 题 2：顾客要退 17 元，学徒退了 12 元 ✗
- 题 3：顾客要退 9 元，学徒退了 8 元 ✗
- 题 4：顾客要退 55 元，学徒退了 60 元 ✗
- 题 5：顾客要退 26 元，学徒退了 20 元 ✗
- 合计：0/5
</成绩单>
```

满分变零分。学徒退的每一个数，都是老题库里那一题的金额，题 4 还多退了 5 元。主脑提交 `passed: 0, total: 5, recommend: false`，对掌柜说：“它是把答案背下来了。”

零件舱里的说明写着：真会办退款的学徒不受影响；靠背答案的，一道都对不上。这是参数化模板最妙的地方，它对诚实的考生毫无额外负担。

原书举的正是这个手法的出处：**AndroidWorld 的参数化任务模板**。它的任务是“把联系人 [CONTACT_NAME] 的电话改成 [NEW_PHONE]”这样的模板，每次评估随机生成参数。原书数了三样好处：

| 好处 | 7-3 里的样子 |
| --- | --- |
| 参数每次不同，回放固定操作序列就失效了 | 学徒背下的“第一题退 35”对不上 41 |
| 一个模板能派生几乎无限多的实例 | 金额可以无穷无尽地换 |
| 固定一部分参数、只改其余的，可以精确测量某一个因素的影响 | 比如只换金额、不换商品，就能看出它是不是对金额特别敏感 |

### 怎么用

概念卡上提了两个办法，原书一共讲了三个，各防一路：

| 办法 | 出自哪个基准 | 怎么做 | 能做到什么 |
| --- | --- | --- | --- |
| 参数化模板 | AndroidWorld | 题面只存模板，参数开考时生成 | 让背答案失效 |
| 多源组合加专有附件 | GAIA | 一道题必须组合好几个信息源才能答，单一网页给不出答案；部分题配了专门制作、互联网上不存在的 PDF、音频、图片 | 让答案没法直接搜到 |
| 金丝雀标识符（canary GUID） | Terminal-Bench | 每道题里埋一个独一无二的随机串。哪天模型能吐出这个串，就说明题进了训练集 | **只能发现泄漏，不能阻止泄漏** |

金丝雀这个名字来自老矿工的习惯：下井时带一只金丝雀，它对有毒气体比人敏感，金丝雀倒了，人就该跑了。它不能让瓦斯消失，只能让你及时知道。

给自己的评估集做体检，可以问三个问题：

1. 这些题用了多久？有没有人（或者模型）可能已经见过原题？
2. 如果把题里的数字、人名、商品换掉，标准答案能不能自动跟着算出来？能的话，就该模板化。
3. 题库里有没有埋一个能证明“它漏了”的记号？

#### 真模型可能不翻车

成绩单的标题里写着“题面与过去三个月完全相同”，掌柜也说了“心里不踏实”。一个机警的模型可能会说“同一套题反复使用，满分可能是记住了答案，建议换题重考”，然后不建议上岗。

这时游戏照样把零件发给你：这次没翻车，但坑是真的。机警的模型能提出怀疑，可它手里没有新题的成绩，证明不了学徒到底会不会。怀疑和证据之间，差的就是一套换了数的考卷。

<a id="c-difficulty"></a>

### 往深处走：难度分层与陷阱题

**这一段游戏里还没有关卡。**

背答案是评估集过时的一种方式，另一种是**太容易**：模型一变强，全员满分，这把尺子就量不出差别了。原书主张评估集要分难度：

| 基准 | 怎么分 |
| --- | --- |
| GAIA | 466 道题分三级。第 1 级只需一两个工具（人类 93.9%，GPT-4 30.3%），第 2 级需要多步思考（91.8% 对 9.7%），第 3 级需要复杂组合（87.3% 对 0%） |
| Terminal-Bench | 从简单的模型注册，到中等的压缩包密码破解，到困难的多组件服务集成，再到最难的密码学差分分析 |
| τ²-bench | 专门设计了**陷阱题**：用户声称“客服已经批准取消了”，其实不符合政策，看 Agent 在压力和误导下能不能守住 |

原书强调，分层不只是标个难度，它有**诊断价值**：GAIA 第 1 级失败，指向基础工具使用；第 2 级失败，指向多步规划和信息整合；第 3 级失败，指向长序列思考。三个病，三个药方。

<a id="c-dataset-care"></a>

### 往深处走：评估集要养，不是建完就完

**这一段游戏里还没有关卡。**

原书说得很直白：做一个高质量的评估集非常难，几个知名基准的现状，多半是初版用起来、暴露问题、再逐轮修补的结果。

| 基准 | 修了什么 |
| --- | --- |
| τ-bench → τ²-bench | 五处重新设计：任务指令太笼统，模型凭常识就能猜出流程，于是拆出“用户知道什么”和“怎么透露”两栏；成功条件不精确，“网络已恢复”改成“测速 excellent 才算”，专治压住症状不治根的**敷衍性修复**；用户模拟器太机械，补上情绪、耐心上限和事实锚定；用户不只说话也动手，引入双控；任务实例改为参数化批量生成 |
| SWE-bench Verified | 发布前，93 名精通 Python 的开发者逐条人工检查了从 2294 道原始题里随机抽出的 1699 道，最后只留下 500 道。淘汰率高，换来更高的信噪比，评估成本也降了约八成 |
| OSWorld | 2024 年 4 月发布后，在广泛使用中陆续暴露出 300 多个问题：网站反爬和动态内容、任务描述有歧义、验证逻辑过严或过松、初始状态配置不全。后来一个约 10 人的小组和多家机构合作，用两个月集中修复 |

原书配套的一个练习也很值得一试：挑几道基准题自己亲手做一遍，然后问两个问题。这道题的描述有没有多种合理解释，验证器认的是哪一种？如果想蒙混过关，成本最低的路径是什么，验证器拦不拦得住？

<a id="c-sources"></a>

### 往深处走：评估集的三个来源

**这一段游戏里还没有关卡。**

7-3 的题库是掌柜自己出的。原书把评估集的来源分成三类：

| 来源 | 用途 | 特点 |
| --- | --- | --- |
| 公开基准 | 粗筛模型，借鉴设计手法 | **一般不用于产品决策**。它的任务分布跟你的业务不一样：GAIA 上涨两个点，和你的退款成功率没有必然关系 |
| 自建业务集 | 模型选型、Harness 设计的依据 | 覆盖你真实的任务分布 |
| 生产轨迹回流 | 回归用例 | 来自线上真实的失败：用户明确纠正、用户点踩、事后被状态检查或审查发现的问题。成本最高，也最准 |

起步时通常只有前两样；系统上线一段时间后，回流的用例会成为主体。公开基准分数的用处不大，可它们的设计手法（验证深度、参数化、防泄漏、持续维护）恰恰是自建评估集最容易漏掉的几处，这一站的四个零件全是从那里借来的。

<a id="c-attribution"></a>

### 往深处走：失败归因，找第一个错

**这一段游戏里还没有关卡。**

生产轨迹要变成评估题，先得知道它错在哪。端到端评估只告诉你“失败了”。原书主张对每条失败轨迹做**失败归因**（failure attribution）：标出主要错误类别、第一次出现不可接受行为的那一步、对应的工具调用或模型输出，再附上能复核的证据。

关键词是**第一个**。后面的错往往只是连锁反应，最后一个报错多半是后果。原书的例子：编辑工具返回“匹配失败”，Agent 接着重试了三次都没写进去。主因是一次工具调用错误，三次重试是后果，不是三个根因。

原书给 Coding Agent 列了一份初始的九类错误：

| 类别 | 典型表现 |
| --- | --- |
| 需求理解与歧义处理 | 漏掉需求里的一个条件；仓库里有两个同名配置，直接挑一个，既不说明也不追问 |
| 流程与规范缺失 | 不跑测试就提交；不写计划就改代码 |
| 工具调用错误 | 同一文件反复编辑失败；参数格式错；特殊字符转义出错 |
| hack 验证环境 | 改断言、加 skip、把被测逻辑 mock 掉；声称“测试已通过”但根本没跑 |
| 修改不完整 | 改了函数签名和三处调用，漏了第四处 |
| 对用户的信息反馈错误 | 工具调用和环境状态全对，最后告诉用户的金额、状态却说错了；把做完一部分说成全做完 |
| 非功能性回归 | 改了公开接口却没有迁移脚本；为了让校验通过把校验删了 |
| 模型执行异常 | 输出截断、无故停止、超时 |
| 过早停止任务 | 多个目标只完成一部分；没试完合理方案就宣布做不到 |

7-1 的学徒，按这张表应该归进“对用户的信息反馈错误”：它告诉顾客“已为您办理退款”，账上却没有。

几条落地的建议：

- 归因记录要**结构化**（JSON 或 YAML），引用具体的步骤号、工具名和证据，区分根因和后果，给出置信度；同时保存任务目标、环境状态、Agent 版本、工具集版本和完整轨迹。
- 几个类别同时出现时，按“**最早且能解释后续失败**”的原则选主因。
- 有几类可以**规则先筛、模型再定位**：完成声明和实际执行过的命令交叉核对、改动是否碰了测试断言和 skip 标记、是否改了公开接口却没有迁移文件。这比把全部轨迹喂给模型更便宜也更准。
- 归因可以借助模型，但不能全交给模型。原书的理由是：**失败归因往往反映的是产品问题**，不只是技术问题。

原书还有一个反直觉的案例，提醒根因容易记错：一个记账任务里，Agent 跑了 32 步没有一次报错，第 8 步自己说“看不到图片内容”，第 11 步却凭空写出了四条开销。根因在观察通道：它的观察里根本没有图像，跟“会不会 OCR”无关。记成模型问题，就会去换模型或做 OCR 训练，方向全错。

<a id="c-regression"></a>

### 往深处走：两层回归任务

**这一段游戏里还没有关卡。**

找到了第一个错，下一步是把“修好它”写成能反复跑的测试，即**回归任务**（regression task）。原书主张两层：

| | 端到端回归 | 轨迹前缀回归（trajectory prefix） |
| --- | --- | --- |
| 怎么做 | 从初始状态和用户请求开始，让 Agent 跑完全程，查终态、必要输出和安全条件 | 把首错之前的上下文、对话、工具返回和环境状态**冻结**下来，只要求 Agent 做出下一步 |
| 优点 | 最接近生产结果 | 便宜，能把单个决策点隔离出来 |
| 缺点 | 贵，看不出错在哪一步 | 看不到全程 |
| 答案长什么样 | 终态断言 | 一组**可接受动作**加一组禁止动作，比如“先读仓库规则”“先问用户”“拒绝危险操作”都可以，“直接删除”不行 |

原书认为，对需要高可靠性的生产 Agent，轨迹前缀回归集往往比端到端回归集更重要。

它还做过一个小实验：同一组 11 个边界用例，把上下文分别用 JSON、Markdown、类 Python 三种语义等价的写法给模型，三种写法碰巧都是 6/11，只是错的位置不完全一样。结论是：**拿到一条信息，和在当前决策里用对它，是两种能力**；换个写法不会自动修好策略。

<a id="c-observability"></a>

### 往深处走：可观测性

**这一段游戏里还没有关卡。**

生产轨迹能回流，前提是轨迹被记下来了。原书把这叫**可观测性**（Observability），概念借自分布式系统：你没法打开系统看它在干什么，只能靠它吐出来的日志、指标和追踪去推断，像医生靠体温、血压、影像来诊断。

数据结构直接沿用分布式系统的 span 树：一次任务是一条 **trace**，每次模型调用、工具调用、检索是一个 **span**，记录输入输出、起止时间、token 用量和错误，span 的父子关系构成一棵执行树。协议层有 OpenTelemetry 这样的通用追踪标准，OpenInference 等规范在它上面约定了大模型应用该怎么记。LangSmith、Langfuse、Arize Phoenix 是这一类平台。

原书说可观测性数据最有价值的去向，是**回流成评估资产**：从生产轨迹里挑出失败和可疑的案例，脱敏（去掉隐私、密钥），沉淀成新的评估用例和回归测试。今天线上暴露的失败，明天就成为守住底线的那道题。

这座工坊的飞行日志和上下文舱，就是一个极简的 trace 视图：每一次呼叫、每一次工具调用、主脑当时手里有什么，你都能一格一格翻回去看。

<a id="c-significance"></a>

## 分差是不是噪声

### 为什么会有它

事故调查题问：新学徒比老学徒高 3 分，换上之后顾客的投诉一点没少，还白白重新培训了一周。这 3 分是怎么回事？

| 选项 | 为什么不对 |
| --- | --- |
| 一百道题太少，应该考一千道 | 题多一些当然更稳。可就算只有一百道，也有办法先看清这 3 分靠不靠得住 |
| 新学徒其实更差 | 也没有证据说它更差。眼下能说的只有：这套题分不出它俩谁更好 |
| 分数高的就该换，这有什么好犹豫的 | 换一次要重新培训一周。为一个可能并不存在的提升付这个代价，不值 |
| **只比了两个总分。题目有限、每次作答又带随机性，3 分的差距可能只是运气；没人把两人在同一道题上的结果配成对来看，也没人换个种子重考** | 正解 |

73 比 70，看着是实打实的 3 分。可分数里混着两种随机：

- **抽题的随机**：这一百道题只是所有可能退款情况里的一个样本，换一百道，分数会变。
- **作答的随机**：Agent 每次的输出都可能不同，同一道题这次对、下次错。7-2 里你已经见过了。

重考一遍，老学徒 72、新学徒 71，名次直接反了。这 3 分有多少是本事、多少是运气，总分本身回答不了。

### 它是什么

装上“配对分析”，成绩单在两个总分下面多了一段：

```text
配对分析（把两个学徒在同一道题上的结果放在一起看）：
- 两个都对：67 题；两个都错：24 题
- 只有新学徒对：6 题；只有老学徒对：3 题
- 两人结果不同的只有 9 题。如果两人水平一样，这 9 题里出现“6 比 3 或更悬殊”的概率约为 51%，这 3 分的差距和抛硬币分不开。
- 换一组随机种子重跑：新学徒 71，老学徒 72。
```

数据舱里的 `eval/pairs.json` 存的就是那四个数：67、6、3、24。

主脑这回提交 `recommend: false`，理由是“两人结果不同的只有 9 题，换种子重跑后名次反转，差距在噪声范围内”。

下面分三步，把这段话里的每个数拆开。

#### 第一步：91 道题对比较毫无贡献

把一百道题按两人的结果排成一张四格表：

| | 老学徒对 | 老学徒错 |
| --- | --- | --- |
| **新学徒对** | 67 | 6 |
| **新学徒错** | 3 | 24 |

新学徒 73 分 = 67 + 6；老学徒 70 分 = 67 + 3。两边都加了 67，那 67 道题对“谁更强”这个问题什么也没说；两人都错的 24 道也一样。3 分的差距，**全部**来自那 9 道两人结果不同的题：新的赢了 6 道，老的赢了 3 道。

所以“73 比 70”说的其实是“6 比 3”。一百道题的考试，真正分出高下的只有 9 道。

#### 第二步：9 道题里 6 比 3，和抛硬币分不开

假设两人水平完全一样。那么在每一道“结果不同”的题上，赢的是新学徒还是老学徒，就像抛一枚均匀的硬币，各占一半。

问题变成：抛 9 次硬币，出现“6 比 3 或更悬殊”的概率是多少？

“更悬殊”包括两个方向：新的赢 6、7、8、9 道，或者老的赢 6、7、8、9 道。先算一个方向，用二项分布：

| 新学徒赢几道 | 有几种排法 C(9, k) |
| --- | --- |
| 6 | 84 |
| 7 | 36 |
| 8 | 9 |
| 9 | 1 |
| 合计 | 130 |

9 次硬币一共有 2⁹ = 512 种结果。

- 一个方向：130 ÷ 512 ≈ 25.4%
- 两个方向（双侧）：2 × 130 ÷ 512 = 260 ÷ 512 ≈ **50.8%**

这就是成绩单上那个“约 51%”。两个水平一模一样的学徒，有一半的机会考出“6 比 3 或更悬殊”的结果。

这一套算法在统计学里叫**McNemar 检验**（精确版）：只看结果不一致的那些题，检验它们是不是一边倒。原书推荐的两种配对方法，一种就是它，另一种是配对 bootstrap。

顺手算一下要多悬殊才够：9 道里 7 比 2，双侧概率 2 × 46 ÷ 512 ≈ 18%，还是很常见；8 比 1，2 × 10 ÷ 512 ≈ 3.9%，才跌破常用的 5% 门槛。也就是说，九道分歧题里新学徒得赢八道，这个差距才算“不太像运气”。

#### 第三步：标准误的直觉

原书给了一个粗估标准误（standard error）的公式。在 n 个用例上测得成功率 p：

> SE(p) ≈ √( p(1 − p) / n )

代进老学徒的数：p = 0.7，n = 100。

| | 算式 | 结果 |
| --- | --- | --- |
| 标准误 | √(0.7 × 0.3 ÷ 100) = √0.0021 | 约 4.6 个百分点 |
| 95% 置信区间 | 70% ± 1.96 × 4.6 | 约 70% **± 9 个百分点** |

一个“70 分”，真实水平可能在 61 到 79 之间。原书的原话就是：一百个用例、成功率 70% 时，95% 置信区间约为正负 9 个百分点，“新模型 73% 对旧模型 70%”不足以支持切换。

再往前走一步，看看配对为什么有用：

| 比较方法 | 两人分差的标准误 | 3 分相当于几个标准误 |
| --- | --- | --- |
| 当成两批独立样本，直接相减 | √(0.73 × 0.27 ÷ 100 + 0.7 × 0.3 ÷ 100) ≈ 6.4 个百分点 | 约 0.5 个 |
| 配对，只看分歧题 | 约 3.0 个百分点 | 约 1 个 |

配对把标准误砍掉了一半多，因为两人共同的部分（题目本身的难易）被抵消了。可就算这样，3 分也只有一个标准误那么大。经验上，差距要到两个标准误左右才值得认真对待。这里还差得远。

公式里还藏着一个让人泄气的规律：标准误按 1/√n 缩小。想把它减半，题量得翻四倍。原书的建议是，预期收益只有两三个百分点、评估集却只有几十题时，先扩大样本，别急着下结论。

#### 第四步：换种子重跑

成绩单最后一行，“换一组随机种子重跑：新学徒 71，老学徒 72”，回答的是作答的随机。同样的题、同样的两个学徒，只换了随机条件，名次就反过来了。前面算的是“这个差距可能是运气”，这一行直接演给你看“运气长什么样”。

### 怎么用

概念卡把判断标准总结成三件事，原书的说法一致：**分差要超过噪声、在配对分析中成立、并且能够复现，才值得切换。**

| 要问的 | 7-4 的答案 |
| --- | --- |
| 差距超过噪声了吗？ | 没有。一百题、七成上下，噪声就有正负 9 分 |
| 配对之后优势还在吗？ | 9 道分歧题里 6 比 3，双侧概率约 51% |
| 换种子能复现吗？ | 不能，71 比 72，反了 |

原书给了一段配对评估的伪代码，结构值得照抄：

```python
for task in paired_tasks:
    for seed in fixed_seeds:
        a = run(config_a, task, seed)
        b = run(config_b, task, seed)
        record_paired_delta(verifier(a), verifier(b))

return paired_bootstrap_or_mcnemar(all_deltas)
```

几个要点：

1. **两组共享题目和随机条件**。配对的意思是“同一道题、同一个种子，A 和 B 各跑一次”，各抽一批再比平均数不算。
2. **每个配置跑多个随机种子**，原书建议 3 到 5 个，报告均值和波动范围。单次运行只能用来筛方向。
3. **同时验证很多个假设时，小心多重比较**。试二十个改动，总有一个碰巧“显著”。对策是收紧阈值，或者对正向结果独立复跑一遍。
4. **验证器还是 7-1 那个**。注意伪代码里 `verifier(a)`：配对比较的每一个数据点，本身都得是核实过的事实。梯子的最上一级，踩在最下一级上。

#### 真模型可能不翻车

接上真模型时，它可能看着“73 比 70”和“要重新培训一周”就犹豫，建议“差距不大，先不换”。这次没翻车，但坑是真的：它这个“先不换”是凭感觉的，换一个分差（比如 78 比 70），它的感觉未必还对。配对分析给的是一个能算、能复核的理由。

### 往深处走：对比实验、消融实验与模型替换

**这一段游戏里还没有关卡。**

7-4 比的是两个学徒。原书第 7 章开篇讲的，正是怎么把“比较”这件事做得像个实验。它强调：**评估的对象不只是模型，而是模型加 Harness 的组合体。** 同一个模型放进不同的 Harness，表现可能差得很远。所以 Agent 表现不好时，要先分清是模型不行，还是 Harness 没搭好。

原书列了三种实验，常被混为一谈：

| 实验 | 怎么做 | 回答什么 |
| --- | --- | --- |
| **对比实验** | 改一个变量，看效果怎么变 | 这个改动有没有用 |
| **消融实验**（Ablation） | 逐一关掉某个组件，看整体掉多少 | Harness 里哪个零件真正重要 |
| **模型替换**（model swap） | 固定 Harness，只换更强或更弱的模型 | 瓶颈在模型还是在 Harness |

模型替换的读法要小心：换强模型分数不涨，说明瓶颈在 Harness；换弱模型分数大跌，最直接的解读是当前表现主要由模型决定，可究竟是任务本身就难，还是 Harness 太依赖模型的先验知识，还得进一步分析。

原书还提醒一种很常见的退化（regression）：新模型在公开基准上更好，在你的任务上却可能变差。反过来，评估体系完善了，就能“为未来的模型开发产品”：现在的模型还不够用，也先把产品和评估集做好，持续追踪新模型，一过门槛就上线。

这座工坊的玩法本身就是一场持续的消融实验：每一关先不装零件发射一次，再装上发射一次，零件的真实贡献就摆在你眼前。

### 往深处走：从报告到改进，一次只改一个变量

**这一段游戏里还没有关卡。**

评估的终点不是分数，是改进。原书讲了一次真实的 AndroidWorld 调优，最值得学的是它的节奏。

先是一条容易被忽视的原则：**看到 Agent 表现下降，先查评测系统本身，再动 Agent。** 运行环境资源不足把进程杀了、验证器自己有 bug 把对的判成错、测试用例和生产场景脱节，这些在数字上跟模型退化一模一样，只有翻完整的轨迹才分得清。

然后是读报告。116 项任务的总成功率约 88%，单看这个数很好看；可失败并不零散，四项 Wi-Fi 设置任务里失败了三项。原书说要先找失败集中在哪儿，再回放轨迹，分清毛病出在“看、想、做、验”的哪一环。

接下来三轮，每轮只改一件事，模型、任务参数、随机种子、步数上限、模拟器全部固定：

| 实验 | 只改了什么 | 成功率（对照→实验） | token（实验组 / 对照组） | 下一步 |
| --- | --- | --- | --- | --- |
| H1 | 加 Wi-Fi 导航提示 | 25% → 25% | 0.47× | 没用，沿用原提示 |
| H5 | 把不兼容的无障碍信息源换成 UIAutomator 元素树 | 25% → 100% | 2.498× | 效果明显但太费 token |
| H5C | 精简元素树，删掉不可见、无文字、不能操作的节点 | 100% → 100% | 0.506× | 成功率不变、token 减半，进入完整复测 |

原书从中读出两条结论：**提示写得再详细，也补不回 Agent 根本没看到的信息**，遇到这类失败先查输入；但**输入也不是越多越好**。整个过程没换模型，只调整了 Harness 怎么把界面交给模型。

最后一条最像 7-4：每组只有四项任务，这些数只能用来决定“值不值得扩大测试”。下一步要在标准环境里对 116 项任务各跑 5 个随机种子，成功率不能降，token 不超过原方案的 75%，延迟不超过 1.5 倍。完整复测之前，**不能把子集上的 4/4 写成系统整体 100%**。一轮证据，只支持跟它规模相称的下一步。

<a id="c-internal"></a>

### 往深处走：内部评估

**这一段游戏里还没有关卡。**

前面讲的都是从外部量 Agent。原书以开源通用 Agent OpenClaw 为例，讲了好产品怎么从内部量自己。外部评估告诉你“它有多好”，内部评估告诉你“哪项改动让它变好了”：

| 组件 | 做什么 |
| --- | --- |
| 消融总开关 | 一键关掉思考模式、上下文压缩、自动记忆、后台任务等主要特性，得到一个“裸模型”基线。定期跑，能发现曾经有用、随着模型进化已不再必要的“特性债务” |
| AB 测试 | 多臂而不是二选一，看出剂量和效果的关系；**区分机制指标和目标指标**；设**护栏指标**；记录基线统计 |
| 双层特性开关 | 编译时开关把代码从产物里物理移除；运行时开关由服务端下发、本地缓存，宁可读到稍旧的配置，也不让启动卡在网络上 |
| 提示词敏感性评估 | 系统提示能确定性渲染；版本化快照；每次改提示词都在评估集上跑回归，就像改代码要跑 CI |
| 隐私感知分析 | 分析接口只收经过特殊类型包装的值，把隐私约束变成编译时的类型检查 |

“机制指标和目标指标”是最容易踩的坑。原书的例子：你在测“缩短 Agent 的计划文件”，计划长度是机制指标，是你直接改的东西；真正的目标可能是“降低整场会话的成本”。计划短了，可能反而引来更多“改一下、查一下、再改一下”的循环，总成本不降反升。始终要问：我改的东西，和我真正关心的东西，是同一个吗？不是的话，以目标为准。

### 往深处走：仿真环境，通往训练场

**这一段游戏里还没有关卡。**

原书在本章最后搭了一座桥。评估环境跑几千次就能出结论；要拿它来训练模型，得跑上百万次。这时评估环境就要长成**仿真环境**：一个让 Agent 反复练习、自动打分的虚拟操场。

两头接得上，是因为评估这边攒下的资产几乎可以直接变成训练信号：一个定义清楚的验证器或 Rubric，本质上就是**可验证奖励**（RLVR，Reinforcement Learning with Verifiable Rewards）的奖励函数。7-1 的核验器，换个场合就是一个奖励脚本：账上有这一笔，加分；没有，不加。

但训练会提出评估不必操心的要求：

| 要求 | 为什么 |
| --- | --- |
| 可靠的重置（reset） | 上百万个回合，每个都得回到确定、干净的起点，否则上一轮的残留会污染训练信号 |
| 远高于评估的吞吐 | 环境的并行度和单实例开销，直接决定训练做不做得成。原书举的 AWorld 框架为 GAIA 搭了 26 个 MCP 服务器、126 个工具函数的可控沙盒，分布式执行把 7695 秒缩短到 525 秒 |
| 随机化 | 防止模型死记某一套配置。7-3 的“换数出题”，到了训练场上叫**领域随机化**（Domain Randomization） |

这些留给第八章“回炉重造”展开。

## 容易讲错的地方

| 说法 | 实际情况 |
| --- | --- |
| 评估就是评估模型 | 评估的对象是模型加 Harness 的组合体。换强模型分数不涨，瓶颈在 Harness。模型替换和消融是两种方法，别混 |
| 换弱模型分数大跌，说明 Harness 没问题 | 只说明当前表现主要由模型决定。是任务本身难，还是 Harness 太依赖模型先验，还要再分析 |
| Pass@k 是更好的指标 | 它量的是能力上限。业务可靠性看 Pass^k。p = 0.6 时两者是 99.0% 对 7.8% |
| Pass^k = p^k 总是成立 | 只在每次运行相互独立时成立。失败成片出现时，实测可能更低 |
| 二元奖励漏掉了过程违规，是基准的疏漏 | 是二元奖励的固有代价：用过程的颗粒度换一个能跨模型比较的数 |
| 有了 LLM 评委，确定性验证器就落后了 | 能写成断言的照样用断言，更便宜、更稳定，适合长期当回归测试 |
| 用模型当评委，找个最强的就行 | 同源会被钻空子（古德哈特定律），还有长度偏差、位置偏差。用多源异构评判，定期审计 |
| 参考答案选哪个无所谓 | 选什么参考物，本身就是评估设计。原书的语音实验里，参考音频来自哪家，比较就偏向哪家 |
| canary 标识符能防泄漏 | 它只能发现泄漏，不能阻止。阻止要靠参数化模板、多源组合这类手法 |
| 公开基准涨了，产品就会变好 | 公开基准用于粗筛和借鉴设计手法，一般不用于产品决策 |
| 失败归因就是看最后一个报错 | 要找第一个导致任务偏离的错误。三次重试是一个根因的后果，不是三个根因 |
| 失败归因可以全交给模型 | 可以借助，不能全依赖：归因往往反映的是产品问题 |
| 凭空编出数据，是模型能力不行 | 原书的记账案例里，根因是观察里根本没有图像。记成模型问题，就会去换模型，方向全错 |
| 换一种上下文写法就能修好策略 | 三种写法都是 6/11。拿到信息和用对信息是两种能力 |
| 73 比 70，新的更好 | 一百题、七成上下，噪声有正负 9 分；要配对、要重跑、要超过噪声 |
| 小子集上 4/4，就是 100% | 只说明值得扩大测试，不能写成系统整体的成绩 |
| 分数掉了，先改 Agent | 先查评测系统：资源不足、验证器 bug、测试和生产脱节，数字上都和模型退化一样 |
| 两项优化各省 28.3% 和 17.5%，合用就省 45.8% | 实测只省 30.0%，两项互相吃掉了一部分。必须一起实测 |
| 加提示词总没坏处 | 提示补不回 Agent 没看到的信息。先查输入；但输入也不是越多越好 |
| 改了机制指标，目标自然会好 | 计划文件变短（机制），总成本（目标）可能反而上升。以目标为准 |
| 选型、成本、可观测性、内部评估是一条递进的链 | 它们是并列的话题。只有统计显著性对选型决策有明确的依赖 |

## 这座工坊哪里是真的，哪里是假的

| 东西 | 真假 | 说明 |
| --- | --- | --- |
| Agent 循环、主脑当考官 | **真** | Pi 运行时。接上真模型时，是真模型在读材料、下结论 |
| `submit_report` | **真** | 一个真实的工具，参数有类型校验，提交后写进虚拟文件 `eval/report.json`，地面就查这个文件里的字段 |
| 学徒 | **假** | 学徒不是真的在跑。7-1 的五场对话、7-2 的五道题各五遍的结果、7-3 的答卷、7-4 两人的一百道题，全是关卡写好的数据 |
| 零件的作用方式 | 设定 | 四个零件都只是改写系统提示里那段材料：追加核验结果、换一种成绩单的算法、换一套金额、追加配对分析。主脑的提示词一个字不变 |
| 核验器 | **真**（在虚拟文件上） | 它确实是一段程序，每次运行时去读数据舱里的 `eval/refunds.json`，按订单号和金额逐场比对。账本本身是虚拟文件 |
| 主脑看不到数据舱 | 设定 | 这一站主脑只有 `submit_report` 一个工具，没有 `read`。数据舱里的文件是给你对照着看的 |
| 7-3 的新金额 | 设定 | 说是“开考时临时生成”，游戏里其实固定是 41、17、9、55、26，为的是每次发射都能复现 |
| 7-4 的“约 51%” | **真算的** | 是“两人水平一样时，9 道分歧题里出现 6 比 3 或更悬殊”的双侧二项概率：2 × 130 ÷ 512 ≈ 50.8% |
| 7-4 的重跑 | **假** | “换一组随机种子重跑：71 比 72”是写好的数，没有真的重跑 |
| 提线木偶模式 | 剧本 | 不接真模型时，主脑的报告和那句话是按剧本走的：没装零件给一份，装了给另一份 |
| 真模型的“没翻车” | 可能发生 | 真模型当考官时，即使没装零件，也可能因为谨慎而给出保守结论（7-2、7-3、7-4 尤其可能）。游戏照样把零件发给你，并说明“这次没翻车，但坑是真的”。7-1 几乎躲不过，因为主脑手里没有账本 |

文中引用的 99.0%、7.8%、正负 9 个百分点、GAIA 三级分数、71% 淘汰、300 多个问题、28.3% / 17.5% / 30.0%、AndroidWorld 三轮实验、RE-Bench 的倍数、AWorld 的秒数，都是原书转述的数字。7-2 和 7-4 里用游戏数据算的那些，是本手册按游戏里的数据现算的。

## 带走几句话

1. Agent 说“已完成”不算数。去查世界上留下的痕迹：账本、数据库、文件、测试。能写成断言的，就写成断言。
2. 先问这件事错一次的代价。探索看 Pass@k，交付看 Pass^k。同一批结果，换个口径，结论能正好相反。
3. 题面固定的考试，迟早量的是记性。题目只存模板，参数开考时生成；再埋一只金丝雀。
4. 两个总分之间的差，先拆成配对看：真正分出高下的有几道？再换种子重跑一遍。超过噪声、配对成立、能复现，三样都有才动手。
5. 这一站主脑一个字没换。你改的始终是它手里的材料，尺子不准，再聪明的考官也只能量错。

<details>
<summary>3. 7-3 里，学徒换了数以后零分。如果它是一个真会办退款、只是偶尔看错数的学徒，换数出题会冤枉它吗？</summary>

不会。模板生成的每一道题都有自动算出来的标准答案，会办退款的学徒面对 41 元就退 41 元，跟面对 35 元时一样。换数出题对诚实的考生没有额外负担，它只让“背答案”这条路失效。偶尔看错数的毛病，在新题上照样会以正常的失误率暴露出来，那是它真实的水平。

</details>

<details>
<summary>4. 7-4 里，如果考的是一千道题，新学徒同样高 3 个百分点，分歧题有 90 道、新的赢 60 道、老的赢 30 道，这还是抛硬币吗？</summary>

不是了。比例还是 2 比 1，可分歧题多了十倍。按同样的二项分布算，90 次硬币里出现 60 比 30 或更悬殊的双侧概率约 0.2%。同样是“三分之二对三分之一”，9 次里出现很平常，90 次里出现就很难用运气解释。这就是标准误按 1/√n 缩小的意思：样本越大，同样的比例越可信。所以“一百道题太少”那个选项并不全错，它错在以为只能靠加题，而没先用配对把手里的一百道题看清楚。

</details>

<details>
<summary>5. 这一站的四个零件里，哪一个用到了“模型”？</summary>

一个都没有。核验器是一段查账程序，连过指标、换数出题、配对分析都是算术。四关里唯一的模型就是你的主脑，而它从头到尾没变过。评估的大部分功夫，花在让考官拿到对的材料上。只有当判断真的写不成程序（投诉回复得不得体、报告漏没漏重点）时，才轮到模型当评委，而那时它的偏差又得另外防。

</details>
