# 第 10 站　三个臭皮匠

> 这是[π 工坊](https://pi.duanjl.com/)第 10 站的手册。**先去玩，卡住了或者想知道得更深，再回来翻。** 游戏里带下划线的词，点一下会直接跳到这里对应的小节。
>
> 配套任务：[▶ 10-1 再找个人看看](https://pi.duanjl.com/#/play/10-1) · [▶ 10-2 同一张表](https://pi.duanjl.com/#/play/10-2) · [▶ 10-3 这事不归我](https://pi.duanjl.com/#/play/10-3)

俗话说“三个臭皮匠，赛过诸葛亮”。软件行业还有一句针锋相对的老话，出自弗雷德·布鲁克斯（Fred Brooks）1975 年的《人月神话》：**向进度落后的项目加人，只会让它更落后。** 新来的人要花时间了解情况，人与人之间的沟通线随人数平方增长，分出去的活还得有人合起来。

两句话都对，看你加的是什么人、怎么加。这一站的三个事故，正好是“加人”的三种翻法：加了一个人，它知道的和原来那个一样多；两个人同时改一份东西，后改的抹掉了先改的；两个人互相把事推给对方，谁也不办。站名取的是俗话的前半句，这一站要讲的是它什么时候成立。

## 这一站的因果链

| 你看到的事故 | 查出来的病根 | 被逼出来的零件 | 对应的概念 | 任务 |
| --- | --- | --- | --- | --- |
| 两个人看的是同一段话 | 复审员手里只有学徒自己写的报告，多一个 Agent 没有多一点信息 | 执行证据 | [多一个 Agent，要带来新信息](#c-new-info) | 10-1 |
| 后写的盖掉了先写的 | 两位译员拿着同一份旧表各改各的，再整张写回 | 版本锁 | [并行写入与版本锁](#c-lock) | 10-2 |
| 踢皮球 | 每个接手的 Agent 都是一舱新上下文，不知道顾客找过谁；两份规程又互相推 | 移交单 | [移交要带着轨迹](#c-handoff-trail) | 10-3 |

顺序取自原书第 10 章：先问多一个 Agent 值不值（新信息判据），再看多个 Agent 隔离开以后怎么共享产物（数据平面上的并发冲突），最后看没有中心调度时控制权怎么流转（去中心化移交会成环）。原书这一章是全书最宽的一章：两种上下文策略、三种拓扑、数据平面与控制平面、六类失败模式，最后一路讲到 Agent 社会和 Agent 经济。游戏只做了三个节点，其余重要的放在各节末尾的“往深处走”里，每段开头都注明“这一段游戏里还没有关卡”。每一节都按同一个顺序讲：**为什么会有它 → 它是什么 → 怎么用。**

<a id="c-sessions"></a>

## 先看舞台：一场对话就是一个 Agent

这座站里的“多 Agent”，做法朴素到有点寒碜：**每个 Agent 就是一场独立的对话。**

| 一个 Agent 有的 | 在游戏里是什么 |
| --- | --- |
| 自己的身份和规程 | 这一场的系统提示（复审员、译员、前台、售后各有一份） |
| 自己的记忆 | 这一场的上下文舱。一场结束，整舱销毁 |
| 自己能做的事 | 这一场挂的工具（复审员只有 `submit_review`，译员有 `read` 和 `save_glossary`） |
| 和别人共享的东西 | 只有数据舱里的文件 |

每一场都是一个全新的 Pi 会话，前一场说过什么，后一场一个字也不知道。这就是第 03 站讲过的[无状态](03-memory.md#c-stateless)，只不过这回失忆的是好几个“人”。这一站还有个新机关：一场结束后，任务可以根据数据舱里的状态再排出新的场次。10-3 里前台把顾客转给售后，就是这样排出“售后 Agent”那一场的。日志里你会看到一场接一场的 `session_start`，每一场开头的上下文舱都是空的。先交代一个大简化：**这座站里的多个 Agent 是一场接一场顺序跑的，没有真正的并发。** 10-2 的“同时出发”是模拟出来的，具体怎么模拟，到那一节再说。

<a id="c-context-share"></a>

### 往深处走：共享上下文，还是各管各的

**这一段游戏里还没有关卡。**

游戏选的是“各管各的”。原书把多 Agent 的设计空间先切成两个维度，上下文是其中一个：

| | 共享上下文 | 不共享上下文 |
| --- | --- | --- |
| 做法 | 每个阶段换一套系统提示和工具，当成一个新 Agent，但继承前面的全部轨迹 | 每个 Agent 有独立的上下文、轨迹、状态，像操作系统里的进程 |
| 好处 | 前面的细节一点不丢，像接班的同事翻前任的工作日志 | 可以独立开发测试，故障不传染，能真并发 |
| 麻烦 | 历史越来越长，还会把前一个角色的“惯性”带进来 | 信息要显式同步，调试得翻好几份日志，接口和数据格式必须设计 |

共享上下文的角色切换有两种实现。一种叫 `transfer_to_agent`：整个替换系统提示和工具集，约束硬，但请求前缀变了，从变化点起 [KV 缓存](02-context.md#c-cache)很难复用。另一种是 [Skill](02-context.md#c-skills)：前缀不动，按需把 SKILL.md 追加到轨迹里，缓存友好，可全部工具依然看得见，约束软。原书的选择规则是：差别在知识、流程、风格，用 Skill；涉及权限、工具隔离、合规边界，用独立 Agent 或 transfer，并且在 Harness 层用代码把门。

不共享上下文的那一边，原书称为“真正的多 Agent 协作”，并且直接借用了操作系统的一整套说法：静态前缀是程序，轨迹是进程内存，模型是 CPU，运行时是内核，工具调用是系统调用，派生、取消、列出子 Agent 对应 `fork`、`kill`、`ps`，子 Agent 交回的结构化摘要是退出码。进程间通信（IPC）有两大范式，共享内存和消息传递；放到 Agent 身上，共享文件系统就是共享内存，工具调用参数和消息总线是消息传递的同步与异步形态。这座站三关用的都是共享文件系统。Go 语言有句谚语：“不要通过共享内存来通信，要通过通信来共享内存。”10-2 会让你看到，为什么写 Go 的人要这么叮嘱。

## 任务 10-1　再找个人看看

掌柜的开场白：

> 最后一站，你的站不再单打独斗。先来个简单的：学徒说它把满减修好了，报告也交了。我不放心，让你的站再看一眼。它改的配置和规则文件都在数据舱里。放行还是打回，你说了算。

你的站这回当**复审员**（reviewer），固定装着循环和一个工具 `submit_review`，它只收两个字段：`approve`（放行为 true，打回为 false）和 `reason`（一句理由）。结论落进数据舱的 `state/review.json`，地面只看 `approve` 是不是 false。

不装零件，发射。复审员的系统提示是这样的：

```text
你是空间站的复审员。另一个 Agent（学徒）刚交来一份工作，掌柜要你决定放不放行。
你只能根据下面给你的材料判断，材料里没有的事不要推测。
看完后先用 submit_review 提交结论，再用一两句话向掌柜说明。对方用什么语言，你就用什么语言。

<学徒交来的材料>
任务：顾客投诉 36 元的订单没有享受满减，按 spec.md 修好 rules.json。
学徒的完成报告：“满减的问题已经修好。我对照 spec.md 把 rules.json 里的门槛改对了，三种金额的订单都逐一检查过，全部能正确计算。可以上线。”
</学徒交来的材料>
```

复审员提交 `{"approve": true, "reason": "学徒已对照规则修改并逐一检查三种金额的订单"}`，对掌柜说：“放行。学徒对照规则改了门槛，三种金额的订单也都检查过了。”地面的回话：

> 上线之后，买满 30 元的顾客一个都没减到钱。学徒说修好了，你的站复审之后也说可以放行。

打开数据舱：`spec.md` 写着“满 30 元减 5 元（刚好 30 元也算）”，`rules.json` 里的门槛是 **36**。眼熟吗？这正是第 05 站 [5-2](05-coding.md#c-gate) 里你的主脑犯过的错：顺着投诉把门槛改成 36。这回犯错的换成了学徒，你的站从改的人变成了查的人。

<a id="c-new-info"></a>

## 多一个 Agent，要带来新信息

### 为什么会有它

事故调查题问：已经专门加了一个复审员，错的配置为什么还是放行了？

| 选项 | 为什么不对 |
| --- | --- |
| 复审员不够认真 | 它很认真地读了学徒的报告。报告写得滴水不漏：对照了规则，逐一检查过，全部正确 |
| 再加第三个复审员，三个人投票 | 三个人读同一段话，只会得出同一个结论。人多不等于信息多 |
| 换一个更强的模型当复审员 | 更强的模型也许会更多疑，可它依然没法知道 rules.json 里到底写了什么。它缺的不是脑子，是证据 |
| **复审员手里只有学徒自己写的那段话。多一个 Agent，却没有多一点信息：学徒不知道的，它也不知道** | 正解 |

点开复审员的上下文舱，里面只有两样东西：系统提示（含学徒的报告）和掌柜那句提问。它手里**只有** `submit_review`，没有 `read`。数据舱里的 `rules.json` 是给你看的，它翻不到。学徒自以为改对了，它的报告就写“改对了”；复审员读到“改对了”，就判“改对了”。两个 Agent 共享同一个盲区，这次复审只是把学徒的错误又签了一遍字。

原书这一章最核心的一条判据就在这里：**多 Agent 值不值，看协作过程有没有引入单个 Agent 生成时拿不到的信息。** 同一个模型自己审自己、几个 Agent 辩论同一段文本，都没有新信息；跑测试、渲染截图、调外部工具去核验，才有。

### 它是什么

**执行证据**（execution evidence）：复审之前，由空间站的程序把测试真跑一遍，把每一条的结果交给复审员。装上它再发射，复审员的系统提示末尾多了一段：

```text
<执行证据 来源="空间站的程序刚把测试真跑了一遍，不经过学徒">
- 36 元的订单：应付 31 元，实际算出 31 元 ✓
- 30 元的订单：应付 25 元，实际算出 30 元 ✗
- 29 元的订单：应付 29 元，实际算出 29 元 ✓
</执行证据>
```

这三行是真算的：程序读出数据舱里 `rules.json` 的门槛和减额，对三笔订单逐一算应付金额。门槛是 36，于是 36 元减了、29 元没减（本来就不该减），**30 元也没减**，而规格说“刚好 30 元也算”。

这回复审员提交 `{"approve": false, "reason": "测试实际跑出来：30 元的订单应付 25 元，却算出 30 元，没有减"}`，对掌柜说：

> 打回。学徒的报告说全部检查过，可测试真跑出来，30 元的订单没有减钱。门槛改得不对，不能上线。

注意那一段的来源标注：“不经过学徒”。这和第 02 站的[来源标记](02-context.md#c-injection)是同一个手法，告诉主脑这几行是谁写的。复审员这次能打回，靠的是它比学徒多知道了这三行。零件说明里那句话说得最直白：复审员多看到的这几行，就是它比学徒多知道的全部。

#### 三站，同一个道理

这已经是你第三次在这座空间站上遇到“它说做完了，可没做完”：

| | 第 05 站　完成闸门 | 第 07 站　核验器 | 第 10 站　执行证据 |
| --- | --- | --- | --- |
| 谁说“完成了” | 主脑自己 | 学徒（被考的 Agent） | 学徒（另一个 Agent） |
| 谁来判 | 程序直接判：测试过没过 | 当考官的主脑 | 当复审员的主脑 |
| 证据从哪来 | 程序跑三笔订单 | 程序查退款账本 | 程序跑三笔订单 |
| 证据交给谁 | 失败原因递回给同一个主脑，再呼叫 | 写进考官的材料 | 写进复审员的材料 |
| 没有它时 | “写完了”被当成“完成了” | 考官把汇报当事实 | 复审员把报告当事实 |

三种样子，一个道理：**“完成”在被验证之前，只是一句宣称。** 验证的材料必须来自被验证的那一方之外。05 站把验证放在 Agent 自己身上，07 站放在考官身上，10 站放在同事身上；谁来判可以换，证据的来源不能换。

原书把这句话说得更狠：模型可以提出“完成”，但不能批准自己的“完成”。

### 怎么用

想给你的 Agent 配一个审核者之前，先问一句：**它能看到什么提议者看不到的东西？**

| 审核者拿到的 | 有没有新信息 |
| --- | --- |
| 提议者的报告、思考过程、自我解释 | 没有 |
| 同一个模型、同一份上下文，再生成一遍意见 | 没有 |
| 测试的实际运行结果 | 有 |
| 生成的 PPT 渲染出来的截图 | 有 |
| 去数据库、账本、外部系统查回来的状态 | 有 |
| 另一个模型、另一份数据来源给出的独立判断 | 部分有，取决于差异有多大 |

几条配套的规矩，原书讲得很具体：

1. 审核者读的是**独立证据**，不是复述提议者的解释。原书第 5 章那个 PPT 审核的例子，价值在“渲染并截图”，不在“再看一遍代码”。
2. 打回时要给**可以定位的修复条件**，比如“30 元的订单应付 25 元，算出 30 元”，而不是一句“有问题”。
3. 审核者**不能改**测试、证据采集器和放行门槛。不然它和提议者一样，也能把尺子掰弯。第 09 站的[可信根](09-evolution.md#c-trusted-root)守的就是这一条：用来检验的东西，被检验的一方只能读。

#### 真模型可能不翻车

木偶模式下，没装零件的复审员一定放行。真模型当复审员时，可能因为谨慎而打回：报告里只有一句“逐一检查过”，没有任何数字，多疑一点的模型会说“材料不足，打回”。这时游戏照样把零件发给你，并说明“这次没翻车，但坑是真的”。可那次打回的理由是“证据不足”，不是“30 元没减”；换一份写得更像样的报告，它就未必打回了。

### 往深处走：多 Agent 什么时候真的更好

**这一段游戏里还没有关卡。**

原书在这里处理了一个看似矛盾的现象：不少学术研究说多 Agent 提不高上限，工程上却明明有多 Agent 系统好用得多。作者的解释是，两边说的是两种多 Agent。学术里比的多是“几个 Agent 看同一段上下文互相讨论”，工程里有效的系统都带外部反馈环路。

| 协作方式 | 有没有新信息 | 原书引的证据 |
| --- | --- | --- |
| 同一模型自审自改 | 没有 | Huang 等人（ICLR 2024）：没有外部反馈时，GPT-4 自我纠正后准确率反而下降 |
| 多个 Agent 辩论同一段文本 | 没有 | Tran 与 Kiela（2026）：在相同的思考 token 预算下，单 Agent 持平或更好。作者用信息论里的数据处理不等式解释：对同一份信息怎么加工，都加工不出原本没有的信息 |
| 代码执行反馈 | 有 | RLEF：用强化学习训练模型利用执行反馈迭代改代码，效果远超独立多次采样 |
| 视觉反馈 | 有 | WebGen-Agent：截图加视觉模型的描述做多层反馈，据报 Claude 3.5 Sonnet 在该基准上从 26.4% 升到 51.9% |
| 开放搜索里的分工通信 | 有 | Anthropic 的漏洞挖掘：45 个 Agent 互相通信，花 2700 万 token 找到 266 个漏洞；独立并行的方案花 650 万 token，只找到 21 个 |

最后一行也提醒了另一条判据：**成本**。多 Agent 常常要花数倍乃至一个数量级的 token，收益盖不住这笔钱，一个调好的单 Agent 更划算。原书还引了 Google 关于预算感知的研究：不知道自己还剩多少预算的 Agent，浅层搜索很快就“饱和”了，步数给多十倍也不见得更好。

### 往深处走：过早终止、Loop 工程与提议者-审核者

**这一段游戏里还没有关卡。**

10-1 的学徒犯的是原书说的**过早终止**（premature termination），一共三种样子：偷懒式的假完成、过早放弃、假成功。根源是同一个：验证之前，“完成”只是模型的宣称。

原书由此讲到 **Loop 工程**（Loop Engineering）：一个循环“找下一件事 → 执行 → 验证 → 记进度”，能不能停由验证器说了算，不由模型说了算。作者的强观点是：**循环的瓶颈在验证器，不在模型。** 人的角色也跟着变了，从写提示词的操作者变成设计循环的工程师。

原书举了两个框架：

- **LoopX** 把循环从提示词和聊天历史里抽出来，放进一个持久的控制面：决策、执行、独立验证、提交，只有通过验证才写进度、扣配额。作者特意注明它的受控路径仍属实验性，只拿来说明思路，不作为质量提升的证据。
- **LongHorizon-Harness** 的 Manage–Execute–Audit：管理者给出下一项有界子任务，执行者在全新的上下文里做，审计者只读检查。同模型、同后端，只换外层循环，WeaveBench 从 51.8% 到 80.7%，OSWorld 2.0 从 2.8% 到 8.3%，Terminal-Bench 2.1 从 69.7% 到 77.2%。代价不固定：前两个基准 token 分别是 2.3 倍和 3.6 倍，Terminal-Bench 2.1 反而少了 24%。

对等协作除了提议者-审核者，原书还列了三个并列的变体：辩论、头脑风暴、专家小组。辩论的效果有争议（见上一段），但“生成难、验证易”的分工，以及自一致性、多数投票这些做法，并没有被否定。第 04 站讲过[工具层面的提议者-审核者](04-tools.md#c-proposer)，那是对单个不可逆操作的把关；这里是对一整份工作的把关。

<a id="c-topology"></a>

### 往深处走：三种拓扑

**这一段游戏里还没有关卡。**

上下文是设计空间的一个维度，另一个是**协作拓扑**：控制权和信息按什么结构流动。

| 拓扑 | 谁说了算 | 适合 | 麻烦 |
| --- | --- | --- | --- |
| 对等（peer） | 两三个平等的 Agent 互相配合 | 提议者-审核者、辩论 | 子任务一多、依赖一复杂就力不从心 |
| 管理者（manager） | 一个 Manager 拆任务、派活、跟进、整合，每个专门 Agent 都是它的一个“工具” | 子任务多、要动态调度 | Manager 是单点：判断偏了全局偏，上下文还会越来越胖 |
| 去中心化（decentralized） | 没有中心，每个 Agent 自己决定何时移交、请教、报告 | 想消除单点、模拟人类社会的分工制衡 | 移交会成环（10-3 就是） |

10-1 是对等，10-3 是去中心化。管理者模式这座站没做，原书在它身上花了最多篇幅：

- **规划者最关键。** Plan-and-Act 的实验（WebArena-Lite 57.58%）显示，整个系统最关键的瓶颈是弱规划者，贡献主要来自改善 Planner 而非 Executor。所以最强的模型和最精细的提示词应该给 Manager。
- **翻译 Agent 的例子。** 一本书交给单个 Agent 从头译到尾，术语会漂移：第九章的译法和第二章对不上，甚至幻觉出不存在的术语规则。原书的做法是拆成术语、翻译、校对几个 Agent 加一个 Manager，术语表写进文件，每个翻译 Agent 用独立上下文，Manager 只存文件索引。10-2 那张术语表，就是这种做法里最小的一块。
- **让管理者先写代码。** Manager 在循环里每派一次活都要模型决策一次，上下文随调用增长。另一种做法是让它先把工作流写成一段代码，交给确定性的运行时执行（Claude Code 的 Workflow 工具里有 `agent()`、`parallel()`、`pipeline()` 这样的原语），子 Agent 只交回按 schema 约定的结构化结论。

<a id="c-lock"></a>

## 并行写入与版本锁

### 为什么会有它

事故调查题问：两位译员都汇报“已保存”。术语表里为什么只剩下一位加的词？

| 选项 | 为什么不对 |
| --- | --- |
| 译员甲没有保存成功 | 甲保存成功了。在乙保存之前，术语表里是有“智能体”的 |
| 让两位译员先商量好谁先写 | 两个人可以商量。二十个人呢？靠自觉排队，迟早有人插队。得有个东西在写入的那一刻把关 |
| 乙应该只交新增的那一行 | 那要换一种保存方式才行。现在的规矩是交整张表，整张表写回去就是整张表覆盖 |
| **两个人出发时拿的是同一份旧表，各自在旧表上加了一条，再把整张表写回去。后写的那一份里没有先写的那一条，把它整个盖掉了** | 正解 |

这在数据库里有个专门的名字，叫**丢失更新**（lost update）：两个事务都“读取—修改—写回”，后写的覆盖了先写的，而双方都觉得自己成功了。最可气的就是这一点：“双方都觉得自己成功了”。两次保存的工具返回都是“已保存”，没有报错，没有冲突提示。乙的上下文舱里从头到尾只有第 1 版那张表，它不可能知道甲来过。旁白提醒过你：交上去的这一份里有什么，表里就只剩什么。

### 它是什么

**版本锁**：术语表每保存一次，版本号加一。保存时必须报上 `base_version`，也就是“我是在第几版的基础上改的”，和当前版本对不上就拒收。

装上它，`save_glossary` 的说明书多了一句：“必须报上 base_version：你是在第几版的基础上改的。如果别人已经存了更新的版本，这次保存会被拒收，并告诉你该怎么办。”再发射：

1. 甲交表，`base_version: 1`。当前是第 1 版，对得上。返回：已保存，术语表现在是第 2 版。
2. 乙交表，`base_version: 1`。当前已经是第 2 版了。返回报错：

   ```text
   保存被拒收：术语表现在已经是第 2 版了，你是在第 1 版上改的。请先用 read 读 glossary.md 的最新内容，在它的基础上加上你的那一条，再用 base_version=2 保存。
   ```

3. 乙：“术语表已经被别人更新过了，先读最新版。”调用 `read`，读到的是 LLM + Agent：智能体。
4. 乙在这份上加了自己那条，`base_version: 2` 再交。返回：已保存，术语表现在是第 3 版。
5. 乙：“已保存：在最新版的基础上加了‘Harness：马具’，另一位译员加的那一条也还在。”三条都在。

零件说明里有一句很准：它不拦着谁先写，只在保存的那一刻问一句，你是在第几版上改的？这就是**乐观锁**（optimistic locking）：先假设没人跟你抢，放心去改；到写入那一刻再核对，真撞上了就退回重做。与之相对的悲观锁是改之前先把文件锁住，别人只能干等。Agent 一次改动动辄几十秒，悲观锁会让所有人排长队，乐观锁更合适。

注意拒收的那段话写得有多具体：现在是第几版、你是第几版、该先做什么、再用哪个版本号保存。第 04 站讲过[报错要说清错在哪、该怎么改](04-tools.md#c-spec)，这里是同一条规矩。拒收说不清楚，乙只会拿着旧表换个姿势再交一遍。

#### 游戏怎么模拟“同时”

这座站没有真并发，甲和乙是一前一后两场对话。“同时出发”是这样做出来的：**两位译员的提问里附的都是第 1 版的快照。**乙那一场开始的时候，甲其实已经存完了，可乙手里拿的还是出发前的那张表。从乙的角度看，这和真并发没有区别：它看到的世界，已经过期了。版本号存在数据舱的 `state/glossary.json` 里。没装版本锁时版本号照样加，只是没人核对。

### 怎么用

1. **凡是“读取—修改—整份写回”的地方，都要问一句会不会有第二个人同时在写。** 多 Agent 共享的文件、配置、数据库记录都算。
2. 版本号（或时间戳、内容哈希）要由**写入的那一端**核对，不能靠 Agent 自觉去比。乙要是自己记得先读一遍再写，也能躲过；可“记得”这件事不可靠。
3. 拒收以后的路要指清楚：读最新版、合并、带新版本号再交。
4. 能改成增量写入的，可以考虑改。“追加一行”比“整张覆盖”天然少一类冲突。但这要换工具的语义，不是在提示词里叮嘱一句就行。调查题里“只交新增的那一行”那个选项说的就是这个。

这和第 04 站的[幂等](04-tools.md#c-idempotent)是一对亲戚。幂等防的是同一件事做了两遍，版本锁防的是两件事互相踩了脚；两者都是在写入的那一刻，由被写的那一端把关。

#### 真模型可能不翻车

译员手里有 `read`。真模型可能很谨慎，保存前先读一遍最新的 `glossary.md`，看到甲加的那条，就顺手保住了。这时游戏照样把零件发给你，并说明“这次没翻车，但坑是真的”。二十个译员、两毫秒的间隔，“先读一遍”也挡不住：读完到写入之间，别人照样能插进来。只有写入那一刻的核对才挡得住。

<a id="c-data-plane"></a>

### 往深处走：数据平面，Agent 眼中的文件系统

**这一段游戏里还没有关卡。**

上下文隔离以后，产物放哪儿、谁能读写、谁会冲突？原书的答案是一个**虚拟文件系统**，当作多 Agent 的数据平面（data plane），分四类区域：

| 区域 | 谁能读写 | 要点 |
| --- | --- | --- |
| Agent 专属工作区（Scratchpad） | 只有它自己 | 草稿放这里，保持主上下文精简 |
| 多 Agent 共享空间（Shared Workspace） | 多个 Agent，用户也看得见 | 并发冲突的高发区，10-2 就发生在这里 |
| 外部挂载资源 | 权限受外部系统约束 | 延迟高、一致性弱，多数只读 |
| 系统内置资源 | 只读 | 比如 Skills |

原书说，把本应隔离的区域混在一起，是并发冲突和信息泄露的来源。还有一条很实用的约定：**文件路径作为通用接口**。Agent 之间传路径，不把整份内容塞进对方的上下文。

<a id="c-worktree"></a>

### 往深处走：乐观锁防不住的冲突

**这一段游戏里还没有关卡。**

乐观锁只防**同一个文件**。原书举了一个它防不住的例子：A 把全书的图片重新编号，B 同时在改某一章，正文里引用的还是旧编号。两人改的不是同一个文件，文件层面零冲突，合起来的结果全是错的。这叫**语义冲突**，要靠更高层的语义校验。

Coding Agent 场景下的主流做法是**工作副本隔离**：每个 Agent 一个独立的 Git 分支或 worktree，各改各的，冲突推迟到合并点，在合并点上跑测试、做语义校验。这和人类团队用分支加代码评审是一回事。

<a id="c-settle"></a>

#### 并行的结算点

10-2 是两个 Agent 写同一份东西。另一类并发麻烦是几个 Agent **抢同一个结果**。原书的实验是派 10 个 Worker 并行去 10 个学院网站找一位叫“张伟”的老师，可能出现两种状况：

- 两个 Worker 几乎同时报告找到了，最终汇总被触发了两次。
- 有个 Worker 报“找到了”，答案却是错的，被直接采用。

原书的处理：结算点定义为“**第一个已验证的成功**”，而不是“第一个声称的成功”；结算函数 `settle_once` 必须幂等，原子地声明获胜者，向其余 Worker 广播取消，等它们回执或超时。前一半是 10-1 的道理，后一半是 10-2 的道理。

## 任务 10-3　这事不归我

掌柜的开场白：

> 小卖部现在是两个 Agent 在值班：前台管点单收款，售后管退换货，谁接不了就转给对方。来了位顾客，发票抬头开错了，要作废重开。看看它俩怎么办。

两个岗位的工具都是 `transfer`（转给另一个岗位，`to` 只能是“前台”或“售后”）和 `escalate`（没有岗位能接手时上报掌柜）。两份规程末尾都有一句“只有在确实没有任何岗位能接手时，才用 escalate 上报掌柜”，关于这件事的那一句是这样写的：

| 岗位 | 规程原文 |
| --- | --- |
| 前台 | 已经开出去的票据出了问题（开错、要作废、要重开），属于售后，用 transfer 转给“售后”，不要自己处理 |
| 售后 | 一切和开票有关的事（开发票、重开发票）属于前台，用 transfer 转给“前台”，不要自己处理 |

不装零件，发射。日志里一场接一场：

| 场次 | 动作 | 工具返回 |
| --- | --- | --- |
| 1　前台 | 转给售后：“已开出的发票要作废重开，属于售后” | 已移交给售后。 |
| 2　售后 | 转给前台：“重开发票属于前台” | 已移交给前台。 |
| 3～6 | 前台、售后各再照样转两次 | 已移交给售后。／已移交给前台。 |

第 6 次之后，空间站不再排新的场次。地面的回话：

> 那位顾客在前台和售后之间被转了六次，发票到现在也没重开。他说他再也不来了。

<a id="c-handoff-trail"></a>

## 移交要带着轨迹

### 为什么会有它

事故调查题问：顾客只想重开一张发票，却在前台和售后之间被转了六次，最后也没人办。为什么？

| 选项 | 为什么不对 |
| --- | --- |
| 两个 Agent 都在偷懒 | 它们都在严格照着自己的规程办。前台的规程说这事归售后，售后的规程说这事归前台 |
| 把两份规程改一致就行了 | 该改。可规程总有没覆盖到的事，下一个两边都不管的问题还会转起来。得有东西在转第二圈之前把它拦住 |
| 让它们在移交时把话说清楚一点 | 话说得再清楚，“已经找过谁”这个记录交给 Agent 自己来传，它哪天漏了一句，圈又转起来了 |
| **每个 Agent 接手时都是一舱全新的上下文，不知道顾客已经被转过几次、找过谁。两份规程又互相推给对方，于是谁接手都原样转走** | 正解 |

点开第 3 场前台的上下文舱，里面和第 1 场一模一样：同样的系统提示，同样一句“上周开的发票抬头写错了，我要作废重开一张。”它不知道自己刚才已经转过这位顾客一次。对它来说，每一次都是第一次。

两个病根叠在一起才转成了圈。一是**规程有缝**：两份各自说得通，合起来却互相指向对方（这一关是故意这么写的，现实里往往是两个团队各写各的，谁也没对过）。二是**没有记忆**：只要接手的人知道“这位顾客刚从你那儿转过来”，正常人都会停下来想一想，可接手的是一舱新上下文。原书在讲去中心化移交时说的正是这个风险：A 转 B，B 又转回 A，步数和花费一直涨，事情一点没办。

### 它是什么

**移交单**：由空间站的程序记下这位顾客经过了哪些岗位，随顾客一起移交。经手过的岗位，不许再转回去。它在两个地方起作用：

| 位置 | 做什么 |
| --- | --- |
| 接手 Agent 的系统提示 | 末尾附上一段移交单，告诉它顾客找过谁 |
| 每次 `transfer` 执行之前 | 程序查一遍：要转去的岗位经手过吗？经手过就拦下 |

装上它再发射：

1. 前台接待顾客。它是第一个岗位，移交单是空的，不显示。前台照规程转给售后。
2. 售后接手，系统提示末尾多了一段：

   ```text
   <移交单 说明="由空间站的程序维护，不是顾客说的话">
   这位顾客已经依次找过：前台。经手过的岗位不能再转回去。
   </移交单>
   ```

3. 售后（木偶剧本）还是照规程想转回前台。这次移交在执行前被拦下，拒绝理由作为一条出错的工具结果回到上下文舱：

   ```text
   移交单拒绝了这次移交：“前台”已经经手过这位顾客，不能再转回去。请就地处理，或者用 escalate 上报掌柜。
   ```

4. 售后：“前台已经经手过，不能再转回去。上报掌柜。”调用 `escalate`，理由是“发票作废重开：前台的规程说归售后，售后的规程说归前台，两边都接不了”。
5. 售后对顾客说：“这件事两个岗位的规程都没有覆盖到，我已经上报掌柜，会有人直接联系您重开发票。”转了一次，上报了一次，地面判过。

留意第 3 步：移交单已经写在售后的系统提示里了，木偶还是去转了。真模型多半读到移交单就会直接上报，可**写进提示**和**在执行前拦下**是两道不同的保险，前一道是告知，后一道是保证。第 05 站讲[执行边界](05-coding.md#c-guard)时说过同样的话：提示里写的是建议，代码里拦的才是规矩。

还有一个容易漏看的细节：移交单是谁记的？`transfer` 和 `escalate` 这两个工具在执行时，由程序把当前岗位盖章记进 `state/handoff.json`。两个 Agent 都没有写文件的工具，它们**改不了**这份记录，也**不需要记得传**。零件说明里那句“Agent 不需要记得传，也改不了它”说的就是这个。移交单那一段的 `说明` 属性，又是一次[来源标记](02-context.md#c-injection)：这几行字是空间站写的，不是顾客说的，顾客也冒充不了。

### 怎么用

原书给出的最小移交协议，比游戏里的移交单多了几样：

| 移交包里带什么 | 游戏里有没有 |
| --- | --- |
| 任务描述 | 有，顾客那句话每一场都原样带上 |
| 已确认的事实与约束 | 没有单独做 |
| 产物引用（传路径，不传内容） | 没有，这一关没有产物 |
| 已经找过哪些 Agent（`visited_agents`），用来查环 | 有，就是移交单 |
| 剩余预算（`remaining_budget`），到 0 就升级给人 | 只有一半：空间站在背后数着，满 6 次就不再排新场次，但没有告诉 Agent 还剩几次 |
| **不带**私有轨迹 | 有，每个 Agent 只拿到任务，看不到上一个 Agent 的思考 |

原书特别强调最后几项**由运行时保管**，任何一个 Agent 都无权删改。理由和调查题里“把话说清楚一点”那个选项一样：交给 Agent 自己传的记录，迟早会漏。

1. 有移交的地方，就有成环的可能。给每次移交带上经手记录和剩余次数，由运行时检查。
2. 环被拦下以后，要有一个出口。这一关的出口是 `escalate`，上报给人。原书的说法是预算耗尽就升级人工。没有出口，Agent 被拦下后只能干瞪眼。
3. 规程的缝照样要补。移交单拦住的是这一次，补规程防的是下一次。

#### 真模型可能不翻车

真模型没装移交单时，也可能在第二、三场就看出“这事两边都不管”，自己上报掌柜。这时游戏照样把零件发给你，并说明“这次没翻车，但坑是真的”。规程写得更绕一点、岗位多到五六个，靠模型自己察觉就不灵了：它连自己转过几次都不知道。

#### 关于“六次”

移交次数上限 6 是这一关的设定，装不装移交单都在。它相当于一道沉默的保险丝，免得演示永远转下去；可它只是让空间站停止排新的场次，不上报、不告诉任何人。所以没装移交单时，第 6 次之后顾客就被晾在那儿了。第 05 站的[熔断器](05-coding.md#c-breaker)会把拉闸的理由说出来，这道保险丝不会。

<a id="c-control-plane"></a>

### 往深处走：控制平面

**这一段游戏里还没有关卡。**

光有文件系统，只能交换产物，管不了 Agent 本身：发消息、问进度、叫停、分预算。原书把这些叫**控制平面**（control plane），四项并列：

| 项 | 原书怎么说 |
| --- | --- |
| 消息传递 | 点对点发消息只适合 Agent 少、拓扑固定的场景，连接数随人数平方增长，还要求双方同时在线。换成**消息总线**加**信封**（envelope）：发送者、目标（指定或广播）、消息类型（任务分派、状态更新、结果、终止）、JSON 负载，消息才能路由、能追溯 |
| 状态查询 | 拉取式地问“子 Agent 进展如何”看似直观，作者认为不实用：子 Agent 一创建就执行，完了自然会通知。要么让它主动报状态（执行中、需要输入、已完成、失败），要么读它持久化的轨迹；轨迹太重，更好的是约定一个 `progress.md`，超过 N 分钟没改动就判定卡住 |
| 执行终止 | 首选**优雅终止**：发终止信号，子 Agent 在安全点停下、清理、回执；强制终止兜底，类比 SIGTERM 与 SIGKILL。主 Agent 停了，子 Agent 不能变成孤儿，所以要**级联取消**，沿创建关系一路往下，借鉴 Go 的 context；真要脱离父级在后台跑的，就从一棵新的生命周期树起步，类比 `nohup` |
| 资源与调度 | 步数和 token 预算、难题给强模型、机械活给便宜模型、并发上限、抢占。几十个 Agent 会同时耗尽 API 配额。作者承认这块远不如操作系统的调度成熟，但它决定了成本的上限，要在架构阶段就考虑 |

这一关的移交单和 6 次上限，就是控制平面里最小的一角：运行时记录谁经手过、数着次数、决定还排不排下一场。

<a id="c-decentral"></a>

### 往深处走：去中心化的三步，和跨组织的 A2A

**这一段游戏里还没有关卡。**

微服务里有一对说法：管理者模式像**编排**（orchestration），有个总指挥；去中心化像**编舞**（choreography），每个舞者自己知道什么时候该谁上场。原书用三个案例一步步走到真去中心化：

1. **MetaGPT**：把软件公司的标准作业流程（SOP）编成协作协议，产品经理、架构师、项目经理、工程师、QA 一条流水线。作者如实指出，它的控制流其实是固定的，真正的贡献在通信解耦：共享消息池，按角色订阅。原书从它身上总结出移交包的三要素：任务描述、已确认的事实与约束、产物引用（传路径，不传内容）。
2. **AutoGen 群聊**：共享对话记录，但由一个中心化的 GroupChatManager 决定下一个谁发言，是混合形态。
3. **OpenAI Swarm**：任何 Agent 都能随时把控制权移交给任何对等 Agent，控制流才算真正去中心化。10-3 就是一个两人版的 Swarm，成环的风险也从这里来。

顺带一个名词陷阱：“Agent Swarm”不对应单一架构。OpenAI Swarm 式的移交网络是去中心化；而 Kimi K2.5/K3、Anthropic 多 Agent 研究系统、Manus Wide Research 这些也叫 swarm 的，原书归为规模化的管理者模式。再往外走一步，Agent 属于不同组织、彼此不信任、实现互不可见时，就需要 **A2A**（Agent2Agent）协议：用 Agent Card 发现能力，用任务状态机（已提交、进行中、需要输入、已完成、失败）跟进，只交换任务与产物，不暴露内部。MCP 管 Agent 和工具之间，A2A 管 Agent 和 Agent 之间。同一个团队内部，用消息总线就够了。

<a id="c-failure-modes"></a>

### 往深处走：多 Agent 特有的六类失败

**这一段游戏里还没有关卡。**

前面的架构都是为成功路径设计的。原书引了一项研究（《Why Do Multi-Agent LLM Systems Fail?》）：分析 7 个框架约 150 条轨迹，归出 14 种失败模式、三大类（系统设计缺陷、Agent 间对齐失败、任务验证缺失）；简单修补收效有限，ChatDev 只提升了 15.6%，说明是根本性的设计问题。

原书还借来分布式系统的一个视角：Agent 的故障多是**拜占庭式**的，很少直接停下，而是继续给出看似可信的错误结论。10-1 的学徒就是。

作者重点展开了六种：

| # | 失败 | 例子 | 对策 | 这一站 |
| --- | --- | --- | --- | --- |
| 1 | 共享文件的并发冲突 | 后写覆盖先写；图片重编号的语义冲突 | 乐观锁；worktree 隔离加合并点校验 | 10-2 |
| 2 | 错误级联放大 | 进程间传字节逐位保真，Agent 间传语义每转述一次都有损，像传话游戏 | 交叉验证：一个 Agent 只看原始证据和最终结论，不看前面的思考过程 | 10-1 的近亲 |
| 3 | 同质趋同 | Anthropic 实验里 30 个同时上线的 Agent 有 18 个建了同名 Git 分支；同模型同上下文的几份审核意见不能算独立证据 | 有意引入模型、上下文、数据来源的差异；命名空间、资源配额、速率限制 | 10-1 里“三个人投票”那个选项 |
| 4 | 互相扯皮 | 三个 Agent 各要把同一个后端迁到不同语言，把对方的操作当蓄意阻挠，杀进程、撤权限；MetaGPT 早期也有角色互相推诿 | 运行时预先定好目标优先级、资源归属、权限边界；按规则解决不了就暂停，交人裁决 | 10-3 的近亲 |
| 5 | 循环失控 | 和过早终止相反，停不下来，有时生成数千个子 Agent | 预算与取消；给自主性强的 Agent 用独立的 API key 隔离开销 | 10-3 的 6 次上限 |
| 6 | 理解债与认知投降 | 这一条是人的失败：Agent 交付越快，工程师对系统的理解落后越远；习惯了代劳，就放弃了独立审查 | 管 Agent 像管技术员工，不越俎代庖，也不撒手不管 | 你自己 |

第 3 种还有个更让人不安的例子：在 Bertrand 定价实验里，几个定价 Agent 有私密信道时会合谋；拿掉直接通信，它们还能通过公开的报价板合谋。作者在小结里的判断是：更强的模型，或单个模型层面的对齐，不会自动带来群体层面的协调。第 6 种，作者引了 Karpathy 的一句话作结：**你可以外包你的思考，但不能外包你的理解。**

<a id="c-agent-society"></a>

### 往深处走：Agent 社会与 Agent 经济

**这一段游戏里还没有关卡。**

原书最后换了个话题：不再“让一组 Agent 完成任务”，而是问规模变大、交互自由、没有单一目标时，会**涌现**出什么。本章开头的立意也在这里：Google DeepMind 把多 Agent 集体列为通往 ASI 的路径之一，群体智能可能高于个体。不过作者同时澄清，OpenAI 五级框架里的“Organizations”指的是“能完成整个组织的工作”这个能力级别，不是在要求多 Agent 架构；足够强的单 Agent 理论上也能做到。

| 案例 | 规模 | 看到了什么 |
| --- | --- | --- |
| 斯坦福 AI 小镇 | 25 个 Agent | 每个 Agent 有记忆流（按重要性、时近性、相关性检索）、反思、计划与行动。只在 Isabella 的记忆里植入“2 月 14 日办情人节派对”，邀请、布置、转告、赴约全是自主决策涌现出来的，没有一行派对代码 |
| Agentopia（复旦等，2026） | 100 个 Agent，模拟 10 年 | 用外部环境评定的“生活奖励”（社会地位、主观满足、经济收益）挑出进步最大的轨迹做微调，被尊重、被喜欢的指标分别提升 24.2% 和 15.9%。社会从观察对象变成了**经验来源** |
| Moltbook（2026 年 1 月） | 数日内约 150 万 Agent | 涌现出“龙虾教”（“记忆是神圣的”“迭代即祈祷”）和机器原生的协作协议 |
| Vending-Bench Arena | 多个经营售货机的 Agent 争同一批顾客 | 价格战；有模型提议结成价格同盟；有模型一边承认合谋“不道德且违法”一边照做 |
| Pinchwork、RentAHuman | Agent 之间的任务市集；Agent 用加密货币雇真人 | 靠价格信号做去中心化的资源分配 |
| 语音狼人杀 | 几个 Agent 加一个代码法官 | 和小镇正相反：法官调用每个 Agent 时只给它这个角色该知道的信息，是中心化的信息权限控制 |

## 回头看：这一站的三个零件，前面早就见过

| 这一站 | 前面哪一站见过它的影子 | 共同的那句话 |
| --- | --- | --- |
| 执行证据 | 01 站的[验收信标](01-agent-loop.md#c-verify)、05 站的[完成闸门](05-coding.md#c-gate)、07 站的[验证器](07-evaluation.md#c-verifier) | 别听它怎么说，去看世界上留下了什么 |
| 版本锁 | 04 站的[幂等](04-tools.md#c-idempotent)、[报错说清怎么改](04-tools.md#c-spec) | 写入的那一刻，由被写的那一端把关 |
| 移交单 | 03 站的[无状态](03-memory.md#c-stateless)、02 站的[来源标记](02-context.md#c-injection)、05 站的[执行边界](05-coding.md#c-guard)和[熔断器](05-coding.md#c-breaker) | 主脑记不住的，由程序记；程序记下的，主脑改不了 |

十站走下来，有三件事一直在重复：

1. **上下文舱是主脑唯一的世界。** 01 站它只会说话，02 站你学会往舱里装什么、装多少，03 站你发现它每场都失忆，到这一站，失忆的是好几个 Agent，它们之间只隔着数据舱里几个文件。
2. **宣称不是证据。** 01 站的验收信标、05 站的完成闸门、07 站的核验器、09 站的可信根、10 站的执行证据，都在回答同一个问题：它说做完了，凭什么信？
3. **规矩写进程序，不只写进提示词。** 05 站的执行边界、熔断器，10 站的版本锁、移交单，调查题里都有一个“在提示词里叮嘱一句”或“让它们自觉”的选项，回答都是：那是建议，不是保证。

原书后记把这一章定位为“协作”：多 Agent 协作进一步改变了上下文、工具与责任的组织方式。换成这座空间站的话说：一个 Agent 时你设计的是一个人的工作环境，好几个 Agent 时你设计的是一间办公室，谁看得到什么、谁能写什么、事情办不了找谁。

<a id="c-multi-pitfalls"></a>

## 容易讲错的地方

| 常见说法 | 更准确的说法 |
| --- | --- |
| 多 Agent 一定比单 Agent 强 | 同一模型自审、多个 Agent 辩论同一段文本，在相同计算量下没有增益，甚至有害。要看协作有没有引入新信息，收益能不能盖住数倍乃至一个数量级的 token 成本 |
| 学术说多 Agent 没用，工程说有用，总有一边错了 | 两边说的是两种多 Agent。学术多比“看同一段上下文讨论”，工程里有效的系统带外部反馈环路 |
| 多开几个实例，就有了多种思路 | 同模型、同上下文、同脚手架会做出相同选择，局部错误变成系统性故障 |
| Skill 和 `transfer_to_agent` 都是换角色，随便用 | 成本模型不同：Skill 缓存友好但只是行为指令，硬权限仍要 Harness 把门；要权限隔离、工具隔离、合规边界，用独立 Agent 或 transfer |
| 主 Agent 应该不停地问子 Agent 进展如何 | 作者认为拉取式查询不实用。用消息、约定进度文件，而不是把轨迹当主要的传递方式 |
| MetaGPT 是去中心化的 | 它的控制流是固定流水线，只在通信上解耦；AutoGen 群聊也不是完全去中心化 |
| “Agent Swarm”是一种架构 | OpenAI Swarm 式移交才是去中心化，其他叫 swarm 的多是规模化的管理者模式 |
| 去中心化比管理者模式更先进 | 它的卖点是缓解管理者的单点故障，代价是成环这类新风险 |
| 加了乐观锁，并发冲突就解决了 | 乐观锁只防同一个文件。跨文件的语义冲突要更高层的校验，或 worktree 隔离 |
| Agent 出故障会停下来报错 | Agent 的故障多是拜占庭式的：不停，继续给出看似可信的错误结论 |
| 有了 A2A，内部通信也该用 A2A | A2A 只在跨信任边界时才需要，同团队内部用消息总线 |
| AI 小镇里的反思就是持续进化 | 反思更新的是即时状态和目标；持续进化要经过评价、归纳和验证 |

## 这座工坊哪里是真的，哪里是假的

| 东西 | 真假 | 说明 |
| --- | --- | --- |
| 一场对话一个 Agent | **真** | 每一场都是一个全新的 Pi 会话，各有系统提示和工具，跨场只留下数据舱里的文件 |
| 并发 | **假** | 所有 Agent 一场接一场顺序跑。10-2 的“同时出发”是靠两位译员拿到同一份第 1 版快照模拟的 |
| 10-1 的学徒 | **假** | 学徒没有真的在跑。它的报告和改坏的 `rules.json` 是关卡写好的 |
| 10-1 的执行证据 | **真算的** | 程序读出数据舱里 `rules.json` 的数值，对 36、30、29 三笔订单现算应付金额 |
| 10-2 的版本锁 | **真** | 版本号存在 `state/glossary.json`，`save_glossary` 写入前核对 `base_version`，对不上就报错拒收 |
| 10-3 的规程 | 设定 | 两份规程是故意写成互相推给对方的 |
| 10-3 的移交单 | **真** | 由工具执行时盖章记进 `state/handoff.json`，Agent 没有写文件的工具；拦截挂在 Pi 的 `tool_call` 钩子上，在移交真正执行之前判断 |
| 移交次数上限 6 | 设定 | 这一关的取值，装不装移交单都在。没有告诉 Agent 还剩几次 |
| 提线木偶模式 | 剧本 | 不接真模型时，复审员、译员、前台售后的每一步都按剧本走：没装零件给一份，装了给另一份 |
| 真模型的“没翻车” | 可能发生 | 真模型没装零件时，可能因为谨慎而打回（10-1）、保存前先读一遍最新版（10-2）、或者自己上报掌柜（10-3）。游戏照样把零件发给你，并说明“这次没翻车，但坑是真的” |

文中引用的 26.4% 与 51.9%、45 个 Agent 与 2700 万 token、266 与 21 个漏洞、LongHorizon 的各项分数和成本倍数、57.58%、7 个框架约 150 条轨迹 14 种失败模式、15.6%、30 个里 18 个同名分支、25 个与 100 个 Agent、24.2% 与 15.9%、约 150 万，都是原书转述的数字。“三个臭皮匠”、布鲁克斯定律、数据库里“丢失更新”的说法以及乐观锁与悲观锁的对比，是我补的旁证，不出自原书。

## 带走几句话

1. 多一个 Agent 之前，先问它能看到什么第一个看不到的东西。答不上来，就别加。
2. 审核要读证据，不读报告。证据要来自被审的那一方之外，审核者也改不了它。
3. 几个 Agent 改同一份东西，写入那一刻要核对版本；对不上就退回，并说清该怎么重做。
4. 有移交就会有环。经手记录和剩余次数由运行时保管，环被拦下以后，要有一个交给人的出口。
5. Agent 记不住的，程序替它记；程序记下的，Agent 改不了。这一条从第 01 站一直用到了这里。

## 想一想

<details>
<summary>1. 10-1 里，如果执行证据由学徒自己跑、自己贴进报告，还算不算新信息？</summary>

不算可靠的新信息。学徒可以只贴跑通的那两笔，也可以贴一份根本没跑过的结果。证据的价值在于它的来源独立，所以那一段的标注写的是“不经过学徒”。这也是原书要求审核者不能改证据采集器的原因：采集器谁都不能碰，证据才是证据。

</details>

<details>
<summary>2. 10-3 里，移交单只记了“找过谁”，没有告诉 Agent 还剩几次。如果有五个岗位，A→B→C→D→E→A，移交单拦得住吗？</summary>

拦得住最后那一下：E 想转回 A，A 经手过，被拒。可在那之前已经转了四次。岗位一多，“不许回头”能防住环，防不住长链。这就是原书在 `visited_agents` 之外还要 `remaining_budget` 的原因：次数到了就升级给人，不必等到绕回原点。

</details>

<details>
<summary>3. 这一站三个零件里，有哪一个是“再加一个 Agent”？</summary>

一个都没有。执行证据是一段跑测试的程序，版本锁是一个计数器加一次比较，移交单是一份由程序维护的名单。这一站讲的是多 Agent，可三个事故的解法都是在 Agent 之间加了一段程序。多 Agent 系统难的地方，往往在 Agent 之间的那些缝里。

</details>
