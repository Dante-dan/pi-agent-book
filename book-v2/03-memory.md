<a id="c-stateless"></a>

## 模型没有状态

### 为什么先讲这个

因为这一站所有的零件，都是为了对付这一件事。

### 它是什么

回想第 01 站学到的：模型知道的只有两样东西，训练时读过的，和此刻上下文舱里装着的。第 01 站还留了一句没展开的话：**上下文舱里的东西，只属于这一场对话。**

在任务 3-1 里你会亲眼看到这句话的意思。昨天那场对话一结束，整舱内容当场销毁，方块一块块掉下去。今天老周再来，面对他的是一个空空如也的新舱。昨天他说过的每一个字，都不在里面。

人和人打交道不是这样的。常去的那家面馆，老板看你进门就喊“老样子？”。模型做不到，原因很朴素：没有人把“老样子”三个字放进它今天的上下文舱。

| | 人 | 模型 |
| --- | --- | --- |
| 昨天聊过的事 | 记得 | 不在今天的上下文舱里，等于没发生 |
| 同一件事说第二遍 | 会不耐烦 | 当成第一次听 |
| 相同的工作 | 越做越熟 | 每次从头做 |

最后一行是最费钱的：相同的调查、相同的确认、相同的弯路，它每次都重走一遍。

### 怎么用

把“模型不记得”当成一条物理定律，而不是一个待修的毛病。接受它，然后问一个更有用的问题：**哪些东西值得我替它记，记在哪儿，下次怎么放回去？**

<a id="c-user-memory"></a>

## 用户记忆：把值得记的存到会话之外

### 为什么会有它

任务 3-1 的事故调查，结论是“昨天那一舱在结束时就销毁了”。最直接的办法是别销毁：把每一场对话的全文都留着，下次原样塞回去。

这条路走不通。老周来了一百次，就得把一百场对话全部塞进上下文舱，而其中九十九场半都是“来份清蒸鲈鱼”“好的”。有用的只有一句：他不吃香菜。

### 它是什么

所以做法是在对话结束后，**多花一次模型调用**，专门干一件事：从刚才的对话里挑出以后还用得上的事实，存到会话之外。下次这位顾客再来，把属于他的那几条放回上下文舱最前面。

原书用的例子是订机票。用户说“帮我订下周五去东京的航班，我喜欢靠窗，我吃素”，对话结束后提取出来的是：

```text
- 用户偏好靠窗座位
- 用户是素食者，航班上需要特殊餐食
- 用户的常旅客号码：12345678
```

注意它没有记“搜索返回了 3 个航班”。好的提取同时满足三条：

| 规则 | 意思 | 老周的例子 |
| --- | --- | --- |
| 选择性 | 只挑以后用得上的，丢掉一次性的细节 | 记“不吃香菜”，不记“今天点了清蒸鲈鱼” |
| 抽象化 | 把这一次的说法归纳成长期的偏好 | “今天别放香菜”归纳成“不吃香菜” |
| 结构化 | 存成以后找得到的样子 | 写清是哪位顾客，按人分开放 |

在游戏里，这一步是一场紫色标签的“对话”：对话结束 · 提取记忆。你会看到上下文舱清空之后，主脑又被呼叫了一次，这次交给它的不是顾客的话，而是刚才整场对话的文字记录。它调用 `remember` 工具，一条事实落进了记忆舱。

### 轨迹和记忆不是一回事

这里有两样东西容易混：

| | 轨迹 | 用户长期记忆 |
| --- | --- | --- |
| 是什么 | 一场对话的完整原始记录 | 跨多场对话提炼出的稳定事实 |
| 怎么变 | 只往后追加，不改 | 会被改写、合并、淘汰 |
| 打个比方 | 流水账 | 档案 |

上下文舱里那一串方块就是轨迹。记忆舱里的才是档案。

### 怎么用

设计记忆时先问三个问题，它们互不相干，可以分开回答：

- **放哪里**：这一场对话里用的，还是跨对话要留的？
- **怎么存**：一句话的便条，还是带字段的卡片？
- **存什么**：一件具体发生过的事，一条稳定的偏好，还是一套做事的流程？

后两个问题，这一站后面的任务会一个一个逼你回答。

## 知识库：从“这个人”到“这一类人”

### 为什么会有它

有了记忆舱，老周不用再交代第二遍。可任务 3-2 来了个新面孔。

深潜组的老吴说过：出舱前 24 小时不能吃豆制品。小林也说过，还特意强调“这是我们组的规矩”。记忆舱把这两条都好好地存了下来，一条在老吴名下，一条在小林名下。

然后阿青来了。他也是深潜组的，明天出舱，点了一份麻婆豆腐。空间站痛快地下了单。

记忆舱没有出故障。问题在于**记忆是按人存的**：阿青是新人，他名下一条记录都没有。而“深潜组都这样”这句话，没有写在任何地方。

### 它是什么

换一个你更熟悉的版本。某位顾客说自己不吃香菜，这是他个人的事，记在他名下就够了。可如果你发现来过的每一位穆斯林顾客都说不吃猪肉，这就不再是哪个人的偏好，而是**一类人的规矩**。把它在每个人名下各记一遍是不够的，因为下一位穆斯林顾客进门时，他名下还是空的。

这两种记忆解决的是同一个问题，只是尺度不同：

| | 用户记忆 | 知识库 |
| --- | --- | --- |
| 记的是谁 | 这一个人 | 这一类人，或者所有人 |
| 例子 | 老周不吃香菜 | 深潜组出舱前不吃豆制品 |
| 谁能读到 | 只在这位顾客的对话里 | 每一位顾客的对话里 |
| 让助手成为 | 懂你的助手 | 懂行的专家 |

> 游戏里没有用“穆斯林不吃猪肉”这个例子，原因是模型本来就知道这条常识，不装知识库它也能答对，这一关就测不出东西了。深潜组的规矩是编的，模型不可能事先知道，只能靠你的设计。

### 规则不会自己冒出来

知识库里的那条规则是哪儿来的？没有任何一位顾客说过“请把这条写成规则”。

原书讲过一个客服的例子。几百条工单各自记着一次处理结果：退伍军人通过了，医生拿到了折扣，教师被告知不符合条件。现在来了位护士问“我能不能享受优惠”。翻遍工单，没有一条写着资格范围。离“护士”最近的是“医生”那条，于是系统顺势推断护士也可以；要是“教师”那条碰巧排在前面，同一个问题就会得到相反的答案。

毛病出在三个地方：

- **只看最像的那一条**：谁排在前面就信谁。
- **边界不在任何一条个案里**：“仅限这几类，其他一律不适用”这种话，没有哪条工单会写。
- **不知道自己没看全**：手里就这几条，照样答得很自信。

解决办法是在平时就把功夫下了：**通读全部个案，提炼成一条带适用范围的规则。** 游戏里这一步叫“夜间整理”，标签也是紫色的。没有顾客的时候，空间站把所有人的记忆摆在一起，再呼叫一次主脑，问它：有没有哪句话，不止一个人说过？

### 怎么用

三条经验：

1. **把原始个案直接堆进去是不够的。** 不管是塞进上下文还是放进检索系统，没有提炼过的东西，模型都用不可靠。
2. **规则要写清适用范围。** “不吃豆制品”是不够的，得是“深潜组成员，出舱前 24 小时内”。
3. **别人的私事别进来。** 把所有人的记忆都塞给每个人，既塞不下，也不该塞。知识库里放的是规则，不是别人的档案。

<a id="c-formats"></a>

## 怎么存：从便条到卡片

### 为什么会有它

任务 3-3 里，老周前天给自己点菜，说“多放辣”；昨天替父亲带饭，说“少盐，一点辣都不能放”。记忆舱老老实实记下了两条：

```text
- 老周：口味重，多放辣
- 老周：少盐，不放辣
```

今天老周又给自己点，说“按我的口味做”。空间站翻开记忆，两条互相矛盾的话都挂在老周名下。它挑了后一条。

记忆没丢，是**记的时候把“这是替谁说的”丢了**。

### 它是什么

同一条信息，可以存得很省，也可以存得很全。原书把它排成四级，每一级都是为了补上一级的缺口，同时带来新的代价：

| 格式 | 长什么样 | 好处 | 毛病 |
| --- | --- | --- | --- |
| Simple Notes | 一条一个最小的事实：“用户邮箱：john@example.com” | 最便宜，存取都快 | 关系全丢。“在某公司当高级工程师、负责推荐系统”被拆成三条互不相干的事实 |
| Enhanced Notes | 一条一整段话，带着来龙去脉 | 语义完整 | 同一件事在好几段里重复；一个属性变了，要改好几段 |
| JSON Cards | 分类 → 子类 → 键值，比如 `work.position.title` | 可以只改一个字段 | 分类是死的。“周末用 Python 做个人项目”该归时间、技术还是爱好？ |
| Advanced JSON Cards | 每张卡片还带着人物、关系、来历和时间 | 分得清“这是谁的事、为什么记” | 生成和维护都更贵、更慢 |

最后一级解决的正是老周这种情况。原书的例子是“张医生”：他可能是你自己的牙医，也可能是你父亲的心脏科医生。脱离了“这是谁的医生”，这三个字没法用。

装上卡片柜之后，同样两句话记成了这样：

```text
- [人物：老周｜关系：本人] 口味重，菜里多放辣（来历：老周给自己点土豆烧牛腩时说的）
- [人物：老周的父亲｜关系：父亲] 高血压，要少盐，一点辣都不能放（来历：老周替父亲打包清蒸鲈鱼时说的）
```

### 怎么用

别一上来就全用最贵的。原书给的取舍很实在：

- **关键而且少量的**，比如忌口、过敏、家里人的关系，用卡片，保证以后查得准。
- **大量而且琐碎的**，比如每次聊了什么，用便条，省钱。
- 多数真实系统是混着用的，不同种类的信息走不同的路。

## 可执行的记忆：让程序去数

### 为什么会有它

任务 3-4 里，老周办了月卡，当月来满 10 次送甜品。他问：十一月我来了几次？

两个月 23 条来访记录都在上下文舱里，一条不少。主脑读了一遍，答：9 次，还差一次。老周掏出小票：明明是 11 次。

记录没丢，格式也够清楚。问题是这件事**根本不该让模型来数**。便条也好，卡片也好，说到底都是文字。文字擅长回答“他忌口什么”，却把三类事情留给了模型心算：

| 这类事 | 例子 |
| --- | --- |
| 聚合统计 | 这个月来了几次？今年出过几趟国？ |
| 发现冲突 | 他正在吃的药，和他的过敏史有没有撞上？ |
| 守住约束 | 他订了出国的机票，护照在出发前还剩不到六个月 |

### 它是什么

原书把这个思路叫 User as Code：**把用户的状态存成带类型的数据，把规则写成普通的函数。** 于是“表示”和“推理”用的是同一种可以检验的东西。

数出国次数，不再是“读一遍再数”，而是一行确定的计算：

```python
count(
    trip for trip in state.trips
    if trip.is_international and year(trip.departure_date) == 2025
)
# => 2
```

护照快过期了要不要提醒，也不必等用户哪天想起来问：

```python
def check():
    for trip in state.trips:
        if trip.is_international:
            days = date_difference(state.passport.expiry_date, trip.departure_date)
            if days < 180:
                alert("passport expires too soon", trip, days)
```

游戏里的“账本”是这个思路的一个小切片：来访记录存成带日期的数据，`count_visits` 替主脑去数。主脑做的事变成了两件它擅长的：听懂老周在问什么，把结果转述给他。

> 这座工坊不提供执行任意代码的环境，所以账本只开放了“按月数来访次数”这一个确定的操作，而不是让主脑自己写代码去跑。原因见第 01 站“动作”一节：不想让它做的事，最可靠的办法是根本不给它那个工具。

### 怎么用

碰到要“数一数”“比一比”“查一查有没有违反”的需求，先问自己：这是在考模型懂不懂，还是在考它算得准不准？后一种就别让它心算，让程序去算。

## 存什么：三种记忆

前面回答了“放哪里”和“怎么存”，还剩一个问题：**存的到底是什么？** 认知科学把人的长期记忆分成三种，每一种在这座食堂里都找得到：

| 类型 | 是什么 | 人的例子 | 食堂里的例子 |
| --- | --- | --- | --- |
| 情景记忆 | 一件具体发生过的事 | 上周三和同事吃了顿很棒的意大利菜 | 老周 11 月 3 日来过，点了土豆烧牛腩 |
| 语义记忆 | 从许多事里提炼出的稳定知识 | 意大利的首都是罗马 | 老周口味重，爱吃辣 |
| 程序记忆 | 做事的套路 | 骑自行车 | 给老顾客点餐：先看忌口，再按口味，最后问要不要打包 |

至于“这一场对话里正在用的东西”，对应的是工作记忆，也就是上下文舱。

到这里一共出现了三套分类。它们回答的是三个不同的问题，彼此互不相干，可以随意搭配：

| 分类 | 回答的问题 | 有哪些 |
| --- | --- | --- |
| 记忆层次 | 放哪里？ | 轨迹（这一场）、长期记忆（跨场） |
| 存储格式 | 怎么存？ | 便条、段落、分类卡片、带来历的卡片、可执行的数据 |
| 认知类型 | 存什么？ | 情景、语义、程序 |

比如“老周爱吃辣”是一条语义记忆，用便条存在长期记忆里就够了。任务 3-4 的来访记录是情景记忆，存成了可执行的数据。

## 接下来要逼出来的东西

这一站还没完。到现在为止，属于一位顾客的记忆都是整份放回上下文舱的。顾客少的时候没问题，可记忆会越攒越多。下面这些任务正在施工，顺序就是原书的顺序：

| 接下来的麻烦 | 会逼出什么 |
| --- | --- |
| 顾客三千位，每人几十条，全放进上下文舱会怎样 | 检索：只取回相关的那几条 |
| 搜“番茄炒蛋”，菜谱里写的是“西红柿炒蛋” | 向量检索 |
| 搜“第 14 条”，回来的是第 4 条和第 41 条 | 关键词检索，以及把两路结果合起来的办法 |
| 公司重组过，同一个人有新旧两份互相矛盾的记录 | 知识图谱 |

## 带走三句话

1. 模型没有状态。它“记得”你，只因为有人把关于你的那几行字放回了上下文舱。
2. 记忆不是把对话存下来，而是对话结束后再花一次功夫，挑出值得留的。
3. 记住一个人和掌握一门知识是同一件事，差别只在尺度。个案不会自己变成规则，得有人去提炼。

<details>
<summary>2. 任务 3-2 里，如果只有老吴一个人说过那条规矩，夜间整理该不该把它写成规则？</summary>

不该急着写。一个人说的可能是他个人的情况，也可能是他记错了。规则管的是所有人，写错一条，后面每一位顾客都跟着错。稳妥的做法是先留在个人记忆里，等第二个人、第三个人也这么说，再提炼。

</details>

<details>
<summary>3. 为什么不让主脑在对话进行中顺手记，而要等对话结束后专门再呼叫一次？</summary>

可以顺手记，很多系统也这么做。专门再呼叫一次的好处是：它能看到整场对话的全貌，不会把顾客中途改口之前的话记下来；它只有一件事要做，不会因为忙着招呼顾客而漏记。代价是多一次调用的钱和时间。

</details>
