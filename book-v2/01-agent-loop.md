# 第 01 站　缸中之脑长出手

> 这是[π 工坊](https://pi.duanjl.com/)第 01 站的手册。**先去玩，卡住了或者想知道得更深，再回来翻。** 游戏里带下划线的词，点一下会直接跳到这里对应的小节。
>
> 配套任务：[▶ 1-1 第一单](https://pi.duanjl.com/#/play/1-1) · [▶ 1-2 白纸黑字](https://pi.duanjl.com/#/play/1-2)

1981 年，哲学家普特南（Hilary Putnam）讲过一个思想实验：把一颗大脑泡在营养液里，用电线接上一台计算机，喂给它足够逼真的信号。这颗大脑会以为自己正在散步、吃饭、读书，其实哪儿也没去。这就是“缸中之脑”。

大模型的处境和它很像，还更惨一点：**连那台喂信号的计算机都没有。** 它读过互联网上数不清的文字，能写诗，能讲量子力学，可你桌上那份 `orders.json` 里写了什么，它一个字也看不到。

这一站你是空间站的总设计师。站上只有一颗这样的主脑。你要在一次次事故里查明它还缺什么，再亲手给它装上。两个任务走完，你会拼出李博杰《深入理解 AI Agent》第 1 章开篇的那个公式：

> **Agent = LLM + 上下文 + 工具**
>
> 大脑、眼睛、手脚。原书特意提醒：这个加号指的是几个工程组件拼在一起，不是什么数学定义。

## 这一站的因果链

每个零件都是被上一次事故逼出来的。顺序就是你在游戏里遇到它们的顺序。

| 你看到的事故 | 查出来的病根 | 被逼出来的零件 | 对应的概念 | 任务 |
| --- | --- | --- | --- | --- |
| 它在胡说 | 上下文舱里根本没有文件内容 | read 工具 | [工具](#c-tool) | 1-1 |
| 一片寂静 | 结果回舱了，但没人再呼叫主脑 | 循环 | [Agent 循环](#c-loop) | 1-1 |
| 有心无力 | 算对了，却没有能写文件的工具 | write 工具 | [动作](#c-action) | 1-2 |
| 它说完成了 | 站里没有任何东西核对过结果 | 验收信标 | [验收与闭环](#c-verify) | 1-2 |

再往后，原书还有一长串被逼出来的东西：工具执行结果和历史消息丢了会怎样、工作流和自主 Agent 怎么选、护栏怎么分层。这些游戏里暂时还没有关卡，统一放在文末的[往深处走](#c-deeper)。

每一节都按同一个顺序讲：**为什么会有它 → 它是什么 → 怎么用。**

## 任务 1-1　第一单

地面指挥的要求只有一句：小卖部今天已支付的订单，一共收了多少钱。数据在 `orders.json` 里。零件舱里只有两个问号。你什么都没装，按下了发射。

<a id="c-context"></a>

## 上下文舱：主脑此刻知道的全部

### 为什么先讲它

发射后的第一句旁白就是：提问进了上下文舱，舱里早就躺着一块紫色的。后面每一次事故调查，线索都让你回这里找。不先认识这根玻璃舱，后面的事都没法查。

### 它是什么

**上下文（context）是模型这一次被调用时能看到的全部文字。** 游戏里它是那根横放的玻璃舱，里面每一块方块是一条消息，颜色告诉你它是谁放进来的：

| 方块颜色 | 是什么 | 谁放进去的 |
| --- | --- | --- |
| 紫 | 系统提示 + 工具说明书 | 空间站的设计者，也就是你 |
| 橙 | 提问 | 地面 |
| 青 | 主脑自己说过的话 | 主脑 |
| 绿 | 工具返回的结果 | 空间站 |
| 红 | 工具返回的报错 | 空间站 |

点开那块紫色的，你会看到“工具说明书（0 份）”，下面一行小字：一份也没有，主脑不知道世界上有“读文件”这回事。再点开橙色的提问，旁边的注释说得更直白：文件名只是几个字，不是文件的内容。

原书把上下文拆成五个部分，正好对上这几种颜色：

| 原书的说法 | 游戏里 | 什么时候变 |
| --- | --- | --- |
| 系统提示词（system prompt） | 紫色方块的上半 | 每次都一样，合称**静态前缀** |
| 工具定义（tool definitions） | 紫色方块的下半 | 同上 |
| 用户消息 | 橙 | 随着交互越攒越长，合称**轨迹**（trajectory） |
| 模型回复 | 青 | 同上 |
| 工具执行结果 | 绿 / 红 | 同上 |

所以紫色那块总是比你的问题先到。它是这座站的“出厂设置”。

### 怎么用

Agent 表现不对，第一件事是**去看它到底收到了什么**，换模型往后放。原书的说法是：没进观察通道的信息，对模型来说就是不存在。很多看上去像“模型不够聪明”的毛病，查到底是该给的东西没给到。

<a id="c-llm"></a>

## 主脑：只会接话的大模型

### 为什么会有这一节

第 1 次呼叫主脑时，扫描环把整舱内容从头扫到尾喂给它。然后它答得有零有整：

> 已支付订单合计 128.50 元，共 23 笔，客单价约 5.59 元。需要我按品类再拆一下吗？

地面指挥回了一句：账本上一共只有 8 笔订单，你的站报了 23 笔。它在胡说。

### 它是什么

大模型干的事，说到底只有一件：**读完给它的全部文字，接出下一段最像样的文字。** 点一下站中央那颗球（主脑 · LLM），说明里也是这么写的。

问它“一共收了多少钱”，最像样的下一段就是一个金额，于是它给了一个金额。它没有撒谎，撒谎得先知道真相。

战国时的赵括熟读兵书，谈起用兵连他父亲赵奢都驳不倒。真到了长平，据《史记》记载，四十余万降卒被坑杀。读过所有兵书，和看得见眼前的战场，是两回事。

原书在这一章做过一组消融实验（ablation study）：把上下文里的组件一样一样拿掉，看 Agent 会怎样。拿掉工具定义的那一组，结论很扎心：

> 模型**不会沉默**。它照样交出一份格式工整、语气笃定的答案，数字来自它训练时记住的东西。在提示词里写“不得自行估计”，只能降低这种事的概率。
>
> 李博杰《深入理解 AI Agent》第 1 章，大意

你刚才看到的 128.50 元，就是这一幕。原书还补了一句：到底是坦白说“我看不到”，还是编一个，取决于模型本身的幻觉率和诚实程度。

| 没有工具时，模型可能的表现 | 后果 |
| --- | --- |
| 编一个像样的答案 | 最危险，看上去完全正常。游戏里的提线木偶演的就是这一种 |
| 老实说“我看不到文件” | 诚实，但活还是没干成 |

两条路的病根相同：它没有眼睛，也没有手。原书把这总结成一句很适合贴在显示器上的话：**给出了回答，不等于完成了任务。**

### 怎么用

把模型当成一个极其博学、但被关在屋里的顾问。它能想，看不见，动不了。原书把它叫作 Agent 的**决策内核**：理解意图、拆解任务、决定下一步做什么。想让它干活，先想清楚怎么把外面的东西递进屋。

<a id="c-tool"></a>

## 工具：让它开口要东西

### 为什么会有它

事故“它在胡说”的调查题问你：问题出在哪？

| 选项 | 为什么不对 |
| --- | --- |
| 主脑不够聪明，换个更大的模型就好 | 再聪明的模型，也读不到一份没给它的文件 |
| 提问里没说清楚文件在哪 | 提问里写了 orders.json，可对主脑来说那只是几个字 |
| orders.json 损坏了 | 数据舱里的文件好好的，只是从头到尾没人碰过它 |
| **上下文舱里根本没有文件内容** | 正解 |

那就得想办法把文件内容弄进舱里。每次手动粘贴当然也行，可那样的话，要这座空间站何用。

### 它是什么

办法朴素得出奇。原书把工具调用（tool calling，也叫 function calling）拆成四步：

1. **声明工具**：在上下文舱最前面放一份说明书，告诉模型有个叫 `read` 的东西，给它一个路径，它会把文件内容还给你。
2. **模型决定**：模型想读文件时不直接回答，而是输出一段格式固定的请求，意思是“请帮我执行 read，路径是 orders.json”。要不要调、调哪个、传什么参数，都是它定的。
3. **结果追加**：空间站认出这段请求，替它真的去读，再把读到的内容作为新的一块放回上下文舱。
4. **模型继续**：模型看到结果，接着往下干。

模型从头到尾没碰过文件。它像餐厅里的客人：看菜单，点菜，等菜上桌。后厨在哪儿、灶台长什么样，它不知道也不需要知道。

在游戏里点一下 read 舱，能看到模型拿到的说明书原文。这是 Pi 自带的 read 工具，一字未改，内容只有三样：

| 组成 | read 的实际内容 | 作用 |
| --- | --- | --- |
| 名字 | `read` | 点菜时报的菜名 |
| 描述 | 读文件内容，支持文本和图片；文本最多返回 2000 行或 50KB，先到哪个算哪个；大文件用 offset 接着读 | 告诉模型什么时候用、有什么限制 |
| 参数格式 | `path` 必填，`offset`、`limit` 选填 | 告诉模型工单怎么填 |

旁白提醒过一句：这就是主脑对这个工具的全部了解。它看不到实现代码，只能照着说明书猜该怎么用。说明书写得好坏，直接决定它会不会用，这是第 04 站的主题。

> 细心的话你会发现，四步里的第 4 步，游戏把它单独拆成了另一个零件。下一节就是它。

### 怎么用

记住一句话：**工具调用是请求，不是动作。** 模型说“请帮我读”，这句话本身什么也不会改变。这个请求执不执行、怎么执行，由你设计的那部分程序决定。

原书讲“模型即 Agent”时也特意澄清过同一件事：后训练能教会模型的，是**什么时候调、调哪个、传什么**这些决策；工具真正的实现和执行，始终在模型之外。

<a id="c-loop"></a>

## Agent 循环：再来一次

### 为什么会有它

装上 read 再发射。主脑递出一张工单：“我先读一下订单文件。”空间站读了，文件内容变成一块绿色方块落回上下文舱。然后，没有然后了。

地面指挥：我等了半天，你的站一个字都没回。

调查题的提示让你数一数主脑被呼叫了几次。答案是一次。那一次它说的是“请帮我读文件”，说完这次呼叫就结束了。结果回来时，没有人再去叫它。

| 选项 | 为什么不对 |
| --- | --- |
| read 工具坏了，没读到内容 | 上下文舱最后一块就是文件内容，读得很完整 |
| 主脑读完文件后卡死了 | 它只被呼叫过一次，之后根本没机会读 |
| 文件太大，主脑处理不了 | 文件只有几百个字。它没被叫起来处理 |
| **结果回到了上下文舱，但没人再呼叫主脑** | 正解 |

这一幕在服务端是真的：没装循环时，工具照常执行、结果照常回舱，但这一回合结束后，程序直接叫停，不再调用模型。

### 它是什么

**循环（agent loop）就是那个“再来一次”。** 工具结果回舱之后，再呼叫一次主脑，把舱里的一切重新给它看；它如果又要工具，就再执行、再呼叫，直到它不再要为止。

这套“想一步、做一步、看一眼结果”的转法，原书称作 **ReAct**（Reasoning + Acting）循环。用伪代码写出来只有十来行。它不是 Pi 的真实接口，但骨架是一样的：

```js
messages = [系统提示, 用户提问]

while (true) {
  reply = await 调用模型(messages, 工具说明书)  // 每次都把全部 messages 发过去
  messages.push(reply)

  if (reply 里没有工具调用) break              // 模型不再点菜，循环结束

  for (call of reply.工具调用) {
    result = await 执行工具(call)               // 点菜的是模型，做菜的是 Harness
    messages.push(result)
  }
}
```

游戏里那圈环绕空间站的发光轨道，就是这个 `while`。装上它再发射，主脑被呼叫了两次，第二次答出“已支付 5 笔，合计 31.00 元（3100 分）。A003、A007 已退款，A005 还没付，都没算进去。”第一单交付。

原书用一个多币种汇总的例子演示过同样的转法：四个季度的收入分别是美元、欧元、英镑、日元，Agent 转了 3 次迭代、调了 4 次工具，最后算出总收入 $9,602,895.73。转的圈数多了，骨架还是这十来行。

<a id="c-memory"></a>

### 它不记得上一次

装上循环之后，留意第 2 次呼叫的旁白：主脑不记得上一次，所以舱里这几块，要从头到尾再喂一遍。扫描环又从舱头扫到了舱尾。喂给主脑的不是“刚读到的文件内容”，而是**舱里的全部，从第一块开始**。

原书的写法是：**上下文 = 静态前缀 + 轨迹**。每一次调用都把轨迹往后追加一截，再整个发过去，模型每次看到的都是完整轨迹。点开飞行日志里的“第 2 次呼叫主脑”，能看到这一次喂进去的方块清单，从 1 号排起。

电影《记忆碎片》（*Memento*）的主角莱纳德记不住十几分钟前的事。他把线索拍成拍立得、写成纸条，最要紧的直接纹在身上。每次“醒来”都先把这些从头看一遍，才知道自己是谁、正要干什么。

**上下文舱就是模型的纹身和拍立得。** 这件事有两个后果，后面的站点会反复用到：

- **舱里没有的，模型就不知道。** 往舱里放什么、放多少、什么时候清，是第 02 站的主题。一场对话结束、整舱销毁之后又会怎样，第 03 站专门讲。
- **舱里有的，每次都要重读一遍。** 轮数越多，每次要读的越长，越慢、越贵。原书的思考题里提到：累计读取量大致随轮数的平方增长。

<a id="c-loop-stop"></a>

### 循环什么时候停

伪代码里只写了一个出口：模型的输出里没有工具调用。原书列的退出条件有四种：

| 退出条件 | 游戏里有没有 |
| --- | --- |
| 模型不再调用工具 | 有，正常交付都走这条 |
| 模型调用了一个专门表示“我做完了”的最终输出工具 | 没有 |
| 出错 | 有。模型调用失败时，屏幕上会出现“通讯故障” |
| 达到最大轮数 | 有。每场对话最多 12 个回合，整次发射最多 120 秒 |

后两道是 Harness 加在外面的保险。希腊神话里的西西弗斯推石头上山，石头滚下来，再推，永无止境。一个验收永远过不了的 Agent 就是这副样子，而且每推一次都在烧钱。

### 怎么用

看到“Agent”这个词，脑子里就该浮现这个循环。别人说的“Agent 框架”“Agent 平台”，剥到最里面都是它。全书后面讲的上下文工程、记忆、评估、多 Agent，都是在这十来行的某一行上做文章。

<a id="c-harness"></a>

## Harness：你一直在设计的那个东西

### 为什么会有它

回头看第一单：模型只负责“说”。往舱里放说明书的是谁？认出工单、真去读文件的是谁？结果回舱后决定要不要再叫醒主脑的又是谁？点开任何一块带工具调用的青色方块，注释都会告诉你：真正去执行的是空间站。

这些活总得有个名字。

### 它是什么

模型之外、把一切接起来的那部分程序，叫 **Harness**。原书讲了这个词的出处：它原指马具。马具不是为了限制马，而是为了把马的力气引到车上。模型越强、越自主，出错时的影响面越大，Harness 反而越要紧。

原书给的生产形态公式是：

> **Agent = Model + Harness**
>
> Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正

注意它的边界：Harness 在 Agent 之内、模型之外。被它操作的那些东西，比如文件、数据库、网页、用户，属于环境（environment），不算 Harness。放到游戏里：

| 东西 | 归谁 |
| --- | --- |
| 主脑 | 模型 |
| 上下文舱、零件舱、循环、验收信标、12 回合上限 | Harness，你设计的部分 |
| 数据舱里的 orders.json、report.json | 环境 |
| 地面指挥 | 环境（用户） |

本站背后跑的 Harness 是 [Pi](https://github.com/earendil-works/pi)，它把这些职责分在几个包里：

| 包 | 负责什么 |
| --- | --- |
| `pi-ai` | 和各家模型服务说话，把不同厂商的格式统一起来 |
| `pi-agent-core` | 循环本身：维护消息、调度工具 |
| `pi-coding-agent` | 把循环、文件工具、会话和界面装配成一个能用的助手 |

### 怎么用

你在游戏里扮演的就是 Harness 的设计师。往舱里放什么、给模型哪些工具、工具请求来了执不执行、什么时候算做完，这些都归你。模型换得了，这些活换不掉。

<a id="c-action"></a>

## 动作：从看见世界到改变世界

### 为什么会有它

发射。主脑一口气递出两张 read 工单，读了 README.md 和 orders.json，然后说：

> 我算出来了：已支付 5 笔，合计 3100 分。但我没有能写文件的工具，没法生成 report.json。

地面指挥：数是对的，可我要的是 report.json。文件呢？

调查题里有个很像正解的干扰项：“循环提前停了”。其实循环停得没毛病，主脑不再要工具，它就结束了。它不是不想写，是手里没东西可用。

### 它是什么

原书把 Agent 和世界之间的边界叫作**观察空间**（observation space）和**动作空间**（action space）：观察通道决定什么能进上下文，动作接口决定什么能真正被执行。没被动作接口允许的操作，只能停在一句文字建议上，就像刚才那句“没法生成 report.json”。

原书还给工具分了五类，这一站你用到的是前两类：

| 类别 | 干什么 | 例子 |
| --- | --- | --- |
| 感知 | 把外面的信息带进上下文 | `read`、`ls`、搜索 |
| 执行 | 改变外面的世界 | `write`、`edit`、发邮件 |
| 协作 | 和别的 Agent 或人分工 | 把子任务派给另一个 Agent |
| 事件触发 | 外部事件把 Agent 叫起来干活 | 来了一封邮件、到了定时时间 |
| 用户沟通 | 中途找用户确认或追问 | 问一句“要不要转机？” |

> 事件触发这一类有点特别：Agent 并不主动调用它，是外部输入把 Agent 叫起来开始任务。工具的分类和设计，第 04 站细讲。

只有感知工具的 Agent，充其量是个解说员。装上 write，下一次它就能把结果落到纸上。

### 怎么用

原书有个判断值得记住：**模型固定时，提升 Agent 表现最主要的工程手段，就是扩展观察空间和动作空间。** 它举的例子是 Manus 把三类产品的能力合在一起：用虚拟浏览器扩观察，用文件系统、代码和命令行扩动作。

这句话反过来读同样要紧：**你不想让它做的事，最可靠的办法是根本不给它那个工具。** 这座工坊没给主脑任何能执行命令的工具，原因就在这里。

<a id="c-verify"></a>

## 验收与闭环：别听它怎么说

### 为什么会有它

装上 write 再发射。主脑写了一份报告，然后说：

> 日结完成 ✅ report.json 已生成：8 笔，合计 44.50 元。

地面指挥拿账本一核对：报告是错的。它把退款和未付款的订单也算了进去，8 笔订单全加上，正好 4450 分。

它没有撒谎。它确实写了报告，也确实不知道报告是错的。调查题的提示一针见血：地面拿账本核对过了，在你的空间站里，有谁核对过吗？

| 选项 | 为什么不对 |
| --- | --- |
| 缺一个更诚实的模型 | 它没撒谎，只是不知道报告对不对 |
| 缺第二个模型来复查一遍 | 另一个模型同样可能被一份像样的报告说服，先用最笨最硬的办法 |
| 缺一段更长的提示词 | 叮嘱它“要仔细”，错的不会变成对的 |
| **缺一个不听它怎么说、只核对结果的环节** | 正解 |

### 它是什么

1987 年签《中导条约》时，里根在白宫引了一句他很爱说的俄国谚语：

> Доверяй, но проверяй。信任，但要核实。

验收信标就是那个“核实”，对应原书 Harness 五要素里的**验证**（verification）：自动判断做得对不对。它是一段普通的程序，打开 report.json，拿里面的数字和账本逐项比。它不懂语言，不会被说服，也不看模型的语气。

原书对验证有一条硬要求：**安全检查只看结构化数据，不看模型自由发挥的文字**，因为后者可能已经被人动过手脚（第 02 站会讲到的提示注入）。验收信标正是这么做的：它读的是 JSON 里的 `paidCount` 和 `paidTotalCents`，主脑说了什么“日结完成 ✅”，它一个字都不看。

更要紧的是，它被做成了一个**工具**，装进了循环里。再发射一次，看这六步：

1. 读 `README.md` 和 `orders.json`。两张工单一起递出，因为这两件事互不相干。
2. 写 `report.json`：8 笔，4450 分。
3. 调用验收。**信标红了**：paidCount 与账本不符，提示只有 status 为 paid 的订单才算收入。
4. 主脑读到原因，重写：5 笔，3100 分。
5. 再次验收。**信标绿了。**
6. 不再要工具，交付。

红灯的原因没有弹窗，也没有让程序崩溃。它只是作为一块普通的工具结果**落回了上下文舱**，下一次呼叫时主脑读到它，于是知道错在哪儿。这就是闭环（closed loop）：**动作的结果，回到做决定的地方。**

| | 没有验收的循环 | 有验收的循环 |
| --- | --- | --- |
| 谁说“做完了” | 模型自己 | 一段不会被说服的程序 |
| 做错了会怎样 | 你事后才发现 | 原因回舱，模型当场重做 |
| 你需要信任什么 | 模型的每一句话 | 验收程序写得对 |

右边这一列也不是万无一失。验收程序本身可能写错，也可能只查了一部分。怎样的验收才算数，是第 07 站的主题。

### 怎么用

**别问模型“做完了吗”，给它一个能自己去按的验收按钮。** 写代码的 Agent 让它能跑测试，做报表的 Agent 让它能对账。验收报出的原因越具体，循环转的圈数越少。

还有一个更硬的版本，游戏里暂时没做：这一站的信标是个工具，按不按由模型决定，真模型偶尔会忘了按（这时地面照样不收）。生产系统里常见的做法，是由 Harness 在模型宣布完成之后自动跑一遍验收，不给它忘的机会。

## 回头看：你拼出了什么

两个任务走完，零件舱里是这四样：

| 零件 | 公式里的位置 | Harness 五要素里的位置 |
| --- | --- | --- |
| read | 工具（眼睛的延伸） | 工具接口、上下文管理 |
| 循环 | 把 LLM、上下文、工具串起来的机制 | 上下文管理 |
| write | 工具（手脚） | 工具接口 |
| 验收信标 | 工具 | **验证** |

五要素里还空着两格：**约束**和**纠正**。原书说，它们加上验证，才是生产级 Harness 的重心；前两样让 Agent 能做事，后三样让它不做错事。下面一节从这里接着讲。

<a id="c-deeper"></a>

## 往深处走

> 这一节的内容，**游戏里还没有关卡**。它们都在原书第 1 章里，按原书的顺序简单讲一遍，等关卡造好了再细讲。

<a id="c-ablation"></a>

### 拿掉一块会怎样：上下文的消融实验

前面提到的消融实验一共四组，游戏里的“它在胡说”只演了第一组：

| 拿掉什么 | 原书观察到的结果 |
| --- | --- |
| 工具定义 | 无法行动，但不沉默，交出一份编造的答案 |
| 工具执行结果 | 闭环断了，Agent 盲目地反复重试，直到耗尽轮数预算 |
| 思考过程 | 几乎没有代价，因为思路可以从工具结果重新推出来 |
| 历史消息 | 做重复的操作，犯同样的错 |

原书的结论是：**各个组件并不等价**，衡量标准是这份信息能不能从别处重建。它也提醒，换一个模型，同样的实验结论可能就变了，所以要重测。

> 注意第二组和游戏里的“一片寂静”不是一回事。“一片寂静”是结果回舱了，但没人再叫主脑；消融实验第二组是主脑一直被叫，却永远看不到结果。前者沉默，后者瞎忙。

### 通用工具还是专用工具

工具设计不好会出事：接口含糊模型就乱用，错误处理不到位会卡死，权限给太宽出了错难挽回。原书给的原则是：**通用的基础能力用来组合和探索，专用工具用来约束高风险、强业务规则的操作。**

| 场景 | 原书的建议 |
| --- | --- |
| 算术 | 计算器一个个加不完，可以换成受限的 Python 解释器：放进沙盒，默认不联网，限定目录，限时间、CPU、内存和输出 |
| 翻日志 | 给一个受控的虚拟工作目录，让它自己翻 |
| 支付、删除、发邮件、生产部署 | 仍然封装成专用工具，加预览和人工确认 |

这座工坊用的其实就是第二行的思路：主脑的文件工具都只能碰一个只存在于内存里的虚拟目录。

### 模型越来越强，Harness 会消失吗

后训练（RL）已经把“何时调工具、调哪个、要不要继续”这些决策教进了模型，这叫**模型即 Agent**（Model as Agent）。很多人由此推出框架不重要了。原书的论证方向正好相反：模型越强，Harness 越关键，因为自主空间越大，出错的影响面越大。

对 Rich Sutton 那篇著名的《苦涩的教训》（*The Bitter Lesson*），原书的立场可以概括成八个字：**方向认同，节奏务实。** Harness 里给模型打补丁的部分，迟早会被模型一层层吃掉；可模型训练以月计，也不可能一次学会真实业务的全部约束，眼下做不稳的，就由 Harness 先补上。

### 约束与纠正

五要素里游戏还没做的两格：

| 要素 | 原书的定义 | 例子 |
| --- | --- | --- |
| 约束 | 故障安全的默认值：能力默认关闭，显式开放 | 退款 Agent 的权限和金额规则 |
| 纠正 | 发现问题自动修正或回退；确认无法恢复之前，不把中间状态暴露给用户，先静默重试 | 超时重试、回退 |

纠正里有个常见零件叫**熔断器**（circuit breaker）：像保险丝，错误连续发生时自动“断电”，停止重试，转交人工。原书提到，Claude Code 的 Harness 里大部分代码干的都是这三件事：流程状态、多层上下文压缩、权限分类、熔断器、错误恢复。

### 竞争力搬到了模型之外

各家模型越来越接近，光比模型分不出胜负。原书举的证据是：LangChain 在 Terminal Bench 2.0 上**一行模型都没换**，只改 Harness（让 Agent 自查执行结果、检测重复循环、调整思考策略），得分从 52.8% 涨到 66.5%，排名从 30 开外进了前 5。

原书把工程范式的演进排成五层，后一层包含前一层：

> 提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程

并引用了 Anthropic 的三条原则：**保持简单、保持透明、设计好工具接口**。最后一条有个专门的名字叫 ACI（Agent-Computer Interface），要站在 Agent 的角度设计接口，能让错误在设计上就不可能发生最好。这叫防呆（Poka-yoke），丰田生产体系里的说法：SIM 卡缺一个角，插反了根本塞不进去；微波炉门不关，就不加热。

<a id="c-workflow"></a>

### 工作流还是自主 Agent

原书在这里换了一个并列的话题：编排。常见的反面做法是一上来就搭复杂流水线，每个节点单看都有道理，合起来又慢又脆，遇到新例外只会再加节点。原书推荐的顺序是**从简单到复杂**：

| 先试 | 适用 | 代价 |
| --- | --- | --- |
| 单次 LLM 调用 | 改提示词、加示例就能解决的 | 最便宜 |
| 工作流（workflow）：代码写死路径，LLM 只在节点里理解和生成 | 能清楚拆成固定步骤，需要严格流程控制 | 缺乏变通 |
| 自主 Agent：路径由环境反馈实时决定，也就是循环里用工具的 LLM | 开放式问题 | 更贵，错误会层层叠加 |

原书的订机票例子很直观。工作流是四个节点：核实身份、搜航班、付款、确认预订，“付款前不能预订”由代码保证，被注入或模型犯错，最多祸害一个节点；可用户付款时想改签，它只能走预设的异常分支，或者交还给人。自主 Agent 则会自己发现要先登录、最便宜的航班要转机就去问用户、用户不同意就换条件。两者也可以混用：合规严格的环节走工作流，灵活的部分交给 Agent。

你在这一站搭的，正是最简单的自主 Agent。

<a id="c-guardrails"></a>

### 护栏三层与人工干预

能做事还不够，还得保证做得安全。原书的观点是一道防线不够，护栏（guardrails）要分层，按被绕过的难度排：

| 层 | 管什么 | 例子 | 局限 |
| --- | --- | --- | --- |
| 上下文层 | 模型看到什么 | 相关性分类器、安全分类器、内容审核、来源标注 | 同一个上下文里的 Agent，很难判断自己是不是已经被注入了，只能降低攻击成功率 |
| 执行层 | 模型能做什么 | 工具按可逆性、权限、财务影响评风险等级；高风险的要额外审查或人工确认 | 复核必须在上下文之外完成，否则会和被注入的 Agent 一起沦陷 |
| 数据层 | 世界最终能被改成什么样 | 数据库行级权限、约束和校验器 | 不依赖上面两层对不对，越权操作在这一层照样被拒 |

越往下越不依赖模型自己的判断。护栏也会出错：为了拦住危险请求，可能连合法但看着敏感的任务也一起拒了，所以评估要两头测。

最后一道是**人工干预**（human in the loop）：失败次数超过阈值，或者碰到大额退款这类高风险、不可逆的操作，就把控制权交还给人。

### 五个贯穿全书的设计模式

原书在第 1 章末尾一次性点了五个名字，后面各章会反复用到：

| 模式 | 一句话 |
| --- | --- |
| 提议者—审核者 | 产出和评判交给不共享上下文的两个角色，评判方看产物，不看推理过程 |
| 渐进式披露 | 先给目录，按需再加载细节 |
| 只增不改（append-only） | 状态只往后追加，换来可缓存、可重放、可审计 |
| 边界集 + 保留集 | 每次修改，既要在“该变的”样本上验证，也要在“不该受影响的”样本上验证 |
| 最小 diff + 可回滚 | 每次改一点，带来源，能单独撤回 |

上下文舱只往后追加方块，从不改前面的，就是第三个模式最朴素的样子。

## 这座工坊哪里是真的，哪里是假的

演示系统最怕不说清楚自己演了什么。这里列个明白账。

| 东西 | 真假 | 说明 |
| --- | --- | --- |
| Agent 循环 | **真** | 服务器上跑的是 Pi 1.5.2 的运行时，事件是它发出来的 |
| `read` / `write` | **真** | Pi 自带的工具，说明书一字未改；只是读写的目标换成了虚拟文件 |
| 验收信标 | 自制 | 为这一站写的验收工具，源码公开 |
| “没装循环” | **真** | 工具照常执行、结果照常回舱，之后服务端确实不再调用模型 |
| 回合与时间上限 | **真** | 每场对话 12 个回合，每次发射 120 秒 |
| 上下文压缩、自动重试、思考 | 关闭 | Pi 本身支持，这里特意关掉，让你看到最原始的循环 |
| 文件系统 | **假** | 工具读写的是一份只存在于内存里的虚拟文件，每次发射各用各的 |
| 提线木偶 | **假** | 没有 key 时使用的、照着剧本输出的模型 |
| token 数 | 估算 | 按字符粗算，只用来决定方块的大小 |

把模型换成木偶，循环照转不误，这件事本身就值得琢磨：**循环并不关心主脑里装的是什么。** 它只认一种约定：输出里有没有工具调用。

换成真模型时，同一个任务每次的走法可能不一样。它有时会碰巧躲过某个坑，比如第一次写报告就写对了。这时零件和概念照样发给你，因为坑是真的：换一批数据、换一个模型，它未必躲得过。

## 带走三句话

1. 模型只知道训练时读过的，和此刻上下文舱里装着的。给出了回答，不等于完成了任务。
2. 工具调用是请求，不是动作。执行的是 Harness，记住这件事的是上下文舱。
3. 想让 Agent 靠谱，就把验收装进循环，让结果回到做决定的地方。

## 想一想

<details>
<summary>1. 任务 1-1 里，如果空间站执行完 read 却忘了把结果放回上下文舱，下一次呼叫时主脑会怎样？</summary>

它会看到自己发出过一个 `read` 请求，却看不到结果，对它来说这次读取等于没发生。它可能再请求一次，再一次，直到撞上 12 回合的上限，这正是原书消融实验里“拿掉工具执行结果”那一组的样子；它也可能干脆开始猜。舱里没有的，模型就不知道。

</details>

<details>
<summary>2. 任务 1-2 里，主脑一口气递出了两张 read 工单。这样做有什么前提？</summary>

两件事互不依赖：读 `README.md` 不需要先知道 `orders.json` 的内容。如果第二步要用第一步的结果，就只能分两个回合。

</details>

<details>
<summary>3. 把验收的不通过原因从“paidCount 与账本不符”改成只说“不通过”，会发生什么？</summary>

模型知道错了，但不知道错在哪儿，只能瞎改再试，回合数会变多，也可能撞上 12 回合的上限。报错写得好不好，直接决定循环转几圈。

</details>

<details>
<summary>4. 调查题里“缺第二个模型来复查一遍”算错。可原书的设计模式里明明有“提议者—审核者”，这矛盾吗？</summary>

不矛盾，先后有别。能用程序判对错的事，先用程序，因为它不会被说服。原书说的审核者有两个前提：它和提议者不共享上下文，而且看的是产物，不是推理过程。拿一个读着同一份上下文、听着同一套说辞的模型来复查，很可能一起被带偏。

</details>
