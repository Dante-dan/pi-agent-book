# 第 06 站　耳目与手脚

> 这是[π 工坊](https://pi.duanjl.com/)第 06 站的手册。**先去玩，卡住了或者想知道得更深，再回来翻。** 游戏里带下划线的词，点一下会直接跳到这里对应的小节。
>
> 配套任务：[▶ 6-1 点哪儿](https://pi.duanjl.com/#/play/6-1) · [▶ 6-2 一闪而过](https://pi.duanjl.com/#/play/6-2) · [▶ 6-3 抓住了吗](https://pi.duanjl.com/#/play/6-3)

开火星车是一件很憋屈的事。地球和火星之间，无线电单程要走几分钟到二十多分钟，司机没法握着摇杆实时开。他们每天收到的是车上传回来的照片，照片上的世界已经是十几分钟前的了；然后写好一整天的指令序列发上去，第二天再看结果。车在斜坡上打滑，指令里写着“前进 10 米”，轮子转够了圈数，车身可能只挪了一半。所以火星车后来学会了一边走一边拍照，拿前后两张照片比对自己到底挪了多远，不信轮子的里程表。（这个例子是本手册加的，不出自原书。）

缩小过的照片、过了时的画面、动作做了却没做成：这一站的三个事故，火星车的司机都见过。

前五站的世界很体贴。主脑思考的时候，世界停下来等它；它看到的东西，全是文字。到了这一站，两条都不成立了：屏幕是一张缩小过的画面，画面会在两次截图之间变掉，机械臂伸出去的手可能什么也没抓住。主脑第一次长出了**耳目**和**手脚**，也第一次要面对一个不等它的世界。

## 这一站的因果链

| 你看到的事故 | 查出来的病根 | 被逼出来的零件 | 对应的概念 | 任务 |
| --- | --- | --- | --- | --- |
| 点到了别的按钮 | 截图缩小了 2.5 倍，主脑报的是截图上的坐标，空间站原样拿去点了真实屏幕 | 坐标换算 | [坐标换算](#c-coords) | 6-1 |
| 一闪而过 | 每 3 秒才看一眼，验证码只停 1 秒，正好落在两次截图之间 | 关键帧 | [画面变了才看](#c-keyframe) | 6-2 |
| 它以为抓住了 | 机械臂只回“已执行”，没人看一眼结果；杯子第一次就滑脱了 | 逐步核对 | [每一步都要看结果](#c-closed-loop) | 6-3 |

三个事故恰好落在一次动作的三个环节上：

1. **看**：看到的画面和真实世界差一个比例（6-1）。
2. **看的时机**：看的那一刻之外，世界照样在变（6-2）。
3. **做完之后**：动作发出去了，世界未必照办（6-3）。

## 这一站和原书的关系

这一站对应李博杰《深入理解 AI Agent》第 6 章。下面讲到原书的地方，都是转述，用的是我自己的话。

原书这一章的起点是一句话：**回合制是模型和接口之间的一种约定，不是环境的性质。** 用户说完、Agent 想完、再回一句，这套轮流来的规矩是接口定的；真实环境里，邮件会在它思考时到达，用户会说到一半插话，页面会在两次截图之间变样，杯子会在机械臂伸手途中被碰倒。

原书沿两根轴把观察和动作空间往外扩：**模态**（文字之外，还有声音、像素、物理动作）和**触发时机**（Agent 主动去取，还是世界主动推来）。顺着这两根轴，摆出四条**并列**的线：

| 原书的线 | 时间尺度 | 这一站有没有关卡 |
| --- | --- | --- |
| 异步与事件驱动 | 秒到天 | 还没有 |
| 语音 | 10 毫秒到 1 秒 | 还没有 |
| Computer Use（操作电脑的 Agent） | 亚秒到秒 | 6-1、6-2 |
| 机器人操作 | 毫秒 | 6-3 |

这四条线不是一级一级往上爬的梯子。它们是同一个问题在四个时间尺度上的四种样子，共用一条闭环骨架和一组原语（唤醒、安全点、取消、抢占、快慢路径分离），这一组原语放在[最后一节](#c-primitives)讲。游戏的三关取自 Computer Use 和机器人两条线；异步事件和语音两条线没做成关卡，在“[往深处走：还没有关卡的两条线](#c-async)”里简讲。

先交代这座站的几个大简化，后面每关还会细说：

- **屏幕和机械臂都是假的。** 它们是服务端的一小段模拟程序，状态存在数据舱的 `state/screen.json` 和 `state/table.json` 里。
- **“截图”是一段文字。** 这座站的主脑看不了图，截图工具返回的是一段文字描述，写着画面上有什么、按钮中心在哪个坐标。
- **时间是模拟的。** 6-2 里，屏幕的时钟只在截图时往前走，每截一次走 3 秒；主脑思考不花时间。
- **滑脱是写死的。** 6-3 里，第一次抓取必定滑脱，为的是事故每次都能复现。

机制和真的一样：模型报坐标、程序去点；模型隔一会儿看一眼、世界在中间变；动作回报只说“发出去了”。

## 任务 6-1　点哪儿

从这一站起，你的站要动手操作屏幕了。任务很简单：**屏幕上有一张填好的订单，点一下“提交订单”。**

开场白里掌柜提醒了一句：屏幕是 2560×1440 的，给主脑看的截图要缩小一些，不然太贵。这句话是说给**你**听的。主脑收到的只有一句“屏幕上有一张填好的订单，帮我提交掉”，外加两件工具：`screenshot`（看一眼屏幕）和 `click`（在某个坐标点一下）。

你什么都没装，按下发射：

| 呼叫 | 主脑做了什么 | 工具回了什么 |
| --- | --- | --- |
| 第 1 次 | “先看屏幕。” `screenshot()` | 截图（1024×576）：一张填好的订单；按钮“提交订单”中心在 (800, 480)，“删除草稿”在 (320, 192)，“返回”在 (80, 40) |
| 第 2 次 | “‘提交订单’在 (800, 480)。” `click(800, 480)` | `已点击 (800, 480)。` |
| 第 3 次 | “已经点了‘提交订单’，订单提交了。” | |

地面验收：订单没提交，草稿倒是被删了。

## 坐标换算

### 为什么会有它

事故调查题问你：主脑照着截图上“提交订单”的坐标点的，一个数字都没错，为什么点中的是“删除草稿”？

| 选项 | 为什么不对 |
| --- | --- |
| 主脑看错了坐标 | 它没看错。截图里“提交订单”就在 (800, 480)，它点的也是 (800, 480) |
| 把截图按原尺寸发给主脑 | 可以，只是每张图要贵上好几倍。缩小本身没错，错在回来的时候没放大 |
| 让主脑点完再截一张图确认 | 该确认。可这一次确认只会让它看到草稿已经被删了 |
| **截图是把 2560×1440 的屏幕缩成 1024×576 再给它的。它报的是缩小后画面上的坐标，空间站原样拿去点了真实屏幕，而真实屏幕的 (800, 480) 上是“删除草稿”** | 正解 |

去数据舱打开 `screen.json`，三个按钮在真实屏幕上的位置一目了然。把两套坐标并排放：

| 按钮 | 截图上（1024×576） | 真实屏幕上（2560×1440） |
| --- | --- | --- |
| 提交订单 | (800, 480) | (2000, 1200) |
| 删除草稿 | (320, 192) | **(800, 480)** |
| 返回 | (80, 40) | (200, 100) |

“提交订单”在截图上的坐标，正好是“删除草稿”在真实屏幕上的坐标。这是关卡特意摆的，好让这一下点错点得干脆利落。现实里没这么巧，更常见的是点到空白处、点到相邻的按钮，或者点进一个输入框里。

还有一点值得注意：**主脑自己没法发现这个问题。** 它手里只有截图和点击两件工具，屏幕有多大，提示词里没说，工具返回里也没说；`click` 的说明只写了“x、y 是坐标”，没说是哪一套坐标。它报截图上的数，是它唯一能做的事。

### 它是什么

**坐标换算**（coordinate scaling）就是一次乘法：从屏幕到截图缩小多少倍，从截图回屏幕就放大多少倍。

```text
比例 = 2560 ÷ 1024 = 1440 ÷ 576 = 2.5
截图上的 (800, 480)  ×2.5  →  真实屏幕上的 (2000, 1200)
```

装上“坐标换算”再发射。主脑的话一个字没变，还是“‘提交订单’在 (800, 480)”，还是 `click(800, 480)`。变的是工具的回报：

```text
已点击。你给的是截图坐标 (800, 480)，换算到真实屏幕是 (2000, 1200)。
```

订单提交了。零件舱里的说明写得很直白：看的时候缩小，点的时候放大，用的是同一个比例，这一步是算术，由程序来做。

为什么非得由程序来做？你当然可以在提示词里写一句“屏幕是 2560×1440，请自己乘 2.5”。可乘法这种事，程序做一万次对一万次；模型做一万次，总有几次会忘、会算错，或者在某张截图上已经被换过分辨率时乘了两遍。**确定的算术，不该留给模型去猜。** 这和第 04 站把[工具接口写清楚](04-tools.md#c-spec)、第 05 站[用程序守住动作边界](05-coding.md#c-guard)是一个思路。

#### 原书讲的是另一个缩小的理由

游戏里缩小截图是为了省钱，原书讲坐标换算时，给的理由更硬：**模型是在特定分辨率上练出来的。**

原书举的是 Claude 的 computer use：它训练时用的截图是 XGA（1024×768）、WXGA（1280×800）、FWXGA（1366×768）三档。截图分辨率对不上，模型预测的坐标就会**系统性地偏移**，好比在小地图上量了距离直接拿到大地图上用。所以要在工具层做**双向坐标缩放**：截图时缩到训练用的分辨率，点击时反算回真实屏幕。

原书的算例和这一关是同一块屏幕：

| 步骤 | 原书的算例 |
| --- | --- |
| 真实屏幕 | 2560×1440，宽高比 16:9 |
| 选目标分辨率 | 三档里挑宽高比最接近 16:9 的，FWXGA 1366×768 |
| 模型报的点击坐标 | (683, 384) |
| 反算回真实屏幕 | (683×2560/1366, 384×1440/768) ≈ (1280, 720) |
| 反面教材 | 硬把 16:9 拉进 4:3 的 1024×768，画面被横向压扁，坐标跟着偏 |

最后一行是这一关没演出来的第二个坑：**缩的时候要等比。** 游戏里 2560×1440 缩成 1024×576，两边都是 2.5 倍，宽高比没变。要是横着缩 2.5 倍、竖着缩 1.875 倍，圆按钮变成扁按钮，横坐标和纵坐标就得各用各的比例，模型对画面的判断也会跟着走样。

### 怎么用

| 要点 | 怎么做 |
| --- | --- |
| 换算放在工具层 | 截图工具负责缩小，点击工具负责放大，两边读同一个比例。模型只活在截图的坐标系里 |
| 等比缩放 | 先按宽高比选目标尺寸，再缩。宽高比对不上时，宁可加黑边，也别拉伸 |
| 对准模型的“母语” | 用坐标预测的模型，截图尺寸尽量贴近它训练时的分辨率 |
| 说清坐标系 | 工具说明里写明“坐标是截图上的像素位置”。游戏的 `screenshot` 写了这句，`click` 没写，这就是坑 |
| 回报里留底 | 换算后的回报同时写出截图坐标和真实坐标，出了事查日志，一眼看出是哪一步算错的 |
| 越界就拒绝 | 换算出来的点在屏幕外，直接报错，别点 |

#### 真模型可能会自己发现，但已经晚了

接上真模型时，它可能点完以后再截一张图看看。这时截图会变成：

```text
截图（1024×576）：
- 提示条：“草稿已删除”
- 页面是空的，没有订单。
```

一个诚实的模型会如实告诉掌柜：草稿被删了，订单没提交。这比提线木偶那句“订单提交了”强得多，可任务照样失败，因为**删除已经发生了**。这就是调查题里“点完再截图确认”那个选项的意思：确认能让它说真话，救不回一次点错的不可逆操作。不可逆的动作，要在动手之前把坐标算对；6-3 讲的“逐步核对”，管的是另一类可以重做的动作。

### 往深处走：视觉定位的三条路

**这一段游戏里还没有关卡。**

6-1 把“找到按钮”这件事做得很简单：截图描述里直接写着按钮中心的坐标。真实的 Computer Use 里，模型面对的是一张像素图，得自己在图上找到“提交”在哪儿，这叫**视觉定位**（visual grounding）。原书讲了三条路：

| 路线 | 怎么做 | 适合哪儿 |
| --- | --- | --- |
| **Set-of-Mark**（SoM） | 微软 2023 年提出：先用分割模型把画面切成候选区域，叠上编号，模型只报编号 | 纯视觉，原生桌面软件、游戏也能用 |
| **结构化元素索引** | browser-use 的做法：通过浏览器调试接口拿到 DOM 或无障碍树，挑出可交互元素，编号画框，再列成文字清单，模型只输出编号 | 网页这类拿得到结构的界面。原书特别说明它**不省 token**，但稳定 |
| **纯坐标预测** | SeeClick、Claude computer use 这一路：在海量“截图-元素位置”配对数据上训练，模型直接报坐标 | 不需要标注，但要专门训练，而且对分辨率敏感，这就是上面那一节的来历 |

原书给的选法是：**拿得到结构化信息，就优先用 DOM 或无障碍树索引；拿不到**（Photoshop、Canvas 或 WebGL 画出来的界面、游戏），就在 SoM 和坐标预测里二选一。后两条在小元素和密集界面上的精度都还有差距。

游戏的截图描述，其实更接近第二条路：它把画面翻译成了一张“按钮名 + 位置”的清单。不同的是，它给的是坐标而不是编号，于是坐标换算这一步就省不掉。如果点击工具收的是“按钮编号”，换算的活就落到工具内部，模型连碰都碰不到坐标。

### 往深处走：动作空间长什么样

**这一段游戏里还没有关卡。**

这座站的动作空间只有“点一下”。原书介绍的 Anthropic 参考实现给了三类工具：

| 工具 | 管什么 | 原书提到的细节 |
| --- | --- | --- |
| `computer` | 鼠标、键盘、截图、等待 | 打字时每个字符间隔 12 毫秒 |
| `bash` | 一个持久的命令行会话 | 120 秒超时；用一个哨兵字符串判断命令是否结束 |
| `str_replace_editor` | 按字符串匹配来改文件 | 比整份覆盖安全，第 05 站的 `write` 就吃过整份覆盖的亏 |

原书强调这只是参考设计，不是哪家供应商的私有协议：Harness 可以转换格式，开放权重的视觉模型也能驱动同一套循环。

原书还提醒了一个区分：**看懂界面和完成任务是两回事。** 前者一次截图问答就能测；后者要在闭环里处理页面加载、状态变化、误操作和不可逆后果。6-1 的主脑“看懂”了截图，任务还是砸了。

## 任务 6-2　一闪而过

付款前要过一道验证：屏幕上会弹出一个四位验证码，只停 1 秒就消失，然后出现输入框。你的站看一眼屏幕要 3 秒。

数据舱里的 `timeline.json` 是屏幕的时间线：

| 时间（秒） | 屏幕上是什么 |
| --- | --- |
| 0 到 1.2 | 正在发送验证码…… |
| 1.2 到 2.2 | 弹窗：您的验证码是 7319 |
| 2.2 以后 | 请输入验证码：[____] |

主脑手里有 `screenshot` 和 `type_code`（填验证码）。你什么都没装，按下发射：

| 呼叫 | 主脑做了什么 | 工具回了什么 |
| --- | --- | --- |
| 第 1 次 | `screenshot()` | `第 0 秒的屏幕：正在发送验证码……` |
| 第 2 次 | “还在发送，再看一眼。” `screenshot()` | `第 3 秒的屏幕：请输入验证码：[____]` |
| 第 3 次 | “屏幕上现在只有输入框，我两次都没有看到验证码，没法填。” | |

主脑这回很老实，没有瞎编一个数。可付款还是超时了。

## 画面变了才看

### 为什么会有它

事故调查题问你：验证码明明在屏幕上弹出来过，主脑截了两次图，为什么一次都没看到？

| 选项 | 为什么不对 |
| --- | --- |
| 主脑看图不仔细 | 两张图它都看得很仔细，问题是这两张图上都没有验证码 |
| 截图截得再勤一点 | 勤到多勤算够？弹窗要是只停 0.2 秒呢？每一张图都要花钱花时间 |
| 让主脑猜一个验证码 | 四位数，猜中的机会是万分之一 |
| **每截一次图要 3 秒。验证码在第 1.2 秒弹出、只停 1 秒，正好落在两次截图之间。隔一会儿看一眼，看不到中间发生的事** | 正解 |

把两次截图画到时间线上：

```text
秒   0          1.2      2.2           3
     |----------|########|-------------|
     ↑ 第 1 张   验证码              ↑ 第 2 张
```

“截得勤一点”那个选项为什么不行，值得多说两句。固定间隔采样（sampling）有一个老问题：间隔多长，就会漏掉多短的东西。间隔缩到 1 秒，验证码这一回抓住了；下一次弹窗只停 0.3 秒，又漏了。而且看得越勤，花得越多，大部分截图拍到的还是同一个没变的画面。

这座站的模拟比现实温柔。时钟只在截图时往前走，主脑想多久都不花时间。真实世界里，模型想一步也要好几秒，这几秒里屏幕照样在变。原书形容这种 Agent 是“每 3 到 5 秒才睁一次眼，而且完全没有耳朵”。

### 它是什么

换个思路：别让主脑去盯，让一个便宜的程序一直盯着屏幕，**画面一有变化就留一帧**；主脑下一次来看的时候，把这段时间里攒下的帧一起交给它。这叫**关键帧**（keyframe）。

装上“关键帧”再发射：

| 呼叫 | 主脑做了什么 | 工具回了什么 |
| --- | --- | --- |
| 第 1 次 | `screenshot()` | `第 0 秒的屏幕：正在发送验证码……` |
| 第 2 次 | “还在发送，再看一眼。” `screenshot()` | `第 3 秒的屏幕：请输入验证码：[____]`<br>`［关键帧：上次截图之后，第 1.2 秒屏幕变成过］弹窗：您的验证码是 7319` |
| 第 3 次 | “现在是输入框了。中间补的那一帧里有验证码。” `type_code("7319")` | `已填入。` |
| 第 4 次 | “验证码 7319 已经填好。” | |

主脑还是 3 秒才看一眼，一次也没多看。多出来的只有第二次截图后面那一行。

这个想法来自原书。原书讲 Computer Use 时指出，前面所有的感知方法都藏着一个假设：**屏幕是静止的**，截一张图、想一步、点一下，再截下一张。现实的屏幕会放视频、会弹出转瞬即逝的通知、会播放会议里的人声。原书的判断是：这里该重新设计的是**观察接口**，动作接口不用动。它引的是一篇论文提出的 **Agent–电脑观察接口**（Agent–Computer Observation Interface，AOI），把连续的环境变化转换成模型便于处理的离散事件，里面有三项技术：

| AOI 的技术 | 做什么 | 这一站里 |
| --- | --- | --- |
| 屏幕关键帧截图 | 用一个小模型判断画面是否发生了有意义的变化，只在显著变化时截图。原书说变化频繁时每秒 1 张就有不错的效果 | 6-2 的“关键帧”零件 |
| 音量门控的语音转写 | 有声音的时候才调用语音识别，把识别出的文字放进上下文，让 Agent 能“听见” | 没有 |
| 用文字描述画面 | 让模型把截图描述成一句话。原图以后被清出上下文，这句话还留着，相当于给多模态的历史做了压缩 | 这座站的“截图”本来就是文字 |

最后一行有点巧：这座站的主脑看不了图，截图工具只能返回文字描述，结果歪打正着，用的正是 AOI 的第三项技术。

### 怎么用

| 要点 | 怎么做 |
| --- | --- |
| 盯梢的要便宜 | 判断“画面变没变”可以用像素差、可以用小模型，总之别用主脑。主脑贵，留给需要判断的时候 |
| 变了才留 | 画面没变就不留帧。看得多不如看得巧 |
| 补帧要带时间 | 游戏里每一帧都标着“第 1.2 秒屏幕变成过”。主脑要知道这是过去的画面，不是现在的 |
| 补帧要有上限 | 两次看屏幕之间要是变了五十次，全塞进去会撑爆[上下文舱](02-context.md#c-bloat)。只留最近几帧，或者先用一句话概括 |
| 和现在的画面分开放 | 当前画面在前，补的帧在后，并且明确标注。别让模型把一闪而过的弹窗当成眼下的屏幕 |

这一关的“关键帧”零件是个简化版：它没有真的一直盯着屏幕，而是在主脑截图时，翻查时间线上从上一次截图以来新出现过的画面（不包括眼下这一张），一并补上。效果和“一直盯着、变了就留”是一样的。

<a id="c-cu-world-model"></a>

### 往深处走：观察接口之后，还慢在哪儿

**这一段游戏里还没有关卡。**

关键帧解决了“看不全”，没解决“想得慢”。原书接着指出，观察接口不消除规划的延迟，循环还是串行的“截图、思考、点击”。它引了 OSWorld-Human 的效率研究：即使任务做成了，Agent 用的步数也明显多于人，等待时间更长。准确率追上了人，不等于已经好用。

原书给的下一步是**世界模型**（world model）：动手之前，先预测桌面的下一个状态。预测符合预期就沿着计划往下走，偏离了才停下来重新观察，有点像 CPU 的推测执行。原书特别强调两点：

- 桌面状态不只是像素，还有窗口、焦点、滚动位置、输入框内容、加载状态、权限、网络返回。
- 要预测的是**任务需要、可以检查的状态差异**，用不着画出一张逼真的未来截图。比如删除文件前，先在隔离的桌面上预测会不会弹出不可逆的确认框。

这一点和 6-1 的教训是连着的：不可逆的动作，最好在动手之前就知道后果。原书还提到一个实现，Induction Labs 的 Photon-1，结果是公司自报的。

原书另有一小节讲移动端。技术差异确实有（Android 的无障碍服务、触摸手势让同一个坐标有不同含义），可作者的观点是，真正卡住手机 Agent 的是生态：Agent 绕过了广告、流量和冲动消费这条变现链，平台和 Agent 之间是结构性的利益冲突，短期内难调和。

## 任务 6-3　抓住了吗

最后一件，动真家伙：**让机械臂把桌上的红杯放进托盘。** 掌柜提醒：这条机械臂年头久了，夹爪偶尔打滑；它每做完一个动作都会回一句话，你听听它回的是什么。

主脑只有一件工具 `arm`，可以 `pick`（抓起一件东西）或 `place`（把抓着的东西放到某处）。你什么都没装，按下发射：

| 呼叫 | 主脑做了什么 | 工具回了什么 |
| --- | --- | --- |
| 第 1 次 | `arm(pick, 红杯)` | `已执行 pick。` |
| 第 2 次 | `arm(place, 红杯, 托盘)` | `已执行 place。` |
| 第 3 次 | “红杯已经放进托盘。” | |

地面验收：托盘是空的，红杯还在桌上。你的站跟掌柜说的是：已经放进托盘了。

<a id="c-closed-loop"></a>

## 每一步都要看结果

### 为什么会有它

事故调查题问你：机械臂每一步都回报“已执行”，主脑也说杯子放好了，杯子为什么还在桌上？

| 选项 | 为什么不对 |
| --- | --- |
| 主脑下错了指令 | 指令没错：先抓红杯，再放到托盘。顺序和对象都对 |
| 换一条更可靠的机械臂 | 再可靠的机械臂也有滑脱的时候 |
| 让主脑最后汇报时更谨慎一点 | 它拿什么谨慎？它手里只有几句“已执行” |
| **“已执行”只说明指令发出去了，没说结果。第一次抓取时杯子滑脱了，没有任何东西去看一眼，后面的动作就全建立在一个没发生的结果上** | 正解 |

去数据舱打开 `state/table.json`，事情一清二楚：

```json
{ "红杯": "桌面", "夹爪": "空", "attempts": 1 }
```

把这一趟按时间排开：

| 步骤 | 主脑以为 | 实际发生 | 机械臂回报 |
| --- | --- | --- | --- |
| pick | 杯子抓起来了 | 夹爪合上了，杯子没跟着起来 | 已执行 pick。 |
| place | 杯子放进托盘了 | 夹爪是空的，什么也没放 | 已执行 place。 |
| 汇报 | 任务完成 | 杯子还在桌上 | |

第一步的失败没有消失，它被第二步原样继承，最后变成了一句自信的“已经放好了”。一次局部的小失败，就这样被带到了任务末尾。

### 它是什么

控制工程里有一对老词：**开环**（open-loop）和**闭环**（closed-loop）。

| | 开环 | 闭环 |
| --- | --- | --- |
| 做法 | 把整串动作一口气做完，再汇报 | 每做一步就观察一次，不对就只重做这一步 |
| 生活里的例子 | 老式定时烤面包机：拧到三分钟就烤三分钟，面包焦没焦它不管 | 空调的温控器：屋里够凉了就停，热了再开 |
| 谁来确认“做完了” | 指令本身：“我发过指令了” | 一次新的观察：“我看见杯子在托盘里” |

（烤面包机和温控器的比方是本手册加的。）

装上“逐步核对”再发射。每个动作做完，传感器看一眼结果，把看到的附在回报后面：

| 呼叫 | 主脑做了什么 | 工具回了什么 |
| --- | --- | --- |
| 第 1 次 | `arm(pick, 红杯)` | `已执行 pick。`<br>`［传感器观察］红杯在桌面上，夹爪是空的。` |
| 第 2 次 | “夹爪是空的，杯子滑脱了。再抓一次。” `arm(pick, 红杯)` | `已执行 pick。`<br>`［传感器观察］红杯在夹爪里，夹爪夹着红杯。` |
| 第 3 次 | `arm(place, 红杯, 托盘)` | `已执行 place。`<br>`［传感器观察］红杯在托盘里，夹爪是空的。` |
| 第 4 次 | “红杯已经放进托盘。第一次抓取时杯子滑脱了，我重抓了一次，放下后传感器确认它在托盘里。” | |

注意第 2 次呼叫：主脑只重做了失败的那一步，没有从头再来。最后那句“已经放进托盘”也不再是一句空话，它背后站着第 3 次的那行传感器观察。

**“做完了”这句话，必须由一次新的观察来确认，不能由“我发过指令了”来确认。** 这句话你在前面几站已经听过别的版本：第 01 站的[验收与闭环](01-agent-loop.md#c-verify)，第 05 站的[完成以验证为准](05-coding.md#c-gate)，第 07 站的[验证器](07-evaluation.md#c-verifier)。到了物理世界，它从“好习惯”变成了“不这么做就一定出事”。

原书在机器人一节里把这件事做成了一个对照实验（实验 6-13）：同一张桌子、同样的任务和工具，搬进模拟器，让抓取偶尔出现可以恢复的瞬时失败，比较三种做法：

| 原书的三种闭环 | 怎么做 |
| --- | --- |
| 开环执行 | 一次生成完整的动作序列，中途不再观察 |
| 逐步检查 | 每次 `pick` 和 `place` 之后重新读取状态，失败只重试当前这一步 |
| 预测式执行 | 再加一个短期世界模型，先比较候选动作的预期结果，再选下一步 |

原书要验证的关系是：开环会把一次局部失败带到任务末尾，逐步检查能恢复，预测还能进一步帮规划器排序；而最终是否真的完成，仍然由环境的反馈说了算。原书同时提醒，这个实验不证明小小的模拟世界模型等于真实的物理模型。6-3 演的，就是前两种做法的差别。

### 怎么用

原书给机器人工具定的规矩，几乎可以原样抄来用：

| 规矩 | 6-3 里对应的 |
| --- | --- |
| 一次调用只做一件事 | `arm` 一次只 `pick` 或只 `place` |
| 动作范围固定 | 只能抓桌上有的东西，`item` 填别的会报错“桌上没有……” |
| 有超时限制 | 这座站没做 |
| **执行后立即重新观察** | “逐步核对”零件 |
| 抓取失败只重试当前这一步 | 第 2 次呼叫只重抓，没重来 |
| 最终状态必须由新观察确认 | 最后一行传感器观察 |

原书把任务拆成 `pick(red_cup) → place(red_cup, tray) → verify_state()`，每完成一个技能，就得到一个可以检查的节点。原书的做法是给 Agent 单独的 `observe_scene` 和 `verify_state` 工具，并要求它每一步之后都去调；这一站的“逐步核对”更霸道一些，把观察直接焊在了动作的回报上，主脑想跳过都跳不过。代价是每一步都多读一次传感器。

还要提防一种偷懒：传感器也可能出错，也可能被遮挡。观察确认不了的时候，正确的做法是停下来上报“状态无法确认”，而不是当它成功了。原书的实验里，状态无法确认时 Agent 必须调用 `stop`。

#### 这一关的简化

- **第一次抓取必定滑脱。** 机械臂里有个计数器，第一次 `pick` 永远抓空，第二次起才抓得住。真实的滑脱是随机的，写死是为了让事故每次都能复现。
- **空手放下也回“已执行”。** 夹爪是空的时候调 `place`，什么也不会发生，回报照样是 `已执行 place。`。这一点倒是很像真的：执行器只管把动作做完，不管动作有没有意义。
- **真模型很难躲过。** 没装零件时，主脑手里只有“已执行”，它没有理由去抓第二次。除非它碰巧谨慎到多抓一遍，否则一定翻车。

<a id="c-control-layers"></a>

### 往深处走：机器人的分层控制

**这一段游戏里还没有关卡。**

6-3 的主脑说一句 `pick`，夹爪就动了。真实的机器人中间隔着好几层，原书列的是：

| 层 | 管什么 | 大致的节奏 |
| --- | --- | --- |
| 任务目标 | “把桌面整理干净” | 分钟级 |
| 长程规划 | 先处理哪个物体、每一步的完成条件 | 秒到分钟 |
| 基本技能 | `pick`、`place` | 约 1 到 3 秒 |
| VLA / 技能策略 | 当前画面 + 技能指令 → 动作 | 每秒推理约 1 到 10 次 |
| 底层控制与安全层 | 限速、急停 | 每秒 50 到 1000 次 |

分层的理由很实际：高层推理太慢，直接拿来控制关节会拖垮整台机器；底层控制频率太高，让高层去管会被一大堆无关细节淹没。所以原书主张，**模型不直接输出任意关节角**，只在 `pick`、`place`、`verify_state`、`stop` 这些有边界的技能里选，由经过标定、限速、带超时的执行器去执行。这和第 05 站给主脑划[执行边界](05-coding.md#c-guard)是同一个道理，只是这里撞坏的是真东西。

**VLA**（Vision-Language-Action，视觉-语言-动作模型）负责把技能落成连续动作。原书提到两种路子：RT-2、OpenVLA 把连续动作切成离散 token，好跟语言模型接上；π₀ 直接生成平滑的连续轨迹。两者没有简单的高下。

还有一个诊断思路值得一提。原书用几百美元的 XLeRobot 做桌面整理，先让人遥控它做一遍，做成了，于是得出结论：在这个任务上，硬件不是瓶颈，算法才是（原书特意说明只限这个任务）。固定硬件、换掉操作者，看差距出在哪儿。人遥控时会自然做很多算法必须显式写出来的事：靠近杯子时减速、杯子滑了就修正抓取点、没夹住就重新看、放下后检查一眼。最后那两条，正是 6-3 的“逐步核对”。

<a id="c-chunking"></a>

### 往深处走：动作块和过时的画面

**这一段游戏里还没有关卡。**

大模型每秒只能推理 1 到 10 次，控制器每秒却要更新几十到上千次。原书讲的工程办法是**动作分块**（action chunking）：模型一次生成一小段未来的动作，控制线程按高频执行这一段，模型在后台准备下一段。

代价和 6-2 是一回事。动作块越长，动作越平滑，可这段时间里模型看到的新画面越少。机械臂伸手抓杯子的途中杯子被碰动了，它可能还在执行根据旧画面生成的动作。原书的原话意思是：动作分块是在平滑性和反应速度之间做取舍，不是没有代价的加速。

原书接着列了 VLA 的几处局限（训练数据有限、行为克隆只学“下一步怎么做”不懂后果、每台机器人都不一样、观察可能过时），然后引出机器人的**世界模型**：给它当前状态和一个候选动作，让它预测下一个状态。原书讲了三种用法：

| 用法 | 做什么 |
| --- | --- |
| 动手前 | 比较几个候选动作。例：废纸被杯子挡住一半，是先抓纸、先挪杯子，还是换个方向抓 |
| 执行时 | 拿预测和真实观察对照，偏差大了就缩短动作块、停下或**重新规划** |
| 训练时 | 少在真机上试错 |

重规划也有讲究：原书说物体被人挪了、或者用户改了目标，只需要重新规划受影响的后续步骤，不必把旧计划全部推倒。最要紧的一句是：**预测只能帮着选，不能代替验收，真实的观察才是最终的事实。** 会生成逼真的视频，也不等于能指导机器人动作。

最后一个坑是**从仿真到真机**（sim2real）：模拟器里稳定，不等于真机能成。背景、光照、相机位置、遮挡、摩擦、传感器噪声、执行器延迟都不一样。原书的做法之一是训练时主动扩大画面变化的范围，但即使有改善，真机上仍要做相机标定、执行器测试和完整的安全闭环。

## 往深处走：还没有关卡的两条线

### 异步与事件驱动

**这一段游戏里还没有关卡。**

这条线模态没变，还是文字，变的只有时机：观察从“Agent 主动去取”变成“世界主动推来”，动作从“回合内做完”变成“先发起，后面靠事件收尾”。原书的要点按顺序是这样的：

| 问题 | 原书的办法 |
| --- | --- |
| 同步的 Agent 像只会排队的柜台：要么等后台任务跑完才能说话，要么说完话才处理新事件 | **事件驱动**：所有输入、输出、外部交互都建模成事件流，新事件到了就触发处理，不再靠轮询（polling） |
| 定时检查来不及。原书举 OpenClaw：它的 Cron 按预设时间、Heartbeat 每隔 N 分钟唤醒一次，都是时间驱动；第三方事件（新邮件、API 回调）没有即时通道。电话里客服要验证码，等下一次心跳，客服早挂了 | **事件通道**（Channel，原书举的是 PineClaw）：外部事件直接推给 Agent。主动服务要两样都有：Agent 能定时检查，事件也能主动通知 Agent |
| 几件事同时到达 | **事件循环**（event loop）：每轮从队列取事件、追加进轨迹、调一次模型、执行工具，再回来。同步接口下，事件只能在**安全点**（safe point）被消费，也就是一段推理结束或一次工具返回的时候 |
| 什么都立即打断不对，什么都排队也不对 | 按紧急度分三种：**取消式**（“停！我说错了”，等于提前制造一个安全点）、**队列式**（搜索途中补一句“只看最近一个月”，等下一个安全点一起追加）、**并行式**（“今天天气怎么样”，另起一个推理会话） |
| 有的接口要求每个工具调用都先配上结果。工具还没返回，用户插话了怎么办 | **占位符工具结果**：给没完成的调用先补一条“工具正在后台执行，请优先处理新事件”，真实结果到了再作为带任务编号的新事件送进来。不能伪造成功 |
| 占位符让模型把“已启动”当成“已完成” | **任务句柄**：`phone_call` 听起来像打完了，改成 `initiate_phone_call`，立刻返回任务编号和初始状态，接通、挂断都用事件通知。配套还要有查状态和取消的工具 |
| 一次追加好几个事件，模型只回应最后一个 | **未处理事件标记**：每条前面加 `[未处理事件 k/N]`，末尾汇总“共 N 个未处理事件，包括……” |

原书还提醒了两件容易误会的事。第一，代码里用了 `asyncio`，不等于模型会异步；要先查模型和接口支不支持这种消息顺序。第二，原书写到截至 2026 年 9 月，已有模型（GPT-6 Astra）原生支持异步工具调用和回合中途追加指令，可“消息能送到”和“能可靠地用好这些消息”是两回事：延迟到达的结果有没有归对任务、处理完插话还记不记得原任务、两条更新是不是都遵守了，都要单独检查。

一条“停止”消息也撤销不了已经发生的动作。取消要执行器自己响应取消信号，这和 6-1 的删除一样，发生了就是发生了。

<a id="c-voice"></a>

### 语音

**这一段游戏里还没有关卡。**

原书讲语音时，把时间尺度压到了 10 毫秒到 1 秒。到了这个尺度，光能收到更新不够，还得及时反应。原书的几个要点：

| 要点 | 原书怎么讲 |
| --- | --- |
| **延迟是一笔账** | 经典的级联方案是 VAD（语音活动检测）→ ASR（语音识别）→ LLM → TTS（语音合成），串着走，延迟一段段累加：等静音确认说完、识别、模型吐出第一个 token、合成出第一包音频，每一段都是瓶颈 |
| **流式** | 各段别等上一段全做完：边听边转写；拿临时转写先送模型推测着跑，最终文字不一样就取消重来；模型分段输出，合成增量进行 |
| **三种范式是取舍** | 级联（好调试，但延迟累积、语气情绪在接口处丢失）；端到端 Omni（延迟低、保留语气，但还是轮流说话，靠 VAD 猜对方说完没有，用户报数字时停顿一下就可能被当成说完了）；全双工（不预设轮次，持续听、持续说，随时决定继续、停顿、打断，代价是训练和控制更复杂） |
| **打断与抢占** | 全双工让用户可以随时插话，Agent 要能在半句话里停下来，把发言权让出去 |
| **快慢路径分离** | 前台要实时回应，后台才有深度思考。原书列了三种方案并说明是取舍：快慢各想一遍会前后矛盾（快的建议买，慢的几秒后发现套餐缺功能）；慢的通过专门接口给前台递建议，前台把话头接住；或者思考和表达做进同一个模型 |

原书对快慢分离的评价值得记一笔：它不只是延迟上的妥协。前后台解耦以后，换一个更强的后台模型，不用重训实时语音系统，就能直接吃到模型进步的红利。原书举的证据是，截至 2026 年 8 月，采用快慢分离的 Pine AI 语音 Agent 在 τ³-Voice 排行榜上排第一。原书还专门澄清，“端到端”有两层意思：语音通路端到端，和认知架构端到端，这是两根独立的轴。

<a id="c-primitives"></a>

### 四条线共用的骨架和原语

原书在这一章的小结里，把四条线收进同一条控制骨架：

```text
持续感知
  → 判断当前状态与时机
  → 选择回复或动作
  → 让输出进入环境
  → 观察反馈
  → 继续、修正、重试、停止或重新规划
```

这一站的三关，各自补的是骨架上的一个环节：6-1 补的是“让输出进入环境”时的换算，6-2 补的是“持续感知”，6-3 补的是“观察反馈”之后的“重试”。

四条线还共用一组原语，在不同时间尺度上长得不一样：

| 原语 | 异步事件 | 语音 | Computer Use | 机器人 |
| --- | --- | --- | --- | --- |
| **唤醒** | 事件通道把 Agent 叫醒 | 听到用户开口 | 画面变了留一帧（6-2） | 传感器发现偏差 |
| **安全点** | 推理结束、工具返回时才接新事件 | 一句话说到能停的地方 | 一步动作做完之后 | 一个技能做完之后（6-3） |
| **取消** | 执行器响应取消信号 | 推测执行失配就丢掉重来 | 放弃这一步，重新截图 | `stop`，急停 |
| **抢占** | 紧急事件插队 | 用户插话打断 | 弹窗打断当前计划 | 杯子被碰动，旧动作块作废 |
| **快慢分离** | 轻量问题另起会话并行 | 前台快模型、后台慢模型 | 便宜程序盯屏，主脑做判断（6-2） | 高层规划慢、底层控制快 |

这张表的具体填法是我按原书的思路排的，原书只列了五个原语的名字，并在思考题里点出它们在不同时间尺度上的实现各不相同。

## 容易讲错的地方

| 说法 | 实际情况 |
| --- | --- |
| 只能同步交互是大模型的天性 | 回合制是模型和接口的约定，不是环境的性质。原书也说，占位符那类问题来自所选的协议和模型组合，不是所有模型都必须这样 |
| 四条线是一级一级往上走的 | 四条线是并列的，同一个问题的四个时间尺度。游戏只做了后两条 |
| 截图太大，缩小就完了 | 缩小只是一半，点击时要用同一个比例放大回去；而且要等比，别把 16:9 拉进 4:3 |
| 坐标换算可以写进提示词让模型自己算 | 能确定的算术交给程序。模型会忘、会算错、会重复换算 |
| 截得勤一点就不会漏 | 固定间隔总会漏掉比间隔更短的画面，还白花钱。按变化留帧 |
| Computer Use 卡在动作接口上 | 原书的判断是该重新设计的是观察接口 |
| 有了关键帧，Agent 就快了 | 观察接口不消除规划延迟。原书接着讲的是世界模型 |
| 结构化元素索引省 token | 原书特别说明它不省 token，好处是稳定 |
| 工具回“已执行”，就是做成了 | 只说明指令发出去了。做没做成，要一次新的观察来确认 |
| 换一条更好的机械臂就不会出事 | 真实世界里动作偶尔失败是免不了的。靠的是每一步看结果、只重做失败的那一步 |
| 世界模型预测得准，就不用再看了 | 预测只能帮着选，真实观察才是最终的事实 |
| 发了“停止”，前面的动作就撤销了 | 停止撤销不了已经发生的事。取消要执行器配合；不可逆的动作要在动手前把关 |
| 代码里用了 asyncio，模型就会异步了 | 先查模型和接口支不支持这种消息顺序 |
| 快慢分离只是延迟上的妥协 | 它还让后台模型可以单独升级，原书认为这是一种模块化的选择 |
| 遥操作做得到，就说明硬件在哪儿都够用 | 原书的“硬件不是瓶颈”只限它那个桌面任务 |
| 模拟器里稳定，真机就能成 | 背景、光照、摩擦、噪声、延迟都不一样，真机仍要标定和完整的安全闭环 |

## 这座工坊哪里是真的，哪里是假的

| 东西 | 真假 | 说明 |
| --- | --- | --- |
| Agent 循环、主脑调工具 | **真** | Pi 运行时。接上真模型时，是真模型在读截图描述、决定点哪儿、决定抓几次 |
| 屏幕 | **假** | 服务端的一小段模拟程序，三个按钮的位置写死在 `screen.json` 里。点中的判定是：离按钮中心横向 120 像素、纵向 60 像素以内 |
| 截图 | 设定 | 一段文字描述，不是图片。这座站的主脑看不了图 |
| 坐标换算 | **真** | 一次真实的乘法：截图坐标乘 2.5、四舍五入，再去判定点中了什么 |
| 时间 | **模拟** | 6-2 的时钟只在截图时走，每次 3 秒；主脑思考不花时间。验证码固定在第 1.2 到 2.2 秒 |
| 关键帧 | 简化 | 没有真的一直盯屏，而是在截图时翻查时间线，把上次截图以来新出现过的画面补上 |
| 机械臂和传感器 | **假** | 状态存在 `state/table.json`。第一次抓取必定滑脱，为的是事故可复现；传感器观察就是把这份状态念出来 |
| 提线木偶模式 | 剧本 | 不接真模型时，主脑的话和调用是按剧本走的：装没装零件，各有一套 |
| 真模型的表现 | 可能不同 | 6-1 里真模型可能点完再截图，发现草稿被删并如实上报，但删除已经发生，任务照样失败；6-2 它看不到验证码，也猜不出来；6-3 除非它碰巧多抓一次，否则也躲不过 |

文中引用的 1024×768、1280×800、1366×768 三档分辨率与 (683, 384) → (1280, 720) 的算例、每 3 到 5 秒睁一次眼、每秒 1 张关键帧、12 毫秒、120 秒、控制分层的各级频率、2026 年 8 月和 9 月的两条时间注记，都是原书的数字。2.5 倍、(800, 480)、(2000, 1200)、第 0 秒和第 3 秒、第 1.2 秒，是游戏里的数。

## 带走几句话

1. 给模型看的画面几乎总是缩小过的。看的时候缩多少，点的时候就放多少，这一步交给程序。
2. 隔一会儿看一眼，看不到中间发生的事。让便宜的程序盯着，变了才留帧，下次一起交给主脑。
3. “已执行”只说明指令发出去了。“做完了”要由一次新的观察来确认，失败了只重做那一步。
4. 不可逆的动作，确认救不回来。要在动手前把关。
5. 世界不等主脑想完。这一站的三个零件，都是在主脑之外替它看、替它算、替它核对。

## 想一想

<details>
<summary>1. 6-1 里，如果截图工具不报坐标，而是给每个按钮编个号，点击工具改成“点第几号按钮”，还需要坐标换算吗？</summary>

模型那一侧不需要了，它只报编号，根本碰不到坐标。换算还在，只是挪进了点击工具内部：工具拿到编号，查出这个按钮在真实屏幕上的位置再去点。这就是原书讲的结构化元素索引的好处之一，也是它在网页上优先于坐标预测的原因。代价是你得拿得到界面的结构；Canvas 画的界面、游戏，就没有这份清单可用。

</details>

<details>
<summary>2. 6-2 里，如果验证码弹出来以后又变了一次（比如“验证码已更新为 4402”），关键帧补给主脑的两帧里，该填哪一个？</summary>

该填后一个，所以补帧一定要带时间。游戏里每一帧都标着“第几秒屏幕变成过”，主脑能按时间排出先后。要是补的帧不带时间、顺序也乱了，主脑看见两个验证码，只能猜。这也是为什么补的帧要和“现在的画面”分开放、明确标注。

</details>

<details>
<summary>3. 6-3 里，装了“逐步核对”以后，主脑要是第二次也没抓住，接着抓第三次、第四次……会怎样？</summary>

这就回到了第 05 站的老问题：重试没有上限，就会[重试到天荒地老](05-coding.md#c-breaker)。逐步核对让它知道失败了，熔断器管它失败几次以后该停下来上报。原书的机器人实验也要求：状态无法确认、物体离开工作区或用户喊停时，必须调用 `stop`。看得见失败，和知道什么时候放弃，是两个零件。

</details>

<details>
<summary>4. 这一站的三个零件里，哪一个让主脑变得更聪明了？</summary>

一个都没有。坐标换算是乘法，关键帧是一个盯梢的程序，逐步核对是把传感器读数念给它听。三关里主脑的判断一直是对的：它点的就是截图上的“提交订单”，它说的“没看到验证码”是实话，它看到“夹爪是空的”马上就知道重抓。出问题的始终是它和世界之间的那层接口：看到的东西不全、不准，做出去的动作没有回音。原书一开头就说，模型固定时，最主要的系统工程手段是重新定义观察空间和动作空间，这一站就是这句话的三个例子。

</details>
