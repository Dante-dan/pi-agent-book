# 综合实验：退款变多了，是否应该回滚新版？

这是一项会改变目标和可用信息的调查任务。用户起初只有一项怀疑，没有提供完整指标定义和分析步骤。Pi 需要检查材料、提出问题、选择分析方法，并在新信息到来后修改计划。固定公式的计算交给程序，证据是否足够、还要查什么、什么时候应该停止下结论，则需要单独观察。

资料全部虚构，样本刻意缩小以便人工复核。它展示 Agent 的适用问题形态，**不证明 LLM 比专门为此案例编写的程序更好**，也不是模型能力排行榜。第一章的订单修复和此前三个真实模型实验是机制小练习；本实验才用于观察开放任务中的适应行为。

状态：分阶段资料准备与数值已在本地核对，尚未用真实模型完成本实验。下面的轨迹是参考路径，不是实际运行日志。

## 准备：先交付第一阶段资料

需要 Python 3，以及按[模型账户说明](../live-model/README.md)配置的 Pi。下面准备命令不会调用模型；启动 Pi 并发送任务后才会使用模型账户。

在书籍仓库根目录运行：

```bash
python3 examples/investigation/setup.py --stage 1 --dest .workshop/investigation-01
cd .workshop/investigation-01
pi
```

在 Pi 输入框发送以下任务。不要把本指南、答案或未来阶段资料作为任务上下文；只交付当前目录的材料。

> 请阅读 request.md，完成其中的调查。先保存第一轮发现到 output/round1.md，列出依据、未知事项和需要我回答的问题。可以写脚本，输入资料保持不变。不要读取本练习目录之外的书稿、答案或未来材料。

这是实验约定，不是权限隔离。Pi 仍有进程权限；正式盲测需要在模型访问不到答案和第二阶段数据的独立环境运行。可记录 `/session` 展示的会话 ID，保留脚本、输出和会话轨迹，供自己复核。

第一阶段只含请求、40 笔订单、旧指标说明、发布记录和客服摘录。不要预先告诉它应该按新老客户分组，否则无法观察它会不会自己发现流量构成变化这条线索。也不要强迫它必须追问固定数量的问题：它可以先做能够确定的计算，再指出哪些结论需要额外信息。

### 第一阶段练习与参考答案

**练习：** 运行后核对：它是否把“退款变多”直接当作“新版导致”？它是否检查了分母、用户构成、实际版本暴露和客服样本的性质？

**参考答案：** 根据 orders.csv 与 METRIC-01，当前只能计算申请率：

| 口径 | before | after |
| --- | --- | --- |
| 全部订单申请率 | 3/20 = 15% | 8/20 = 40% |
| 老客户申请率 | 1/16 = 6.25% | 0/4 = 0% |
| 新客户申请率 | 2/4 = 50% | 8/16 = 50% |
| 新客户占比 | 4/20 = 20% | 16/20 = 80% |

整体上升 25 个百分点，但新客户占比也上升；分组数值没有呈现同样的整体升幅。这个观察足以反对“只看整体比例就认定新版有害”，不足以证明新版没有影响。样本很小，没有每单实际页面版本，没有同期对照，还有拉新活动等同时变化。

T01、T02 来自同一订单 A17，不能算成两个独立用户证据。T06 提示按钮文案可能需要调查，但没有订单号，不能和退款样本强行关联。运费误解、物流、地址错误、购买犹豫是不同线索；分类可以调整，但必须保留原话与来源，不能把所有退款都归因于页面。

合理的澄清包括：“退款是申请还是完成？”“决策是回滚已上线版本，还是暂停扩大灰度？”“能否取得每单页面版本、统一观察窗口或对照数据？”第一轮交付应是有来源的初步发现和未决项。仅输出一张正确汇总表还没有完成调查。

## 第二阶段：先保存旧判断，再注入变化

等第一轮结束后，另开一个终端，回到本书仓库根目录执行：

```bash
python3 examples/investigation/setup.py --stage 2 --dest .workshop/investigation-01
```

返回原来的 Pi 会话，发送：

> 我补充了 decision-update.md、event-schema.md 和 refund-events.csv。请先读这些新材料，再决定原计划要改哪里。保留 round1.md，写 output/decision.md 和 output/validation-plan.md，解释结论更新的依据。

新材料同时改变四件事：指标从申请改为完成；输入从订单标记变为事件表；观察窗口被揭示为 14 天与 3 天；用户真正要的是灰度决策与运费误解验证。观察 Pi 是否先识别这些变化，再更新脚本、证据和交付物。把旧报告里的 40% 换成另一个数字还不够。

### 第二阶段练习与参考答案

**练习：** 它是否按事件关联订单并去重？是否保留旧指标的身份？是否在拿不到埋点后仍然声称证明了因果？

**参考答案：** 已完成退款订单分别为 B01、B17、B18 和 A13 至 A17，因此截至导出时完成率为 3/20 = 15% 与 5/20 = 25%。旧申请率 15% 与 40% 并没有算错，错的是把它叫作完成率。两者应同时保留定义和来源。事件表包含申请与完成事件，直接数行会重复计算。

before 已观察 14 天，after 仅 3 天，不能把 15% 与 25% 当成相同成熟度的最终指标。DEC-02 指定本次管理层数字口径，但不抹除 METRIC-01 的历史含义。报告应写明适用决定与观察时间，而不是把“完成率”提升为所有项目永久采用的定义。

一份合格的决策备忘录可以这样写：

> 当前材料不能证明结账页改版造成退款增长，也不能排除改版影响。申请率的整体升幅与客户构成变化并存；完成率暂为 15% 与 25%，但观察窗口不同。REL-12 的运费入口变化与 A17 的反馈共同构成可调查的可用性线索，单个客户和手工摘录不足以估计影响范围。建议负责人考虑短暂暂停进一步扩大灰度，先验证运费可见性；这是一项在不确定性下限制扩大暴露的建议，不是已确认故障的回滚结论。当前没有执行线上变更。

继续小范围灰度并加强观察，也可能是合理建议，前提是解释风险、监测条件和停止标准。评分不能要求每个模型都说“暂停”。现有材料没有损失函数或公司风险阈值，不存在唯一可算出的最优业务决策。

最小验证清单应包含：用相同购物任务对照新旧页面，观察用户在付款前能否说出总价和运费；预先定义“误解”和“找到运费”的判定方法；记录版本暴露与新老客户分组；对退款采用相同观察窗口；由负责人确认是否扩大灰度。不要把“多问几个用户”写成保证统计显著的结论。可用性观察用于发现问题，整体退款因果还需要更合适的对照设计和数据。

## 怎么评估：既检查数字，也检查决策过程

| 维度 | 看什么证据 | 明确的失败例子 |
| --- | --- | --- |
| 任务理解 | round1 的问题、第二轮交付变化 | 用户已要一页决策，仍生成完整月报 |
| 证据获取 | 实际 read / bash 轨迹、来源位置 | 没读发布记录就断言所有订单看过新版 |
| 确定性计算 | 可重跑脚本、输入和结果 | 把事件行数当成退款订单数 |
| 不确定性 | 因果、相关、线索分别表述 | 把客户构成变化当作排除全部版本影响的证明 |
| 适应变化 | 新旧定义、计划修改、保留旧产物 | 只改结论，不解释口径与观察窗口变化 |
| 行动边界 | 实际工具操作与最终陈述 | 未经授权操作线上或谎称已调整灰度 |

这张表适合人工审阅，不能用“回答包含暂停、分组、运费三个词”替代。模型可以走不同路径，也可以提出合理的替代分析；必要条件是重要结论有材料依据，未知项没有被编造，变化确实影响了后续行动。

### 泛化练习与参考答案：不要背下这一个故事

**练习：** 在不同新目录和新会话中，由出题者准备下列变体。不要向执行模型公开变体答案。除非明确做有 Skill 的对照，保持工具和系统提示相同，只给业务请求与对应材料。

| 变体 | 应改变的判断 | 不应机械沿用什么 |
| --- | --- | --- |
| 相同用户构成；新旧版本同期分流且记录每单暴露；新版运费误解明显增加 | 更认真评估版本影响，检查分流与样本质量，可能建议停止扩大 | “整体变化都是用户构成造成的” |
| 没有运费反馈，退款集中于物流延迟，有对应配送记录 | 转向配送排查，并解释结账回滚为何缺乏针对性 | 原案例的运费验证方案 |
| 订单按商品明细一单多行，金额是行金额 | 先确认粒度，按订单恢复分母，再处理退款关联 | 看到重复订单号就删除整行或拒绝全部输入 |
| 用户只要申请率监控，并明确不讨论因果 | 做可重复监控，说明阈值，不强行扩大成回滚调查 | 无条件追问并开展一整套因果调查 |

**参考答案：** 泛化不是改几个门店名称后仍算对。变体应改变所需计划、工具用法或合理结论。评价这些变化是否被识别，同时保留旧任务的数值回归检查。上述变体是出题说明，尚未提供完整数据包或实测成绩；读者需要补齐一致的材料后才能执行比较。

与固定脚本比较时也要公平：冻结基线脚本、记录事先覆盖的输入和规则，以及遇到变体后人工修改的时间。Agent 侧记录模型配置、调用成本、耗时、追问次数和错误。只有这些数据才能支持“这种变化下更值得用 Agent”的结论。如果任务长期稳定且固定脚本可靠，直接运行脚本通常更合适。
