# 第 10 章 多 Agent 协作

> 出处说明：行号均指 `book/chapter10.md`（共 736 行，已通读）。`介绍` = 引言 `introduction.md`，`后记` = `afterword.md`。

## 一句话主旨

多 Agent 的价值不在“人多”，而在协作过程是否**引入了单个 Agent 生成时拿不到的新信息**（执行结果、截图、外部工具验证）；围绕这条判据，本章讲清上下文共享与否、三种拓扑（对等/管理者/去中心化）、数据平面与控制平面基础设施，以及多 Agent 特有的六类失败模式，最后把视角推到 Agent 社会。（§本章开头 L1–9；§多 Agent 何时真正优于单 Agent L46–77；§本章小结 L714–722）

## 起点问题

前九章全围绕**单个** Agent：先建上下文、知识、工具、交互，再靠评估、后训练、持续进化让它长期变好（L3）。缺口是：单个 Agent 终究受限于模型能力边界和上下文窗口（L5）。本章问：怎样组织多个 Agent，通过分工、通信、相互验证，完成单个 Agent 难以承担的任务（L3）。作者的更高远动机是“群体智能可以高于个体”，并引 Google DeepMind《从 AGI 到 ASI》把多 Agent 集体列为通往 ASI 的路径之一（L7）。同时作者特意澄清：OpenAI 五级框架里的 Organizations 指“能完成整个组织的工作”这一能力级别，不是对架构的要求，足够强的单 Agent 理论上也能达到（L5）。

| B4 | 并行搜索一个命中，其余应立刻停；主 Agent 终止后子 Agent 成孤儿 | **优雅终止**（`terminate` 信号，在安全点响应、清理资源、回 ack）为首选，**强制终止**兜底（类比 SIGTERM/SIGKILL）；**级联取消**沿创建关系向下（借鉴 Go context；脱离父级的后台 Agent 从新生命周期树起步，类比 `nohup`/`context.Background()`） | 稀缺的 token/并发额度谁来分配 | §执行终止 L180–184 |

### 链 C：失败模式（**并列**的六种，非递进）

| # | 现象 | 被逼出来的对策 | 原书出处 |
|---|---|---|---|
| C1 | 共享文件系统并发冲突：简单冲突（后写覆盖先写）与**语义冲突**（A 重编全书图片编号，B 同时修改章节并引用旧编号，文件层面零冲突、结果全错） | **乐观锁**（版本号/时间戳，写入前校验，失败则重读重做）只防同一文件；跨文件语义冲突需更高层语义校验；Coding Agent 场景主流做法是**工作副本隔离**（每 Agent 独立 Git 分支/worktree，冲突推迟到合并点） | §失败模式一 L537–547 |

## 概念清单

- **共享上下文**（shared context）｜要让后续 Agent 不丢前序细节｜后续 Agent 继承前一个 Agent 的完整对话历史/轨迹，每阶段换 system prompt+工具集即为新 Agent（接班同事翻前任工作日志）｜优势信息不丢，挑战上下文膨胀、被历史干扰｜L19、L81
- **不共享上下文**（isolated context）｜要模块化、并发、权限隔离｜每个 Agent 独立上下文和历史，靠显式通信交换信息，像进程隔离｜接口和数据格式设计至关重要｜L21、L104–129
- **IPC 两大范式**｜Agent 通信问题在分布式系统里早有答案｜共享内存 vs 消息传递；Agent 世界：共享文件系统=共享内存，工具调用参数与消息总线=消息传递的同步/异步形态｜L23–29。Go 谚语“不要通过共享内存来通信，要通过通信来共享内存”（L29）
- **协作拓扑**｜决定控制权与信息按什么结构流动｜对等 / 管理者 / 去中心化；Graph Engineering 视角下都是不同图拓扑｜L36–42
- **新信息判据**（信息增量）｜解释学术与工程的矛盾｜协作是否引入单 Agent 生成时无法获得的信息｜用它判断是否该上多 Agent｜L48–67
- **RLEF**｜证明执行反馈有价值｜强化学习训练模型利用代码执行反馈迭代改码，远超独立多次采样｜L62
- **WebGen-Agent**｜证明视觉反馈有价值｜截图+VLM 描述的多层反馈，据报 Claude 3.5 Sonnet 在该基准 26.4%→51.9%｜L62
- **步骤预算 / 预算感知**｜更多步数不等于更好｜Google《Budget-Aware Tool-Use…》：无预算意识的 Agent 浅层搜索很快“饱和”；BAVT 按剩余预算比例调探索/利用｜Manager 应按子任务复杂度动态分配预算并引导“先规划再实现再测试再改进”｜L73–75
- **`transfer_to_agent` vs Skill**｜角色转换的两种载体，成本模型不同｜前者替换 prompt+工具集（强约束、破坏前缀缓存），后者固定前缀按需追加（缓存友好、约束弱）｜差异在知识/流程/风格→Skill；涉及权限/工具隔离/合规→独立 Agent 或 transfer，并在 Harness 层用代码限制｜L85–92
- **多 Agent ↔ OS 对照**｜借用成熟经验｜静态前缀=程序，轨迹=进程内存，LLM=CPU，运行时=内核，工具调用=系统调用，spawn/cancel/list=fork/kill/ps，结构化摘要=退出码，Actor 模型的 LLM 版｜L106–123
- **虚拟文件系统四区**｜混置本应隔离的区域是并发冲突与信息泄露的来源｜Scratchpad（私有，保持主上下文精简）/ Shared Workspace（用户可见，并发高发）/ 外部挂载（权限受外部约束、延迟高一致性弱、多只读）/ 内置资源（Skills，只读）｜用表10-3 当布局检查表｜L133–164
- **数据平面 / 控制平面**｜产物交换与生命周期管理是两回事｜文件系统=数据平面；消息、状态查询、终止、调度=控制平面｜L131、L192
- **信封（envelope）**｜让消息可路由可追溯｜发送者/目标/类型/负载｜L170
- **轨迹持久化 / 进度文件**｜无需状态上报协议获取子 Agent 状态｜JSONL 日志可直接读，但太重；约定 progress.md 更轻，并可用修改时间检测卡住｜L176–178
- **优雅终止 / 强制终止 / 级联取消**｜并行搜索的一个成功要让其余停止，且不留孤儿｜SIGTERM/SIGKILL 类比；Go context 式向下级联｜L180–184
- **过早终止三形态**｜Agent 实践中极常见失败｜偷懒式假完成、过早放弃、假成功｜统一根源：验证前“完成”只是宣称｜L202
- **Loop 工程**（Loop Engineering）｜把宣称变证明｜验证器而非模型判定“是否真能停”；人从写提示词的操作者变成设计循环的工程师；2026 年 6 月由 Addy Osmani 总结，Boris Cherny“我的工作是写 loop”｜“循环的瓶颈在验证器”｜L204
- **LoopX**｜把循环从提示词/聊天历史抽到持久控制面｜决策→执行→独立验证→提交；只有通过验证才写进度并耗配额｜“模型可以提出‘完成’，但不能批准自己的‘完成’”；作者注明 v0.4.0 受控 Turn 路径仍属实验性，只作示例而非质量提升证据｜L208–216
- **LongHorizon-Harness / MEA**｜长程 GUI+CLI 任务跨多次上下文刷新｜Manager 出下一项有界子任务→Executor 在全新上下文执行→Auditor 只读检查｜同模型同后端只换外层 loop：WeaveBench 51.8%→80.7%，OSWorld 2.0 2.8%→8.3%，Terminal-Bench 2.1 69.7%→77.2%；代价 token 2.3×/3.6×（前两个基准），TB2.1 反降 24%｜L218–224
- **提议者-审核者**（Proposer-Reviewer）｜自审无效｜审核者读独立证据，退回带可定位修复条件，且不能改测试/证据采集器/发布门槛｜PPT 审核价值在“渲染并截图”而非“再看一遍代码”｜L228–262
- **规划者–生成者–评估者**｜长程应用开发｜Anthropic 2026：评估者用 Playwright 操作真实应用提缺陷；Agent 间靠文件交接；用显著更高成本换质量｜L264
- **辩论 / 头脑风暴 / 专家小组**｜对等协作的三种变体｜对抗、独立生成后互启发、跨领域互补｜辩论效果有争议（见上），自一致性/多数投票与“生成难验证易”的分工不被否定｜L268–282
- **管理者模式**｜子任务多、动态调度｜Manager 把子 Agent 当工具调用｜单点瓶颈；规划者质量决定上限｜L284–292
- **并行结算点 / `settle_once`**｜两个几乎同时的成功不能触发两次汇总｜“第一个已验证成功”才结算，原子声明获胜者，向其余广播取消，等 ack 或超时｜L294–312，竞态说明 L412
- **灵台（Lingtai）**｜管理者模式的产品化｜主器灵=Manager，分神=短时并行工作者（只带结论回来），分身=持久专门化队友；“器灵即其文件”；上下文将满时“凝蜕”｜L360–366
- **管理者生成 Agent 工作流**｜管理者在循环里每次派活都要决策、上下文增长｜管理者先写一段代码，交确定性运行时执行；Claude Code Workflow 工具的 `agent()`/`parallel()`/`pipeline()`，子 Agent 只返回 schema 约定的结构化结论｜L429–441
- **去中心化 / 编舞**｜消除 Manager 单点故障、模拟人类分工制衡｜每个 Agent 自主决定何时移交/请教/报告｜微服务的 choreography｜L445–449
- **MetaGPT（SOP）**｜把软件公司 SOP 编码为协作协议｜PM→架构师→项目经理→工程师→QA 固定流水线；真正贡献是共享消息池+按角色订阅带来的解耦；“移交包”三要素：任务描述、已确认事实与约束、产物引用（路径不是内容）｜作者如实说控制流并非去中心化；QA 直找 PM 等多向反馈是扩展设想，原版未实现｜L453–473
- **AutoGen 群聊**｜共享对话记录+中心化选择器｜GroupChatManager 决定下一个发言者｜混合形态，不是完全去中心化｜L475–477
- **OpenAI Swarm / handoff**｜控制流真去中心化｜任意 Agent 可随时把控制权移交给任意其他 Agent｜移交只传任务包+产物引用；成环用 `visited_agents`+`remaining_budget` 防护，由运行时保留｜L479–501
- **“Agent Swarm”一词的两种用法**｜避免被名字迷惑｜OpenAI Swarm 式 handoff 网络（去中心化）；Kimi K2.5/K3、Anthropic 多 Agent 研究系统、Manus Wide Research 是规模化的管理者模式（orchestrator-worker 星型）｜L503
- **A2A（Agent2Agent）**｜跨组织、互不信任时三种内部机制不够｜Agent Card（能力发现）/ Task 状态机（已提交、进行中、需要输入、已完成、失败）/ 不透明协作（只交换任务与产物）；Google 2025 发布后捐给 Linux 基金会｜MCP 管 Agent↔工具，A2A 管 Agent↔Agent，不取代三种内部机制｜L515–521
- **崩溃故障 vs 拜占庭故障**｜Agent 故障的性质｜Agent 很少停止，而是继续给出看似可信的错误结论｜交叉验证、多数表决是经典手段｜L533
- **理解债 / 认知投降**｜人的失败模式｜交付速度越快对系统的理解越落后；习惯代劳后放弃审查｜L575
- **涌现行为（Emergent Behavior）**｜Agent 社会的核心现象｜无法从个体规则直接预测的集体行为；关键在“没有任何显式的派对组织代码”｜L587、L615

## 容易讲错的地方

- **“多 Agent 一定更强”是误解。** 作者明确：同一模型自审、不同 Agent 辩论同一段文本，在等计算量下无增益甚至有害（表10-1，L52–60；L238、L272）；辩论论文里的收益很可能只是多花了计算量（L272）。判断标准是“是否引入新信息”和“收益是否覆盖数倍至一个数量级的 token 成本”（L48、L77）。
- **学术与工程的矛盾是“两种多 Agent”**：学术比的多是“多个 Agent 看同一段上下文互相讨论”，工程中有效的系统带外部反馈环路（L67）。
- **多个实例 ≠ 多种思路。** 同模型同上下文同脚手架会做出相同选择，局部错误变系统性故障（L196、L557）。
- **Skill 与 `transfer_to_agent` 不是同一种成本模型**：Skill 缓存友好但只是行为指令，硬权限仍需 Harness 门；需要权限/工具隔离/合规边界时用独立 Agent 或 transfer（L85–92）。
- **“拉取式状态查询”看似直观，作者认为不实用**：子 Agent 创建即执行，完成时会自动通知主 Agent；更好的是消息或约定进度文件，而不是把轨迹当主要传递方式（L172–178）。
- **MetaGPT 不是真去中心化**：控制流是固定流水线，只在通信（消息池+订阅）上解耦；“QA 找 PM 澄清需求”之类多向反馈是扩展设想，原版未实现（L451、L473）。AutoGen 群聊也不是完全去中心化（L477）。
- **“Agent Swarm”不对应单一架构**：OpenAI Swarm 式 handoff 才是去中心化；Kimi/Anthropic/Manus 的 swarm 多是规模化管理者模式（L503）。
- **乐观锁只防同一文件**，跨文件语义冲突需要更高层校验或 worktree 隔离（L547）。
- **Agent 故障是拜占庭式的，不是崩溃式的**：很少停止，而是继续给出可信的错误结论（L533）。
- **去中心化并不比管理者天然更好**：它的卖点是缓解管理者单点故障（L447），代价是成环等新风险（L481）。
- **A2A 不取代三种通信机制**，只在跨信任边界时需要；同团队内部直接用消息总线（L521）。
- **Agent 社会里的“反思”不是第九章的持续进化**：前者更新即时内部状态和目标；后者要经过结果评价、跨轨迹归纳和验证才算长期能力更新（L607）。
- **强观点**：“循环的瓶颈在验证器，而不在模型”（L204）；“模型可以提出‘完成’，但不能批准自己的‘完成’”（L214）；弱规划者是最关键瓶颈，应把最强模型给 Manager（L292）；“你可以外包你的思考，但不能外包你的理解”（L577）；更强的模型或单体层面的对齐不会自动带来群体协调（L722）。
- **LoopX 和 LongHorizon 的数据别说过头**：作者注明 LoopX 受控 Turn 路径是实验性，不能作为一般质量提升证据（L214）；LongHorizon 的成本代价不固定（有的基准 token 2.3×，TB2.1 反减 24%，L222）；单个轨迹对比不能代替总体统计（L224）。
