# 知识库：原书每一章的因果链

这里是 π 工坊设计关卡、写手册之前的底稿。来源是李博杰《[深入理解 AI Agent](https://github.com/bojieli/ai-agent-book)》（Apache-2.0）的十章正文：每一章从第一行读到最后一行，按固定格式整理出它的推导顺序。

> 这些文件是**整理和转述**，不是原文。每条论断后面的行号指向原书 `book/chapterN.md`，要引用请回到原文核对。

## 为什么要有它

工坊的玩法是“零件由事故逼出来”。事故的顺序如果是凭印象排的，学到的因果就是假的。所以定了一条规矩：**做任何一站之前，先有这一章的因果链；关卡和手册都只从因果链里取材。**

## 三方分工

| 角色 | 负责 | 产出 |
| --- | --- | --- |
| 阅读者 | 通读原书一章，按 [SCHEMA.md](SCHEMA.md) 整理因果链、概念、例子、关卡候选 | `chNN.md` |
| 游戏开发 | 从因果链里挑能做成“确定可复现的事故”的节点，做成任务 | `playground/` |
| 手册作者 | 对照已经做好的游戏写手册；顺手核对游戏文案和原书是否一致 | `book-v2/NN-*.md`、`review-station-NN.md` |

手册永远在游戏之后写：它解释的是玩家刚在屏幕上看到的那一幕。

## 全书结构

原书引言把十章分成两部分：

| 部分 | 章 | 回答的问题 |
| --- | --- | --- |
| 如何构建 Agent | 1–6 | 基本概念 → 上下文 → 记忆与知识 → 工具 → Coding Agent → 观察与动作空间的扩展 |
| 如何提升 Agent 能力 | 7–10 | 先用评估建立可度量的反馈，再从模型参数（后训练）、单体系统（持续进化）、群体系统（多 Agent）三个层面扩展能力 |

贯穿全书的公式是 **Agent = LLM + 上下文 + 工具**，引言给了三种说法：

| 实现层 | 直觉层 | 强化学习的说法 |
| --- | --- | --- |
| LLM | 大脑 | 策略（Policy） |
| 上下文 | 眼睛 | 观察空间（Observation Space） |
| 工具 | 手脚 | 动作空间（Action Space） |

引言里另有两个反复出现的立场：**实践在前，命名在后**（Skill、Harness 这些词出现之前，对应的做法已经在用了）；**好的设计原则应该穿越模型的迭代周期**。

## 章与章之间的递进

下面只列各章条目“递进能力”一节里明确写到的依赖，方便安排开工顺序。

```
1 入门（公式、ReAct 循环、Harness 五要素、提议者与审核者）
├─ 2 上下文工程（静态前缀 + 轨迹、KV Cache、Skills、状态栏、压缩）
│   ├─ 3 记忆与知识库（跨会话；检索；更新走提议者与审核者）
│   └─ 4 工具（渐进式披露接 Skills；执行层防御接提示注入）
│       └─ 5 Coding Agent（代码即元能力；测试与类型是现成的 Harness）
│           └─ 6 交互（把“轮流说话”的前提打破）
└─ 7 评估（给后三章提供尺子）
    ├─ 8 后训练（改模型参数）
    ├─ 9 持续进化（改模型之外的载体；第 3 章的定期整理是它的知识管理版本）
    └─ 10 多 Agent（群体层面）
```

## 用这些条目时要注意

- **并列就是并列。** 原书很多地方是换话题而不是递进，条目里都如实标了。设计关卡时不要为了凑一条梯子把并列主题硬串起来。
- **事故要确定可复现。** “关卡候选”里的事故都应该来自关卡自己的虚构数据或确定性计算。模型凭常识就能答对的题测不出东西。
- **数字只引用，不复现。** 原书引用的外部数据（比如某个基准的分数）在游戏里只能转述并注明来源，不能包装成游戏自己测出来的。
- **原书会更新。** 条目里的行号对应整理时的版本；大改之前先 `git pull` 原书，看对应小节有没有变。
