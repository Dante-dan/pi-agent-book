# 第 1 章 AI Agent 入门

> 出处行号均指 `book/chapter1.md`（共 572 行，已通读）。本章作者自己声明是"全书的概念地图"（L9），所以**大部分内容是并列的概念引入，不是严格递进**。下面把真正有"因为 X 不行所以 Y"的地方串成链，其余如实标为并列。

## 一句话主旨
Agent = LLM（大脑）+ 上下文（眼睛）+ 工具（手脚），模型固定时最大的杠杆是扩展观察空间与动作空间；能跑的 Demo 和可靠的产品之间的鸿沟，靠 Harness（上下文管理 + 工具接口 + 约束 + 验证 + 纠正）去填，模型之外的工程成了竞争力所在（§现代 Agent L11-27；§Harness 工程 L263-319；§本章小结 L539-557）。

## 起点问题
本章是第一章，没有"上一章留下的缺口"。它的出发点是一个观察：Cursor、Deep Research、Manus、豆包手机助手、Pine AI 形态各异，但都不再是"你问一句它答一句"，而是自主规划、调工具、按结果调整（§开篇 L3-5）。要回答的两个问题（L265 原文自述）：**Agent 是什么**（前半章），**Agent 如何在生产环境可靠运行**（后半章）。

原书的推导可以拆成四条链：**链 A**（Agent 是什么 → 为什么要 Harness，原书主干，A1–A10 基本递进）、**链 B**（编排模式：工作流 vs 自主）、**链 C**（护栏三层，递进最清晰）、**链 D**（设计模式，纯并列，不成链）。链 A 末尾通过"工程原则"过渡到链 B/C，但 L353 作者明说后面三节（选型、编排、护栏）是"独立但重要的主题"，所以 B、C 与 A 是**并列关系**。标注"叙述衔接"的格子表示原书只是顺着往下讲，并无"X 不行所以 Y"的论证。

| A7 | "每个组件都不可或缺"只是论断，要靠实测 | **消融实验**（实验 1-1）：完整基线 + 四组各缺一个组件（系统提示词不参与消融）。结论：缺**工具定义**→无法行动，但**不沉默**，会给出格式工整、语气笃定、实为参数记忆编造的答案（"不得自行估计"之类约束只降低编造概率）；缺**工具执行结果**→闭环断裂，Agent"盲目"反复重试直到耗尽迭代预算；缺**思考过程**→几乎无代价（可从工具结果重建）；缺**历史消息**→冗余操作、重复犯同样的错。组件并不等价，衡量标准是信息能否从别处重建 | 各组件如何协同成一个循环？ | 实验 1-1 L151-159 |
| A8 | 三个组件需要一个机制串起来 | **ReAct 循环**：想→做→看，直到任务完成；**轨迹**（trajectory）= 动态消息历史；**上下文 = 静态前缀 + 轨迹**，每次调用都追加、都看到完整轨迹；退出条件：模型不再调工具 / 最终输出工具 / 报错 / 达最大轮数。例：多币种汇总 3 次迭代、4 次工具调用得 $9,602,895.73。用 Kimi K3（客户端仍驱动循环）与 GPT-5.6 Responses API（服务端闭环）两个实验展示"模型即 Agent" | 基本机制证明有效，但暴露脆弱点：模型可能幻觉（编造工具或参数）、选错工具、出错后无法自救。Demo ≠ 产品 | §ReAct L161-261 |
| A9 | 一个能跑的 Demo 和可靠的产品之间有鸿沟（幻觉、选错工具、不能自我恢复，L265） | **Agent = Model + Harness**；**Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**。约束=故障安全默认值（能力默认关闭、显式开放）；验证=自动判对错，**安全检查只看结构化数据、不看模型自由文本**（可能已被提示注入操纵）；纠正=发现问题自动修正/回退，确认无法恢复前不暴露中间态（先静默重试）。五项构成闭环：上下文+工具让它"能做事"，约束预防/验证发现/纠正闭环让它"不做错事"。Harness 是 **Agent 边界内、模型之外**的运行与治理层，不含 Environment。Claude Code 的 Harness 大部分代码是约束/验证/纠正：流程状态、多层上下文压缩、权限分类、熔断器、错误恢复 | 作者把这个判断推广：为什么说这是竞争力所在、行业怎么演进？ | §Harness 工程 L263-319 |
| A10 | 当各家模型能力越来越接近，光比模型分不出胜负 | **工程范式演进**：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程（层层包含，不是替代）；**竞争优势转到模型之外**。证据：LangChain 在 Terminal Bench 2.0 上只改 Harness（让 Agent 自查执行结果、检测重复循环、优化思考策略），得分 52.8%→66.5%（排名 30 开外→前 5）。三条核心原则（Anthropic）：**保持简单**、**保持透明**、**设计好工具接口 ACI**（Agent 视角而非程序员视角，用设计让错误无法发生=防呆 Poka-yoke，如 SIM 卡缺角、微波炉门不关不加热） | 工程原则说"保持简单"，具体到编排怎么选？（→ 链 B，并列主题，L353） | L321-351 |

### 链 C：护栏（三层，按被绕过的难度排序，不是请求处理顺序）

| # | 上一步在哪儿翻车 | 被逼出来的概念/方案 | 它又留下什么新麻烦 | 原书出处 |
|---|---|---|---|---|
| C1 | 只靠一道防线不够，单个护栏不太可能提供足够保护 | **护栏分层**：先针对已识别风险设置，发现新漏洞再加；多个专门护栏组合。三层：上下文层、执行层、数据层，**越靠下越不依赖模型自己的判断，越难被一次成功的攻击穿透**。护栏也会失败：**误拒绝**——为降低危险请求放行率，可能连带拒绝合法但形式敏感的任务（授权安全测试、蒸馏研究），所以评估要同时测"该拒的拦住了吗"与"明确允许的能完成吗" | 第一层具体怎么做？ | §护栏 L466-476；L472 |

| C3 | 上下文层给不出保证，需要不依赖模型判断的第二道 | **执行层**（管模型能做什么，动作生效前验证）：**工具风险评级**（按可逆性、权限等级、财务影响标低/中/高，高风险需额外审查或人工确认）；**复核必须由上下文之外的机制完成**（独立审查进程、最小权限凭证、沙盒隔离、人在回路），否则会和被注入的 Agent 一起沦陷；输出检查（PII 过滤、输出验证）也属于本层，因为给用户的回复本身是一次动作 | 即使注入得手、生成的代码漏写权限判断，世界最终被改成什么样还要有最后保障 | L486 |
| C4 | 前两层都依赖"动作之前拦截" | **数据层**（管世界最终能被改成什么样）：数据库行级安全、约束与校验器、受控视图/存储过程、由受信任运行时绑定且无法伪造的访问上下文；**不依赖上面两层是否正确**，越权操作在数据层照样被拒（第五章展开） | 还需要在 Agent 做不下去时平稳移交 | L488 |
| C5 | Agent 无法完成或遇到高风险时 | **人工干预**（Human in the loop）：两类触发——**超过失败阈值**（重试/操作次数上限，超出即升级）、**高风险操作**（敏感/不可逆，如大额退款付款；至少在团队对可靠性建立信心之前）。客服升级人工、Coding Agent 把控制权交回开发者；部署早期尤其重要，帮助发现失败模式并建立评估周期 | （链 C 结束；转到并列的章节映射与设计模式） | §人工干预 L490-502 |

### 链 D：设计模式（并列，不成链）
原书一次性命名五个贯穿全书的模式，彼此是并列关系（L525-537）：
- **提议者—审核者**：产出与评判由不共享上下文的两个角色承担，评判方看产物（渲染结果/测试输出/结构化调用参数）而非推理过程；前提是**自审不可靠**（同上下文的模型难发现自己的盲区，也难判断自己是否被注入）。
- **渐进式披露**：先给可检索目录，再按需加载细节；同时优化上下文预算与选择精度（Agent Skills：元数据常驻，正文按需加载）。
- **只增不改（Append-only）**：状态追加演进，换来可缓存、可重放、可审计；KV Cache 前缀稳定性是性能形态（改动越靠前，作废缓存越多）；新工具 schema 追加到轨迹末尾而不插回前缀。
- **边界集 + 保留集**：任何修改要同时在"应当改变的样本"和"不应受影响的样本"上验证；只测前者把过拟合当进步，只测后者把无效修改当安全。
- **最小 diff + 可回滚**：每次修改小、带来源、可单独回滚，让归因成为可能；本章三条更新路径按可回滚程度从高到低排列。

### 并列旁支：Agent 的三条学习/更新路径（L125-135）
不是链上的节点，是对"A5 模型 RL 内化"的补充：行为改变不只发生在训练阶段。**上下文适应**（任务内，快、便宜，受窗口限制）、**外部产物更新**（知识文档/Prompt/Skill/程序与 Harness，可审计可修订，仍需经上下文或工具被使用）、**参数更新**（后训练，部署成本高，适合高维隐式能力如医疗影像、语言风格）。三者是不同时间尺度上的协同，而非互斥。

### 并列主题：模型选型（L355-370）、框架对比（L442-462）
- 选型：选对模型往往比优化提示词更有效；不推荐具体版本；**在自己的任务上评估**；开源与闭源差距在 6 个月内但成本显著更低；工具调用能力差异大，必须在场景中测；除能力外要考虑**策略边界**（厂商对网络安全、蒸馏、隐私、高风险操作的限制，同一任务在聊天产品/Coding Agent/API 里结果可能不同，业务关键任务要准备人工接管或替代模型）；绝大多数 Agent 需要支持思考的模型（例外：单步简单任务、固定位置点击）；输出速度（20 轮每轮慢 2 秒=多等 40 秒）和多模态。
- 框架表：Codex Harness、Claude Agent SDK、LangChain/LangGraph、n8n、Dify、CrewAI、OpenClaw、DeepSeek Harness、Pi。作者强调框架会过时，关键是"用尽可能少的抽象层让你专注业务逻辑"。

## 概念清单

- **Agent 公式**（Agent = LLM + 上下文 + 工具）｜要有一个最小工程骨架来谈构建｜加号是工程组件组合；LLM=大脑、上下文=眼睛、工具=手脚；映射 RL 的策略、观察与历史、观察/行动接口但非一一等同；不含 Environment｜用它拆分析任何 Agent 产品（表格：Cursor/Deep Research/Browser Use/豆包/Pine AI 各自的眼睛、手脚、策略）｜§现代 Agent L11-59
- **Environment 与边界**｜Agent 与环境是 RL/控制论里闭环的两方｜环境含文件、数据库、网页、用户、其他 Agent、物理或仿真世界；Agent 只通过观察与行动接口触达｜用来判断某物属于 Harness 还是 Environment：沙箱的权限与重置机制属于 Harness，沙箱内随行动变化的文件进程属于 Environment；与物理部署位置无关｜L21-29；L279
- **观察空间 / 动作空间**｜模型固定时这是主要的能力杠杆｜观察通道决定什么能进上下文，动作接口决定什么能真正执行｜扩展它们=扩展上下文和工具（Manus 取并集、OpenClaw 延伸到消息渠道和本地数据）｜L37-45
- **工具调用**（Tool Calling / Function Calling）｜让 LLM 从纯文本生成器变成能执行操作的系统｜四步：声明工具→模型决定→结果追加→模型继续；模型决定"要不要、调哪个、传什么参数"｜开发者只需定义和执行工具｜L79-101
- **五类工具**｜系统化讨论工具｜感知/执行/协作/事件触发（外部输入驱动 Agent，不是 Agent 主动调）/用户沟通｜第四章展开｜L65-77
- **通用 vs 专用工具原则**｜通用能力强但扩大出错和攻击面，专用工具受约束｜通用基础能力用于组合探索，专用用于高风险和强业务规则｜计算器→受限 Python（沙盒、默认无网络、限定目录、时间/CPU/内存/输出上限）；支付/删除/邮件/部署封装为专用工具+预览+确认｜L103-107
- **内部思考**（Reasoning）｜在不改变环境的前提下提升行动质量｜行动前先规划推演，依赖预训练里沉淀的逻辑规则｜绝大多数 Agent 需选支持思考的模型｜L113；L367
- **模型即 Agent**（Model as Agent）｜后训练（RL）把工具调用决策内化｜**RL 写进参数的是决策**，工具实现和执行仍在框架/服务端｜编排循环没消失，只是决策权交给模型；循环跑在哪取决于接入方式（Responses API 服务端闭环；Kimi 路径客户端仍驱动 `while` 循环）｜L115-119；实验 1-2 L237-245
- **Harness**（马具）｜模型强大但不可预测，需要把能力引导成可靠任务执行｜Agent 边界内、模型之外的运行与治理层：上下文管理+工具接口+约束+验证+纠正｜模型越强越要它；模型每内化一层它就卸下一层、转去兜底新的能力前沿｜L117-121；L263-319
- **约束 / 验证 / 纠正**｜让 Agent"不做错事"｜约束=故障安全默认值；验证=自动判对错、只看结构化数据；纠正=自动修正或回退、确认无法恢复前不暴露中间态｜Claude Code 的权限分类、熔断器、错误恢复、多层上下文压缩即属此类｜L285-317
- **熔断器**（Circuit Breaker）｜错误连续发生时继续重试会放大问题｜像保险丝，连续失败自动"断电"停止重试，转人工｜属于纠正｜L287；L316
- **上下文五部分 / 静态前缀 + 轨迹**｜要拆开才能做消融和缓存｜系统提示词+工具定义=静态前缀；用户消息+模型回复+工具结果=动态轨迹；上下文=静态前缀+轨迹｜每次调用拼接；只增不改的设计纪律从这里引出｜L139-147；L167
- **消融实验**（Ablation Study）｜验证"每个组件都不可或缺"需要实测｜逐一去掉组件看系统表现｜得到的是组件的不等价排序，而非"都重要"；换新模型结论可能变｜L149-159
- **ReAct / 轨迹**｜串联 LLM、上下文、工具的机制｜想→做→看循环；轨迹是积累的消息历史｜轨迹结构化便于解释调试；大量轨迹可分析、沉淀知识库、用于 RL｜L163-232
- **工作流（Workflow）**｜需要严格流程控制与安全｜预定义代码路径，LLM 只在节点内理解生成｜付款前不能预订等规则由代码强制；缺变通｜L384-399
- **适配层**｜工具/模型的能力短板需要补丁｜给工具（或模型）补短板的 Harness 代码，如提示词改写｜会随模型变强被内化，是模型"吃掉"Harness 的典型对象｜L406；L416
- **自主 Agent**｜工作流缺变通｜路径由环境反馈实时决定，本质是循环中用工具的 LLM｜必须设停止条件；需沙盒、护栏、人机检查点｜L420-432
- **ACI / 防呆**（Agent-Computer Interface / Poka-yoke）｜模型与工具之间唯一的沟通通道就是接口，模糊接口被模型放大成系统性错误｜从 Agent 视角设计接口，命名参数直观，易误用处在设计上让错误无法发生｜SIM 卡缺角、微波炉门不关不加热（丰田生产体系）｜L349
- **护栏三层**｜单道防线不足｜上下文层/执行层/数据层，按被绕过的难度排序｜上下文层管看到什么，执行层管能做什么，数据层管世界最终被改成什么样｜L466-488
- **人工干预**｜无法完成或高风险时平稳移交｜失败阈值或高风险操作触发｜客服升级人工、Coding Agent 交回开发者｜L490-502
- **工程范式五阶段**｜说明竞争优势为何转移｜提示→上下文→Harness→Loop→Graph，层层包含｜Loop 工程管跨轮次持续自主运转（谁发现下一件事、何时验证、何时算完成）；Graph 工程把 Agent 循环、确定性程序、人工审批组织成显式执行图｜L321-337
- **五个设计模式**｜后面章节反复使用｜见链 D｜见链 D｜L525-537

## 关卡候选

约定：事故必须由**关卡自己的虚构数据和脚本化工具**触发，不依赖模型已有的常识；"模型会不会编造/跳步"不能靠真实模型的随机表现，要由关卡引擎保证可复现（例如受控的模拟模型或固定种子的失败注入）。

| 任务 | 事故（玩家看得见的失败） | 被逼出来的零件 | 对应因果链节点 |
|---|---|---|---|
| 1. 汇率汇总：按虚构汇率表，算四个季度的外币收入总和与季均 | 没有工具定义时，Agent 仍交出一份格式工整、语气笃定的报告，数字却来自参数记忆，与虚构汇率表对不上（"给出了回答≠完成了任务"） | 工具定义（`convert_currency`、代码解释器） | A1, A7 |
| 2. 工具结果不回流：同一个汇率查询工具返回结果，但没有进入上下文 | Agent 盲目重复调用同一工具，直到耗尽迭代预算，仍无答案 | 工具执行结果追加到轨迹（ReAct 闭环）+ 最大轮数/停止条件 | A7, A8, B3 |
| 3. 健忘的 Agent：多步任务中每一轮都重新开始，不带上历史消息 | 重复执行已完成的操作（如对同一客户重复提交同一份申请），重复犯同样的错 | 历史消息/轨迹（上下文 = 静态前缀 + 轨迹） | A6, A7, A8 |

## 容易讲错的地方

- **公式不含 Environment**：Agent = LLM + 上下文 + 工具 只描述 Agent 边界之内；Environment 是交互的另一方（L13）。
- **Harness 不是"模型之外的一切"**：而是"Agent 边界内、模型之外"；工具定义/适配器/沙箱权限与重置机制属于 Harness，沙箱内的文件进程、数据库、网页、用户属于 Environment；即使仿真环境与 Agent 同进程，它仍是 Environment（L279）。
- **RL 内化的是决策，不是工具执行**：何时调、调哪个、传什么参数；`web_search`/`code_runner` 的真实实现仍在模型之外（L241，作者致谢读者在 GitHub Issue #30 指出这一区分）。
- **"模型即 Agent"≠框架不重要**：作者论证的方向是反的——模型越强，Harness 越关键（L117-119）。
- **Bitter Lesson 的立场**：方向认同（模型会持续吃掉 Harness），节奏务实（训练以月计，业务约束无法一次内化）；Harness 工程是教训在工程时间尺度上的实践，不是对它的抵抗（L121）。
- **缺工具定义不等于拒绝或沉默**：模型会照样给出格式一模一样的答案，数据来自参数记忆；是坦白拒绝还是编造取决于模型自身幻觉率与诚实度，"不得自行估计"类提示只能降低概率（L157）。
- **"给出了回答"不等于"完成了任务"**：上下文残缺时典型失败不是报错退出，而是一个毫无破绽的答案（L159）。
- **不要笼统说"每个组件都不可或缺"**：组件并不等价，标准是信息能否从别处重建；而且模型迭代快，同一消融换新模型结论可能不同（L159）。
- **思考过程可丢**：因为它可以从工具结果重建，丢掉几乎没有代价（L157）。这是消融实验在其设定下的结论，作者同时提醒换模型要重测。
- **通用工具并不总优于专用工具**：高风险与强业务约束操作应封装为专用工具（L107）。
- **Harness 重要≠越复杂越好**：Manus 的"Less structure, more intelligence"；复杂拓扑固定，遇例外只会加节点（L378-380）。
- **工程范式五阶段是层层包含而非替代**，单个 Agent 循环正是执行图里的一个节点（L337）。
- **两个公式不是两套骨架**：全书骨架只有 Agent = LLM + 上下文 + 工具；Agent = Model + Harness 是它在生产形态下的展开，仅是"构建"部分内部的观察视角，不是十章目录（L508）。第六章不属于五要素任何一项，它扩展的是观察与动作空间本身的模态与时机（L519）。
- **三层护栏是按被绕过的难度排序，不是请求处理的先后顺序**（L476）。
- **上下文层的结构性上限**：同一上下文里的 Agent 难判断自己是否被注入，只能降低成功率、给不出保证（L484）；因此执行层复核必须在上下文之外（L486）。
- **安全检查只看结构化数据**，不看模型自由生成的文本，因为后者可能已被提示注入操纵（L286）。
- **护栏也有误拒绝**，评估要两头测（L472）。
- **自由格式工具调用只是 API 参数格式的演进**（JSON→原始文本），不是模型架构革新；客户端循环逻辑不变（L249）。
- **事件触发工具不是 Agent 主动调用的**，是外部输入驱动 Agent 开始任务（L73）。
- **选型不要只看榜单**：要在自己的任务上评估；模型有某能力不代表承载它的产品允许调用；同一任务在聊天产品/Coding Agent/API 里结果可能不同（L361；L365）。
- **推荐顺序**：先优化提示词，再考虑工作流，最后才引入自主 Agent，是降低意外风险最实用的顺序（L551）。
