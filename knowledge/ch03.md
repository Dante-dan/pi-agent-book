# 第 3 章 用户记忆和知识库

出处行号均指 `book/chapter3.md`（共 698 行，已从头到尾通读）。

## 一句话主旨
第 2 章管的是「单次会话内」的上下文；本章让 Agent 在会话结束后仍记得用户（用户记忆，个体尺度）、记得领域知识（知识库，群体尺度）。两者共用向量检索与知识压缩，也面临同样的三个麻烦：信息冲突、知识过期、检索不准（§开篇 L3–9）。章末两条线汇合：把知识库的检索技术反过来用到用户记忆上，得到「Advanced JSON Cards 常驻 + 上下文感知检索按需」的双层记忆（§实验3-11 后 L635）。

## 起点问题
- 接第 2 章：上下文窗口只在当前会话有效，对话一结束一切归零。本章要解决「跨会话记住用户、记住知识」（L3）。
- 作者在开篇就点明全章结构：先做用户记忆，再讲知识库 RAG，最后「反过来」把 RAG 用到用户记忆（L9、L426、L575）。

## 因果链

**阅读提示**：本章不是一条直线。主链 A（L15–241）是用户记忆内部的递进，结尾以「记忆多了找不到」接到主链 B（RAG，L243 起）。B 之后的「结构化索引 / OpenViking / 更新 / 智能体化 RAG / 上下文感知检索」按原书自己的说法「并非一条严格递进的阶梯，而是围绕如何组织与检索知识从不同侧面展开」（L428），所以我把其中确有因果的几步串成链 B2，其余并列项放在「并列支线」里。链首尾相接处我在表后注明。

| B1 | 模型训练数据有截止日期，知识库可随时更新；记忆/知识太多无法全放进上下文 | **RAG**：检索器从知识库找相关片段，生成器（LLM）基于片段回答。例：用户问「我买的东西想退款，流程是什么」，`retriever.search("退款流程", top_k=2)` 取回退款政策+操作步骤两段，再生成答案。核心三步：检索 → 注入上下文 → 基于上下文生成 | 长文档怎么变成「能被检索的单元」？ | §RAG 基础 L243–264 |
| B2 | 整篇文档只压成一个向量：多个主题混在一起，向量表达不了任何一个；且嵌入模型有输入长度上限；片段过大还连带注入无关内容，浪费窗口、稀释注意力（与前面 Enhanced Notes「段落越长越抓不住重点」同源） | **分块（Chunking）**：①固定大小（如 512 token，重叠 50–100 token；简单但拦腰截断段落/代码/表格）②递归/结构感知（按标题→段落→句子降级，生产最常用）③语义切分（在相邻句嵌入相似度骤降处下刀，需额外嵌入计算）。大小权衡：太小语义模糊（「该公司收入增长了 3%」哪家公司？哪个季度？），太大主题混杂向量被稀释。起点：256–1024 token、重叠 10%–20%，按实测调。 | **伏笔**：任何分块都会切断块与原始上下文的联系（「该公司」指谁、出自哪份报告都留在块外），后文「上下文感知检索」才正面解决（B2 的新麻烦直通 B2' 与 C5） | §文档分块 L270–284 |
| B3 | 块切好了，用什么找「语义相近」的？计算机只懂数字 | **稠密嵌入**：文本→稠密向量，语义近则向量近；用**余弦相似度**（看方向不看长度，因为文本长度不同不代表语义不同）。直觉例：「如何养猫」(0.9,0.5,0.1) 与「猫咪饲养指南」(0.8,0.6,0.1) 余弦≈0.99；与「股票投资策略」(0.1,0.1,0.9) 余弦≈0.25（L296–298 手算）。演进：Word2Vec（固定词向量，king−man+woman≈queen，但一词多义无解，如 river bank vs investment bank 同一向量）→ BERT/BGE-M3（自注意力，同一词在不同语境不同向量；BGE-M3 实际同时输出稠密/稀疏/多向量，本书只取稠密；BERT 输入上限 512 token，不适合长文本）。 | 知识库百万级时逐一算相似度太慢 | §稠密嵌入 L286–308 |
| B4 | 上百万文档逐一算相似度太慢 | **ANN（近似最近邻）索引**，实验 3-4：ANNOY（树；构建快、内存低、**不支持增量更新需重建**、精度较高；适合静态数据）vs HNSW（图；构建较慢、内存较高、支持增量但长期插入后宜定期重建、精度极高；适合需实时索引新信息的场景）。作者强调：选索引策略与选嵌入模型同样重要 | 稠密检索懂语义，但对精确词是否可靠？ | 实验 3-4 L310–330（表 3-2） |
| B5 | 稠密检索「懂语义但可能漏关键词」：搜「HTTP-403」可能只返回「服务器错误」的泛泛讨论 | **稀疏检索**：词袋模型（只看出现哪些词、几次，忽略词序；「猫追狗」=「狗追猫」）。**TF-IDF**：词在本文档越多、全库越少见越重要（100 篇里 60 篇含「模型」、仅 3 篇含「蒸馏」，后者更有区分度）；缺陷：词频线性增长（出现 10 次是 5 次的两倍）、不校正文档长度（长文档靠字多得高分）。**BM25**：保留 IDF，加**词频饱和**（k1 控制）与**长度归一化**（b 控制）；其 IDF 写法不同于 TF-IDF，ln((N−df+0.5)/(df+0.5))，代价是 df>N/2 时为负，实现中通常设下限。**倒排索引**（词→文档，像书后术语索引） | 稀疏只认字面：「kitty」找不到只写「cat」的文档 | §稀疏嵌入 L332–358 |
| B6 | 需要观察 BM25 内部怎么算，才能理解它对精确词强、对同义弱 | **实验 3-5 日志**（N=10 篇，k1=1.5，b=0.75，avgdl=250）。查询「模型蒸馏」：「模型」df=3，IDF=0.76，命中 doc_1(TF5,长200)贡献 1.52、doc_3(TF2,长500)贡献 0.82、doc_7(TF8,长150)贡献 1.68；「蒸馏」df=2，IDF=1.22，命中 doc_1(TF3,长200)贡献 2.15、doc_5(TF1,长250)贡献 1.22。最终排序 doc_1(3.67)>doc_7(1.68)>doc_5(1.22)>doc_3(0.82)。结论：doc_1 里「蒸馏」词频(3)低于「模型」(5)，但因更稀有，贡献(2.15)反超(1.52)；同时命中两词的文档叠加得分遥遥领先。作者总结：精确匹配在技术代码、人名上极佳，读不懂同义表达 | 两种方法盲区互补 → 都跑 | 实验 3-5 L360–383 |
| B7 | 两个引擎各有盲区；合并时得分尺度不可比：余弦 0–1，BM25 可能 0 到几十 | **混合检索三阶段**：并行检索 →融合（**RRF 倒数排名融合**：弃原始分只看排名，得分=Σ 1/(k+rank)，k 常取 60 用来压低靠前名次间的差距；简单稳健，但丢掉原始分里的相关性信号）→**神经重排序**。作者特别澄清：重排序**不是**为补救 RRF 丢的信息才加；无论怎么融合都值得加，因它换了更强的匹配范式：**跨编码器**把查询和候选拼成一段文字送入模型逐词比对，精度远高于检索阶段**双编码器**各自独立编码再比向量；对融合后候选池前 N 个（如 50）逐一精排。重排序不替代融合，是在融合产生的候选池上精排。类比：双编码器=猎头筛简历，跨编码器=面试官深谈。示例模型 BAAI/bge-reranker-v2-m3 | 流水线调优需要客观指标 | §混合检索 L385–400 |
| B8 | 多阶段流水线无法凭感觉调优 | **三个检索指标**（表 3-3）：recall@k（前 k 个里是否含正确答案的查询比例；回答「该找的找到了吗」，最贴近 RAG 需求）、MRR（第一个相关文档排名倒数的均值；第 1 得 1 分，第 10 只得 0.1）、nDCG（综合全部相关文档的排名与相关程度，后排折扣更大）。脚注：本书的 recall@k 实为命中率 hit rate，与学术标准 recall 不同，是为与 Anthropic Contextual Retrieval 的口径一致。工业界另有**检索失败率**=正确信息未出现在 top-20 的查询比例 | 验证整套流水线 | §如何度量检索质量 L402–414 |
| B9 | 想看每类查询下谁赢 | **实验 3-6** `retrieval-pipeline`：test_client.py 覆盖语义相似（kitty↔feline/cat）、精确名称、多语言、技术代码；展示每个文档在稠密排名、稀疏排名与重排序后的变化，可见重排序把「被单一方法低估但实际高度相关」的文档提到顶端。结论：**没有任何单一检索策略在所有场景下可靠**，稠密+稀疏+重排序才是生产级正确做法 | 但块之间是扁平的、互不关联，知识本身该怎么组织？ | 实验 3-6 L416–422 |

| C1 | 把原始案例/文档不加处理平铺进知识库，即使检索技术再好也不保证召回全部相关信息，模型基于不完整上下文做错判断。**案例一（黑猫白猫计数）**：知识库 100 个独立案例文档（90 黑 10 白），问「比例是多少」，受 top-k（如 20）限制，大部分案例根本检不到，模型只看到如 15 黑 3 白就给出错误比例（第 2 章用过同一例子说明「注意力是软检索」，装满 100 个也难精确计数，RAG 下更糟）。**案例二（Xfinity 优惠）**：知识库是几百条客服工单，各记一次个案结论（退伍军人 John 通过、医生 Sarah 拿到折扣、教师 Mike 不符合），没有任何一条写资格范围本身。护士来问能不能享受时三重障碍：①**最近邻偏置**（护士与医生语义最近，Sarah 排前则推断可以；若 Mike 碰巧排前则得到相反答案）②**边界语义缺失**（「仅限……其他一律不适用」这种全称+否定不存在于任何单条工单，调大 k 也解决不了）③**完整性信号缺失**（模型无从判断自己看全没有，所以不追问，直接自信作答） | **索引期提炼**：离线通读全库，把「100 个个体」压成统计摘要「共 100 只猫：90 黑(90%)、10 白(10%)」，把散落个案提炼成带边界的规则卡「Xfinity 优惠适用于现役与退伍军人、持证医护人员（含护士）；教师等其他职业不适用」。作者结论：未经提炼和结构化的知识，无论存向量库、检索注入还是塞长上下文，模型都无法可靠利用，必须在索引阶段投入计算 | 提炼/结构化具体有哪些做法？ | §超越扁平文本 引言 L424–443 |
| C2 | 需要在索引期组织知识 | **结构化索引**（索引前先用 LLM 归纳、抽象、建关联）。两条路并列：**RAPTOR**（递归抽象，切块为叶子→聚类→LLM 为每组生成父节点摘要→递归成树；例：SSE2 支持 128 位整数运算、SSE4.1 新增字符串比较指令聚到一组，生成父节点「x86 SIMD 指令集的各代演进」；可在多抽象层次检索）与 **GraphRAG**（LLM 抽实体与关系成三元组，社区发现算法找紧密集群并生成摘要）。图的两大优势：①**多跳推理**（「我的医生所在医院的地址」要走 用户→医生→医院→地址；扁平存储要么多次独立检索再让 LLM 拼接、易断链，要么无法表达）②**实体消歧**（区别于词义消歧 WSD：「bank」河岸/银行靠上下文嵌入即可；而两位同名「张医生」是实体消歧，需维护实体本身的知识；图里张医生-A(科室,牙科) 与张医生-B(科室,心脏科) 是不同节点，消歧成为图的原生能力，回应 A4 里 Advanced JSON Cards 靠 person/relationship 人工字段做的事） | 知识图谱作为用户记忆的**通用**存储有固有局限 | §结构化索引 L445–466 |
| C3 | 三元组化造成**语义降级**：「如果下周还下雨，我就取消去海边的计划，改去博物馆」被拆成（我,有计划,海滩旅行）（我,有备选计划,博物馆旅行），条件逻辑与时间依赖全丢；三元组抽取错误还会造成知识污染 | **分层互补**：以完整自然语言保存核心信息，辅以结构化元数据做索引；医疗问诊、法律案件、家族关系等需多跳/精确消歧的垂直场景才把图谱作专项索引。实验 3-7（`structured-index`，英特尔 CPU 架构手册数千页）：查「请解释 SSE 指令集」，RAPTOR 先在高层摘要定位「SIMD 指令集」再向下钻到 SSE 细节；GraphRAG 定位「SSE」实体后沿边找到 XMM 寄存器、浮点运算、ADDPS 等指令，并借社区信息给出在 CPU 架构中的位置。前者适合「由概念钻进细节」，后者适合「A 和 B 什么关系」，组合通常好于单选。何时需要：只是「找到含某信息的片段」（退款政策是什么）用混合检索就够；需跨文档综合（SSE 与 AVX 架构差异）或多层导航才值得；代价是索引与查询都要多次 LLM 调用，成本延迟显著上升 | 学术路线重；有没有更轻量、人和 Agent 都能直接读写的组织方式？ | L468–480 |
| C4 | RAPTOR/GraphRAG 偏重；知识若只是一堆孤立文本文件，除全文扫描或向量检索外 Agent 无从导航，知识越多越难找 | **文件系统范式（OpenViking，字节跳动火山引擎开源）**：所有上下文（记忆/资源/技能）映射为虚拟文件系统，每条有 `viking://` URI（目录：resources/、user/memories/、agent/skills、agent/memories）。**L0/L1/L2 三层按需加载**：L0 约 100 token 一句话摘要（判断相关性）、L1 约 2000 token 概览（供规划决策）、L2 全文；每目录自动有 `.abstract`(L0) 和 `.overview`(L1)；L0 判无关就不加载 L1/L2，大部分查询到 L1 即可决策。思路与第 2 章 Skills 渐进式披露如出一辙。选 Markdown 纯文本而非专用库：人可直接读写、Git 版本控制与回滚、Agent 有 write_file 即可在工作分支自主记录再经审核合入。会话结束可提议把用户偏好写入 user/memories/；写入 agent/memories/ 的操作记录**不能直接当可靠经验**，需结果评价、跨轨迹归纳、后续验证才成为第 9 章的经验学习 | 纯文本文件还需「横向链接」才能导航 | §文件系统范式 L482–499 |
| C5 | 文件间无交叉引用时，知识越多越难检索 | **像 Wikipedia 一样组织**：条目提及其他条目时加链接，辅以入口页和索引页，Agent 顺链接导航——相当于用轻量链接实现 GraphRAG 的一部分导航能力。作者强调**不同模型主动建链意愿不同**：强模型写新知识时自发回指已有条目、维护索引，不少模型只会孤立追加文件；所以写入提示词必须写明：每新增条目先检索并链接相关已有条目，更新所在目录索引，形成双向可达引用网 | 知识会持续进来：怎么改才安全？ | L501–503 |
| C6 | 上线后新信息持续进入：只追加不整理会越积越乱，只定期重写则新信息无法及时生效 | **两条更新路径**。**增量更新（事件触发）**：把知识库当代码库，每次变更是一个 PR；Markdown 知识库/用户记忆文件/规则文档也进 Git（差异审查、版本历史、责任追溯、一键回滚）；沿用第 1 章「提议者—审核者」：Proposer Agent 先检索相关旧知识再提最小而完整的 diff（增/删/改，维护链接、索引、时间元数据、证据引用），不是把最新对话粗暴追加到末尾；Reviewer Agent 拿「变更前知识+diff+原始证据」独立核查是否有证据支持、有没有遗漏限定条件、是否与别处冲突、删改是否过度，拒绝时要给指向证据和行号的可执行意见；双方迭代至收敛，设最大轮数/预算，超限转人工，**不得默认放行**；CI 检查格式/链接/元数据/权限标签（知识若为代码还跑类型检查与测试）后，才从已合入版本增量重建索引。**三层分离**：原始证据层（只增不改）/ 知识层（Markdown 或代码）/ 服务层（可重建的检索索引）。Proposer/Reviewer 必须是 **Agent 而非两次固定 LLM 调用**（要自己搜相关文档、追证据、跑检查，且能查完整的被授权知识库与证据库）；优先**能力相近但来自不同家族的模型**（Claude+GPT，或 DeepSeek+Kimi）降低同类错误概率，能力不宜悬殊；权限强制分工：Proposer 只写工作分支，Reviewer 只读证据并提交审核结果，只有合并流程能改主分支和线上索引 | 局部都正确的修改累积出全局问题 | §知识应该如何更新 L505–524 |

| P1 从数据集提取隐性知识（知识发现） | 前提变了：知识不在文档里而隐含在海量结构化案例中（判例里法官如何权衡动机/伤害/自首）。两阶段：①LLM 把案情转成标准化 JSON（核心难点是 Schema）②因子分析与重要性建模，得到「判决因子重要性层次模型」。**实验 3-12**（CAIL2018 刑事判决）：自下而上的因子发现（让 LLM 分析数百样本自由列出可能影响判决的因素），得到「核心模式（自首、赔偿等）+ 按罪名的扩展模式（涉案金额、伤害等级）」；因子分析不直接让 AI 预测刑期（黑箱），而把案件转成独热编码（盗窃=[1,0,0]、抢劫=[0,1,0]、诈骗=[0,0,1]，不用 1、2、3 以免算法误认「诈骗比盗窃严重 3 倍」），是非题 1/0，聚类找「案件原型」（如「轻微口角引发的徒手斗殴致人轻伤」「有预谋团伙持械围殴致人重伤」）；模型驱动 Agent 按重要性顺序追问补全判决因素，再检索最相似原型，用其统计（典型刑期范围）给出有判例支撑的分析 | §从数据集中提取深度知识 L637–663 |
| P2 多模态记忆（前沿，文本记忆无法存人脸/声音） | 思路一：存原始图片+文本描述并在 Markdown 引用；思路二：把嵌入存在上下文里，每张脸/声纹仅占 1 个 token，1000 token 可容纳 1000 张脸，Agent 靠注意力在其中找最相关的；思路三：写进模型参数——每用户 fact-LoRA 直接问几乎完美复述，但一做**间接推理**就失灵（冻结骨干从没学过如何「查阅」临时挂载的适配器）；User as Engram（arXiv:2606.19172）把嵌入写入 Engram 模型空闲的哈希 N-gram 槽位、无需梯度更新，可扩展性强于思路二但要求预训练模型支持 Engram、查准率可能不如思路二 | §前沿探索 L665–675 |

## 概念清单
每项格式：**名称**（原书术语）｜为什么会有它｜它是什么｜怎么用｜出处

- **用户记忆 vs 知识库**｜Agent 需要既「懂你」又是「领域专家」｜个体尺度的个性化记忆 vs 全体共享的集体知识｜共用向量检索和压缩，共同麻烦是冲突/过期/检索不准｜L5–7
- **记忆提取三规则：选择性/抽象化/结构化**｜全存太冗余，原话不能直接用｜只留对未来有用的、归纳为长期偏好、存为可检索字段｜会话后用额外 LLM 调用｜L41
- **LoCoMo**｜需要公开基准｜长期对话记忆基准，约 300 轮、最多 35 会话，含问答（单跳/多跳/时间/开放域/对抗）、事件摘要、多模态对话生成｜参照对比｜L45
- **三层次评估框架（基础回忆/多会话检索/主动服务）**｜八项能力太平，缺少递进的难度刻度｜三个递进层级，贯穿全章（实验 3-1/3-9/3-11）｜按层出题评分｜L58–64
- **LLM-as-a-judge**｜开放式回答无法精确匹配｜用另一个 LLM 对照参考答案打分｜实验 3-1 评分｜L68

## 递进能力
- **读完本章 Agent 比第 2 章多了（按获得顺序）**：
  1. 会话后提取「选择性/抽象化/结构化」的长期记忆；
  2. 用三层次标尺评估记忆好坏；
  3. 区分轨迹/长期记忆/业务状态，并在四种格式间做取舍，必要时用可执行状态做聚合/冲突检测/约束告警；
  4. 冲突处理策略（写入时 UPDATE vs 追加并在检索时排序）与记忆压缩；
  5. 构建 RAG：分块→稠密+稀疏→RRF→重排序，并用 recall@k/MRR/nDCG 验收；
  6. 索引期提炼（摘要卡、规则卡）、RAPTOR/GraphRAG、文件系统式知识库（L0/L1/L2 + 链接）；
  7. 知识库的增量更新（PR + 异源 Reviewer）与周期性全量整理，失效下线与租户隔离；
  8. 智能体化 RAG 的多轮检索，以及 RAG 的安全边界；
  9. 上下文感知检索，并把检索反哺用户记忆，形成双层记忆。
- **依赖前面章节**：第 1 章的 ReAct、提议者—审核者模式、动态轨迹；第 2 章的上下文工程、注意力是软检索（黑猫白猫）、prompt caching、Skills 渐进式披露、来源标记、上下文感知压缩（需与本章同名概念划界）。
- **给后面章节埋的伏笔**：第 4 章（工具设计中的执行层防御、多模态信息提取先转文本）；第 6 章（业务状态、事件驱动）；第 9 章（睡眠学习=定期整理、经验学习=程序性经验，agent/memories 不能直接当可靠经验）。本章小结自己定位：本章建的是第 1 章发现循环中的「提案」段，把一条证据变成一次最小、可审查、可回滚的修改，不负责判断系统整体是否变好（L681）。

## 关卡候选
事故全部基于玩家自编的私有语料或确定性计算，不依赖大模型常识。

| 任务 | 事故（玩家看得见的失败） | 被逼出来的零件 | 对应因果链节点 |
|---|---|---|---|
| T1 「明天再问我」：新会话里问「我上次订的航班/会员号是多少」 | 纯上下文 Agent 回答不知道；全存原话又无法检索且塞爆窗口 | 会话后提取器（选择性/抽象化/结构化）+ 用户长期记忆工具 | A1、A3 |
| T2 同名张医生 + 两辆车：用户说「帮我约张医生」「预约我的车保养」 | Simple Notes 存「张医生-牙科」「张医生-心脏科」两条互不关联的事实，Agent 随便挑一个；或默认猜一辆车 | Advanced JSON Cards（person/relationship/backstory），Agent 追问是哪位/哪辆 | A4、C11 |
| T3 搬家冲突：先说「住北京」，再说「搬到上海」，之后问「我之前住哪」或在用户其实只是「计划」搬家时 | v2 式 UPDATE 把「北京」覆盖，历史不可恢复；错误 UPDATE 无法回滚 | 仅追加（带时间）+ 检索时按时间排序 | A7 |
| T4 计数/日期类：「我今年出了几次国门」「护照够不够」 | 文本记忆让 LLM 心算，次数算错、漏掉护照 <180 天的告警 | User as Code 的聚合函数与约束检查（确定性计算） | A5 |
| T5 精确词 vs 同义词：知识库含 `HTTP-403` 的内部排障手册；另一查询用「kitty」找只写「cat」的文档（语料自编） | 仅稠密检索返回「服务器错误」泛泛讨论，漏掉含精确码的文档；仅稀疏检索找不到同义词文档 | BM25 + 稠密 + RRF（k=60）；再加重排序观察排名变化 | B5–B9 |
| T6 top-k 计数：100 个猫案例文档（90 黑 10 白），top-k=20，问比例 | 模型基于被检索到的子集给出错误比例（如 15 黑 3 白） | 索引期统计摘要卡 | C1 |
| T7 护士资格：几百条工单只记个案（医生通过、教师被拒），问「护士能享受优惠吗」 | 最近邻偏置：答案取决于哪条排前；调大 k 也不解决；模型自信不追问 | 索引期规则卡（带边界）；孤岛文件需加链接/索引页 | C1、C4、C5 |
| T8 孤立块歧义：多家公司的「收入增长了 3%」；以及三条互相矛盾的转账指令 | 检索回来的块缺来源，答成别家公司；三条转账指令孰为最终有效无法判断 | 上下文感知前缀（谁、何时、什么意图）；对照 B2 的分块缺陷 | B2、C11、C12、C13 |
| T9 多轮检索（可选）：复合法律式问题（自编小法条库：A 罪量刑、B 情节、C 累犯规则） | 单次检索缺关联信息，答案遗漏累犯条款；ReAct 多轮则补上 | 检索工具化（智能体化 RAG）；再叠加「检索内容含注入指令」事故 → 来源标记/高风险动作授权 | C9、C10 |

## 容易讲错的地方
1. **「记忆 = 存对话」是误解**：用户记忆不保存每句话，而是用额外 LLM 调用提取并审查；轨迹是 append-only 的流水账，长期记忆是会被反复改写、合并、淘汰的档案（L17、L80）。
2. **「只增不改」是指原始记录，不是发给模型的 Context**；Context 可压缩重组（L78）。**轨迹≠工作记忆**：前者不可变完整序列，后者是按相关性裁剪的动态子集（L217）。
3. **三套分类（层次/格式/认知类型）是正交的**，不是一条链（表 3-1，L180–190）。
4. **Mem0 的方向是反转的**：不是越早消歧越好；v3 改成追加+检索时推理，原因是错误 UPDATE/DELETE 不可逆丢历史（L196–204）。Mem0-g 现应视为历史设计，别再当现行方案讲。
5. **「记忆能力八项」是作者自己的归纳口径，不是某基准原始分类**（L47）；记忆三层次框架是作者自设计的（L58）。
6. **recall@k 在本书是命中率（hit rate）**，非学术标准 recall；跨来源比较要小心（L412）。
7. **重排序不是为了补救 RRF 丢失的得分才存在**，而是换了更强的匹配范式（跨编码器），无论怎么融合都值得加；且重排序不替代融合，在融合产生的候选池上精排（L398）。
8. **余弦看方向不看长度**（L292）；BM25 的 IDF 与 TF-IDF 的 IDF 不是同一公式，且 df>N/2 时为负，实现要设下限（L348–352）。
9. **没有单一检索策略在所有场景下可靠**，是实验 3-6 的明确结论（L422）。
10. **调大 top-k 不能解决「边界语义缺失」**（L438）；仅靠检索无法补完整性信号——必须在索引期提炼（L443）。
11. **结构化索引不是默认选择**：混合检索已覆盖大多数需求；结构化索引成本（多次 LLM 调用）与延迟显著上升（L480）。**GraphRAG 不适合做用户记忆的通用存储**（语义降级），推荐「自然语言为主+结构化元数据为辅」分层互补（L468–470）。
12. **词义消歧（bank）≠ 实体消歧（两位张医生）**：前者靠上下文嵌入，后者需要维护实体知识（L464）。
13. **文件系统范式的前提是文件间必须有链接与索引**，否则知识越多越难找；而且**不同模型主动建链的意愿不同**，提示词必须写明（L501–503）。
14. **agent/memories 里的操作记录不能直接当可靠经验**，需结果评价、跨轨迹归纳、后续验证才算第 9 章的经验学习（L499）。
15. **知识更新必须走 Proposer/Reviewer，且二者必须是 Agent 而不是两次固定 LLM 调用**；优先异源模型；Reviewer 核对证据和 diff，不是顺着 Proposer 的结论再讲一遍；超限转人工，**不得默认放行**（L522–524、L517）。
16. **定期整理不能只在已有摘要间相互改写**（早期误读会代代传），必须回原始数据；冲突不是「保留最新」，而是 qualification（场景限定），证据不足就保留冲突与待确认状态（L533–534）。
17. **权限过滤必须下推到检索层**：越权内容一进 LLM 上下文就难保证不泄露（L540）。
18. **检索内容可以影响措辞，但不应直接触发有副作用的动作**（L556）。
19. **上下文感知检索与第 2 章「上下文感知压缩」名字相近但相反**：前者索引期、对知识库文本块做加法；后者运行期、对对话历史做减法（L604）。作者还特别说明它**不是**架在智能体化 RAG 之上的更高一层，而是回头修补最基础的分块环节（L428）。
20. **主动服务最难**，因为需要「全局概览（常驻）+精确细节（检索）」两种视角，单靠一种都会失败（L635）。
21. **fact-LoRA 能背事实但不会间接推理**：把事实存进去与让模型知道何时取用是两回事（L673）。
22. **原书自己说「并非严格递进」**：「超越扁平文本」下的六个主题（结构化索引、OpenViking、更新、智能体化 RAG、上下文感知检索、结构化数据集提取）是并列展开，设计关卡时不要强行串成一条梯子（L428）。
