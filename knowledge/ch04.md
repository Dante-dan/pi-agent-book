# 第 4 章 工具

> 行号均指 `book/chapter4.md`（全文 449 行，已通读）。

## 一句话主旨
工具设计决定 Agent 的能力上限：先决定能力做成什么形态（默认偏通用，四种情形退回专用）、怎么描述、参数怎么忠实传递；再决定怎么分发（MCP / Skill Hub）和一次让模型看见多少；最后按感知、执行、协作三类各讲设计重点（L431）。

## 起点问题
第一章列了五类工具（感知、执行、协作、事件触发、用户沟通）。本章要回答：这些工具具体怎么设计，才不会让模型选错、传错、做错，也不会把上下文撑爆。事件触发和用户沟通两类依赖异步运行时，明确推到第六章，本章只讲 Agent 主动调用的前三类（L5, L32）。章末抛给下一章的问题：Agent 能不能写代码来“创造”工具（L441）。

## 因果链

本章是“两条主链 + 三条并列的分类展开”，不是一条直线。作者在 L5、L47、L135 反复强调：“能力做成什么形态”和“一次看见多少条能力”是两个彼此独立的决策，只隔一节生态，因为生态把接入成本压到一条命令，才有了“太多”的问题。

### 链 A：通用设计原则（L34–L131，对所有工具成立）

| # | 上一步在哪儿翻车 | 被逼出来的概念/方案 | 它又留下什么新麻烦 | 原书出处 |
|---|---|---|---|---|
| A1 | 早期把每个 API 端点包成一个工具，粒度过细，Agent 要协调好几个工具才完成一个目标 | **ACI**：工具对应 Agent 的目标而非底层 API 操作，对 Agent 友好而非对人友好 | 那“能力”到底用什么形态表达？专用工具还是别的 | §工具设计的通用原则 L36 |
| A2 | 每个专用工具的 schema 要占数百 token，工具一多就堆积；能力还得写代码才能改 | **专用—通用谱系**：专用工具 ↔ Skill（目录里几十 token，正文用时才读）；默认通用优于专用（code_interpreter 代替计算器；`read_document` + `file_type` 代替三个 extract_*），整合看功能相似性与场景重叠度 | 通用并非处处好，什么时候该退回专用 | §能力的表达形式 L38–L51 |
| A3 | 通用执行器开放太大：生产库写操作无法精细授权审计；各平台 grep/find 语法不同；高频操作；参数结构复杂 | **四种退回专用的情形**：安全权限审计、屏蔽平台差异给更好反馈、使用频率极高、参数结构复杂 | 参数复杂这条为什么特别重要 | L53 |
| A4 | Skill 全靠自然语言，模型要自己拼命令行并转义引号，规则比 JSON 复杂且因 shell 而异，参数复杂时更易出错 | 折中：让 Agent 把复杂结构化参数写进 JSON 文件再在命令行引用；同时承认 Skill 的优点：人人可写，局部错误不会“牵一发而动全身”（schema 引号花括号不配对会让整个 Agent 报错） | 综合起来该用什么标准决定形态 | L55–L57 |
| A5 | 形态选择缺判据 | **四个决策维度**：安全与权限、参数复杂度、变更频率（常变的用 Skill）、模型能力（强模型可用 Skill + 通用执行器，弱模型要 schema 引导） | 一次一个工具调用、每个中间结果都进上下文很浪费 | L59–L64 |
| A6 | 逐个调用工具、每步结果都搬进上下文，token 消耗大 | **代码编排工具调用**：LLM 一次写脚本，中间变量留在执行环境，只回传最终结果；抓多个网页批量提字段可省约两个数量级 token（作者原话为“约”）。深入留给第五章 | 工具有了，模型怎么知道何时用、怎么用 | L68 |
| A7 | 大多数调用失败不是模型不知道工具能做什么，而是不知道不能做什么；复杂任务里模型只能分出一小部分注意力核对参数格式 | **工具描述的艺术**：写“什么时候用”；写边界与反例；参数用具体例子代替抽象规范（E.164 例子）；写返回值与耗时代价；附 1–5 个真实调用示例（某些基准 72%→90%，作者注明因任务而异）；选错工具先查描述，不要先怀疑模型 | 描述写得再好，工具自己改了参数怎么办 | §工具描述的艺术 L72–L86 |
| A8 | 工具层悄悄改写输入（弯引号→直引号）或追加参数（git commit 自动加标记参数），模型反复失败却无法自行诊断 | **参数传递保真性**：模型感知的世界与工具操作的世界不能有系统性偏差；必须规范化时要在描述里说明并在返回里告知 | 工具定义各框架格式不同，开发者要重复适配 | §参数传递的保真性 L90–L98 |
| A9 | OpenAI、Anthropic、LangChain 工具格式各异，开发者重复适配 | **MCP**（2024 年底，Anthropic 发布）：客户端-服务器；JSON Schema 描述；stdio / Streamable HTTP；工具 / 资源 / 提示三类原语；“一次开发，处处可用” | 工具怎么分发，怎么不全量吃上下文，安全吗 | §工具生态 L102–L114 |
| A10 | MCP 只管专用工具的接入，Skill 就是个装 `SKILL.md` 的文件夹，不需要协议 | **Skill Hub / 注册表**：skills.sh（Vercel，2026-01）一条 `npx skills add` 安装；ClawHub。两条渠道都把接入成本压到一条命令 | 成本和风险各自如何 | L116–L121 |
| A11 | 引入第三方能力等于把一段不受控文本放进上下文，还可能交出凭证 | **三类 MCP 风险**：工具描述投毒、恶意或被劫持的服务器（供应链）、同名工具遮蔽；缓解：审查描述、锁版本、最小权限凭证；带脚本的 Skill 多出一类（任意代码）风险，但作者明说不是“Skill 一定更危险” | 能力接入越容易，数量越多 → 下一条链 | L123–L131 |

### 链 B：工具太多怎么办（L133–L216，A11 之后换话题：从“怎么表达与分发”转到“一次暴露多少”）

|---|---|---|---|---|
| B1 | 工具上百个后即使最先进的模型也易选错；平铺吃 token；每次工具集变动都击穿 KV Cache | 三层答案由“按需”程度递增：层次化组织与按需加载 → 主动工具发现 → Skills | 先看最朴素的一层 | §工具太多怎么办 L135–L137 |
| B2 | 仅 5 个 MCP 服务器就可能有数万 token 的定义，200K 窗口未开始对话就用掉近三成 | **按需加载只暴露索引**：Cursor 把工具描述同步到文件夹，Agent 默认只看名称索引，A/B 测试 token 降 46.9%；Pi Coding Agent 核心刻意不内置 MCP（CLI + README + Skills），`pi-mcp-adapter` 只给一个约 200 token 的代理工具（搜索→看定义→调用）。结论：是否用 MCP 与是否开局暴露全部定义是两个独立决策 | 上百个工具时扁平列表仍然难选 | L141–L146 |
| B3 | 扁平列表在上百工具时难选 | **层次化组织**（搜索 / 读取 / 解析 / 查询，在系统提示词中说明分类）；**检索式预筛选**（语义相似度先筛候选；Anthropic 实验 Opus 4 准确率 49%→74%） | 预筛选只按初始查询做一次性匹配，“Debug the file”这类请求会牵出事先无法预见的多步工具链 | L148–L157, L161 |
| B4 | 一次性匹配无法预见任务中途冒出的需求 | **主动工具发现**：Agent 发现缺口时用自然语言声明需求，系统匹配注入。MCP-Zero：系统提示词不放任何 schema，服务器级→工具级两层语义路由，约 2800 个工具省约 98% token；工程上等价于“工具搜索工具”（Claude API 的 Tool Search Tool）。匹配低于阈值要明确返回“未找到”，由 Agent 改写、手工实现或创造工具（第九章） | 动态加载工具会破坏 KV Cache | L163–L171 |
| B5 | 若工具定义在静态前缀，每加载一个新工具整段缓存失效 | 把新工具完整 schema 追加到上下文末尾，固定在轨迹原位置；OpenAI `tool_search` / `defer_loading`、Anthropic `tool_reference`、Codex CLI 默认开启。真正导致重算的只有两种：TTL 过期，或修改/移除/重排已加载工具集。“工具定义必须在最前面”不再是铁律，代价是模型后训练要学会读散落各处的定义 | 整套机制（离线嵌入索引、缓存、弱模型训练）工程繁琐，前提是每个工具都是“面向模型的正式定义” | L173–L185 |
| B6 | 上述基础设施太重 | **Skills 作为按需查阅**：渐进式披露内建为默认形态，启动只看每个 skill 的 name + description（数百 token），用到才读 sub-skill 与脚本；类比人查工具书而非通读维基。专用工具要达到同样效果须另建一层；Skill 与 MCP 并非隔离，MCP 官方在推动 skill 经 MCP 分发 | 通用问题讲完，转入三类工具各自的设计 | §Skills L204–L216 |

| D4 | 事后让第二个模型重读同样内容会共享盲区 | **事后验证的要诀是模态切换**：代码生成的文档渲染成图再看排版；改配置后在沙盒真跑 | 前两者管“操作前/后”，管不了“执行时”实时校验 | L296 |

## 概念清单
- **ACI**（Agent-Computer Interface）｜早期 API 封装粒度过细｜对标 HCI，工具应对应 Agent 目标而非 API 操作｜本章三条通用原则（形态、描述、保真）都是它的展开｜L36
- **专用工具 vs Skill**｜专用工具 schema 占数百 token、参数受约束；Skill 目录只占几十 token、人人可写｜谱系两端，默认偏通用，除非有明确的安全/权限/性能理由｜按四个维度决策｜L38–L64
- **通用执行器 / code_interpreter**｜LLM 本身会写代码，不要限制它｜一个解释器代替数十个专用工具，还能处理没预想的边缘场景｜同时是“代码编排工具调用”的基础｜L49, L68
- **代码编排工具调用**｜逐步调用会把每个中间结果搬进上下文｜LLM 一次写脚本，中间变量留在执行环境，只返回最终结果｜抓取多网页批量提取；约省两个数量级 token｜L68
- **工具描述的“边界条件”**｜失败根因是不知道工具不能做什么｜写明做不到什么、不接受什么输入，参数用具体例子，附 1–5 个调用示例｜Agent 选错工具时先查描述｜L72–L86
- **静默输入转换 / 静默参数注入**｜工具层“好心”改参数，制造模型无法自行诊断的系统性偏差｜反模式；原则是“模型感知的世界与工具操作的世界不能有系统性偏差”｜规范化必须在描述中说明并在返回中告知｜L90–L98
- **MCP**｜各框架格式不一，重复适配｜客户端-服务器协议，工具/资源/提示三原语，stdio 与 Streamable HTTP｜“一次开发，处处可用”｜L102–L114
- **Skill Hub / 注册表**｜Skill 只是文件夹，不需要协议｜skills.sh、ClawHub，一条 npx 命令安装｜接入成本压到一条命令，也扩大信任边界｜L116
- **工具描述投毒 / 恶意服务器 / 同名工具遮蔽**｜description 原样进入上下文｜MCP 三类风险；缓解为审查描述、锁版本、最小权限凭证；Sidecar 为运行时最后一道防线｜L123–L129
- **按需加载（只暴露索引）**｜MCP 工具定义吃 token｜Cursor 方案 token 降 46.9%；Pi 的 `pi-mcp-adapter` 约 200 token 代理工具｜“是否用 MCP”与“是否全量暴露”是两个决策｜L141–L146
- **层次化组织与检索式预筛选**｜上百工具平铺难选｜按信息源性质分类；按语义相似度先筛候选；Opus 4 准确率 49%→74%｜L148–L157
- **主动工具发现 / MCP-Zero / Tool Search Tool**｜一次性匹配无法预见中途需求｜Agent 声明缺口，系统两层语义路由匹配注入；约 2800 工具省约 98% token｜低于阈值要返回“未找到”｜L161–L171
- **动态加载与 KV Cache**｜工具在静态前缀则每加一个就失效｜新 schema 追加到末尾并固定在原位置｜只有 TTL 过期与改动已加载工具集会重算；代价是模型须学会读散落各处的定义｜L177–L183
- **渐进式披露（工具侧）**｜嵌入索引等基础设施繁琐｜Skills 把它内建为默认形态，启动仅 name + description｜类比查工具书｜L204–L210
- **感知工具的接口设计**｜输出量超出处理能力｜搜索返回结构化候选 + 分页；read 用 offset/limit；显式标示截断；只读所以可缓存可并行｜L222–L228
- **原生多模态 / 提取为文本 / 工具化多模态分析**｜不同模型能力与 token 成本不同｜见链 C 的递进｜按内容类型选择（纯文字用文本提取，布局敏感保留图像）｜L230, L246–L262
- **输入验证 + 权限控制（黑名单）**｜执行工具错误代价高｜快速失败、路径遍历与命令注入检查、目录限制、黑名单（仅最基础层）｜L278–L280
- **提议者-审核者（事前审批 / 事后验证）**｜单一模型决策可能错｜异家族、能力相近；拒绝理由进轨迹；事后验证靠模态切换｜用于不可逆操作：收费、发邮件、改关键配置、创建外部资源｜L282–L296
- **Sidecar**｜需要执行时实时门控且不拖慢｜并行轻量 LLM，只读结构化工具调用字段，拒绝熔断器｜也用于筛记忆、摘要工具输出｜L298–L326
- **自动验证与反馈闭环**｜write_file 只回“成功”太晚发现错误｜写后 lint，结构化错误随返回值｜L328–L332
- **长输出截断与持久化**｜输出冗长｜头 50 + 尾 50 + 中间提示 + 落盘 + read_file 引导｜L334–L341
- **沙盒层级**｜通用执行器能跑任意代码｜进程级 → 容器 → microVM；venv 不是沙盒｜按输入可信度选择｜L343–L355
- **幂等性与预检-确认两段式**｜取消或超时后副作用不明｜唯一标识去重 / 先查后改；不可幂等的操作用两段式｜L361–L367
- **子 Agent 原语与 HITL**｜任务超出单 Agent 能力｜spawn/cancel、消息、list_agents；HITL 超时降级与反馈循环｜L386–L412

## 容易讲错的地方
- “形态”与“数量”是两个独立决策，容易混为一谈，因为 skill 目录条目比 schema 便宜一个数量级。Skill 只是把“全量常驻”的可行边界推远，并没有替你选好披露策略（L47）。
- “是否用 MCP”与“是否开局暴露所有 MCP 工具定义”也是两个独立决策；MCP 协议本身并不规定全量还是按需（L143, L206, L210）。因此“MCP 一定比 Skill 费 token”不成立，需看宿主披露策略（L121）。
- 默认取向是通用优于专用，但有四个明确的例外；作者强调 Skill 对模型要求更高，参数复杂时更易出错，折中是写 JSON 文件再导入（L49, L53, L55）。
- “Skill 一定比 MCP 危险”不是作者的结论：带脚本的 Skill 多一类风险，但纯文档型 Skill 不执行第三方代码，本地 MCP 服务器本身就是程序；按代码来源、执行位置、沙盒与审批、权限范围评估；安全扫描过的 Skill 也不保险（L131）。
- 作者强观点：当 Agent 频繁选错工具，优先检查描述，不要先怀疑模型能力；清晰列出边界比描述能力更重要（L76, L84）。
- 提议者-审核者：两个模型要来自不同家族但能力相近，Haiku 审 Opus 反而不可靠；但 Sidecar 用轻量模型是合理的，因为它判断的是简单分类，不是开放式思考（L288, L308）。
- 事后验证的要诀是模态切换，不是让第二个模型把同样内容重读一遍（L296）。
- Sidecar 不审查最终输出，而是对行为做独立判断；与流式输出并行，但对被审的那次工具调用起门控作用（L302–L304）。
- Python venv 不是沙盒，它只隔离包依赖（L345）。本地执行的实际权限取决于宿主沙盒与审批，而非“本地执行”这一事实（L349）。
- 黑名单只是最基础的防护，不应作为唯一手段（L280）。
- 动态加载并非天然破坏缓存：新 schema 追加并固定在原位置即可，真正导致重算的只有 TTL 过期与改动已加载工具集；“工具定义必须在最前面”不再是铁律（L177–L183）。
- 只读感知工具可缓存并行，但缓存键要含用户身份与授权范围、需设 TTL；并行要留意速率限制与快照不一致（L228）。
- 静默截断是危险的，要显式标示（L226）。
- 事件触发工具与用户沟通工具不在本章，放到第六章（L5, L32, L439）。
