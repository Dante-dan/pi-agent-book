# 第 7 章 Agent 的评估

（行号均指 `book/chapter7.md`，共 876 行，已全文通读。）

## 一句话主旨
构建完不等于构建正确：只有把“什么算成功、任务从哪来、谁来验证、分数如何变成决策”四个环节做成可重复的体系，Agent 的迭代、选型、后训练才有可靠方向；评估对象是“模型 + Harness 的组合体”，不只是模型（`开篇 L1–25`、`L17`）。

## 起点问题
前六章展开了单 Agent 的构建（上下文、知识、工具、代码、观察与动作空间），但开发者面对一堆没有显然正确答案的设计选择（模型、工具、知识库、记忆、提示词/Skills、Harness 约束，L5–13），只能靠直觉。缺口：怎么判断 Agent 变好了还是变差了，并且分清是“模型能力不足”还是“Harness 设计缺陷”（L17）。本章建的是第一章“发现循环”里的**证据**段（`本章小结 L856`）。

## 概念清单

- **对比实验 / 消融实验**（Ablation）｜没有度量就无法区分真提升与波动｜改一个变量看效果；逐一关闭组件看整体性能掉多少，判断组件真实贡献｜消融定位 Harness 内部哪个部件重要｜L15、L19
- **模型替换实验**（model swap）｜要分清“模型不行”还是“Harness 不行”｜固定 Harness 只换模型：换强不涨→瓶颈在 Harness；换弱大跌→主要由模型决定（原因是任务难还是 Harness 过度依赖先验，需进一步分析）｜与消融是两种不同方法｜L17–19
- **渐进式信息透露**（Progressive Information Disclosure）｜真实用户只会说“我上不了网”，多数基准一上来给完整需求｜把用户知识范围建模为独立字段 `known_info`，真正故障原因不在其中｜Agent 必须提问、引导用户查询｜L87
- **事实锚定**（Grounding）｜没有它，模拟用户会顺着 Agent 的引导确认“已解决”，评估退化成两个模型互相确认｜规定用户关于设备状态的回答必须以工具返回为依据｜写进 `task_instructions`｜L89、L258
- **双控**（Dual-Control）｜技术支持场景里很多动作本来就该由用户在自己设备上做；仅 Agent 能改环境不真实｜用户也有独立工具集（check_status_bar、toggle_airplane_mode…）；故障放在数据库不可见的一侧｜Agent 必须在用户改完后重新调用工具才能知道结果，验证因此覆盖“是否读到了用户侧结果”｜L91、L119、L260
- **Pass@k / Best@k / Pass^k**｜能力上限与业务可靠性是两个问题｜Pass@k=至少一次通过；Best@k 取连续得分最好一次；Pass^k=连续 k 次全对且无安全/合规/幻觉一票否决｜探索类（科研、漏洞挖掘）看前者，支付/退款/权限/部署看后者；有副作用的操作要在沙盒/可回滚环境采样，失败全计入｜L133–160
- **评估环境五要素**｜缺一个评估就无法构成可重复循环｜数据集、环境状态、工具接口、评分标准、执行协议｜作为对照框架分析其他基准｜L166–180
- **FAIL_TO_PASS / PASS_TO_PASS**｜只验前者可通过删断言蒙混，只验后者等于没验｜两组各证一个命题：“已修复”“未破坏”；另排除 flaky 测试｜SWE-bench Verified 的验证器｜L226
- **canary GUID**｜无法阻止泄漏，但要能发现泄漏｜每题嵌入 GUID，模型能输出即说明数据进了训练集｜Terminal-Bench｜L248
- **参数化任务模板**｜固定动作序列回放会作弊｜模板+随机参数，可固定部分参数测单一因素｜AndroidWorld、τ²｜L246、L262
- **敷衍性修复**｜“网络已恢复”边界不清，压制症状也算过｜成功条件写成可核实的“测速 excellent 才算”｜τ² 重设计之二｜L256
- **Rubric 四准则**（Scale AI）｜笼统的“好不好”无法诊断｜专家指导、全面覆盖（含陷阱 Pitfall）、按重要性加权（含 Veto）、自包含可验证｜按维度给四档具体判定+边界案例｜L312–324
- **一票否决 Veto**｜幻觉等底线问题不能被其他高分抵消，也防关键词堆砌｜触发即总分归零｜用户记忆 Rubric 的“幻觉检测”；实验中 180 次评判触发 28 次｜L320、L355–359、L394
- **长度偏差 / 位置偏差**｜评判模型偏向长回答/先出现的候选｜长度偏差三防（Rubric 惩罚冗长并设上限、配对比较先控制长度、审计分数与长度相关性）；位置偏差交换顺序各评一次，两次一致才计入｜L310、L547
- **古德哈特定律 + 多源异构评判**｜同源模型会被 Agent 钻空子，并学会躲开评判不擅长检测的错误｜不同家族多个 LLM 评判、同一 Rubric、加权或一致性聚合；部署期单模型快评、定期多源审计｜L396–404
- **失败归因**（failure attribution）｜端到端只给成败；最后一个报错多是后果｜标首个导致偏离的错误+类别+证据；记录结构化；保存任务目标/环境状态/版本/完整轨迹｜“最早且能解释后续失败”原则选主因；失败归因反映产品问题，不能完全交给 LLM｜L434–460
- **静默失败 / 首错定位两法**｜没有工具报错就没法搜关键字｜事实锚点比对（陈述 vs 工具返回，取首次背离）；轨迹前缀二分（截到第 k 步交人接手能救回，说明错在 k 之后）｜实验 7-6｜L474–476
- **轨迹前缀回归任务**｜端到端贵且无法定位｜冻结首错之前的上下文，只测下一步；答案为“可接受动作集合”+禁止动作｜对高可靠生产 Agent 往往比端到端更重要｜L515–521
- **配对分析 / 多随机种子 / 多重比较**｜小样本分差可能是噪声｜McNemar/配对 bootstrap；3–5 种子；阈值收紧或独立复跑｜“超过噪声、配对成立、可复现”才切换｜L674–696
- **预算-能力曲线**｜单点成绩外推不到长时任务｜报告性能随时间/token/调用次数的曲线｜选型要在接近真实时长的多个预算点比较｜L579
- **p95 尾部延迟**｜均值被快请求拉低，掩盖少数严重卡顿｜95% 请求不超过的延迟｜与 TTFT、思考延迟一起看｜L571
- **机制指标 vs 目标指标 / 护栏指标**｜把正在改的东西当优化目标是最常见错误｜机制=直接改的量，目标=真正关心的量，护栏=不能变差的底线｜以目标为准｜L793–795
- **仿真环境 / RLVR**｜评估要演化成训练场｜验证脚本即奖励脚本；需可靠 reset、高吞吐、随机化｜通向第八章｜L827–829

## 递进能力
- 读完本章，Agent（及其开发者）比上一章多了：
  1. 用对比/消融/模型替换把“模型问题”和“Harness 问题”分开；
  2. 把成功定义成 Pass@k 与 Pass^k 两种口径并换算；
  3. 搭可重复的评估环境（五要素，含用户模拟器与双控）；
  4. 设计能防“口头完成”的验证器、难度分层、防泄漏、持续维护评估集；
  5. 用 Rubric+LLM-as-a-Judge（含偏差防范与多源评判）评估无法写成断言的任务；
  6. 对失败轨迹做首错归因，并转成端到端/前缀回归任务；
  7. 做统计上站得住的比较、模型选型与成本拆解；
  8. 用可观测性（trace/span）把生产轨迹回流为评估资产；
  9. 用“先查评测系统、每轮只改一个变量”的闭环改进 Harness。

## 关卡候选
事故均基于本章原书给出的机制，不依赖模型本身的常识。

| 任务 | 事故（玩家看得见的失败） | 被逼出来的零件 | 对应因果链节点 |
|---|---|---|---|
| 1. 手机断网客服：Agent 查库一切正常，用户却说没信号 | 数据库返回“线路与漫游配置正常”，Agent 反复确认后宣布“已解决”，模拟用户附和；换成启用事实锚定的用户后才暴露状态栏仍显示 No Service | 用户模拟器（known_info/unknown_info 分离）+ 事实锚定 + 用户侧工具（双控） | N2 |
| 2. 退款客服 0.8 分：老板问“能上线吗？” | 同一 Agent 单次成功率 0.6，跑 5 次，Pass@5=99% 但 Pass^5=7.8%，真实退款线上连续出错 | Pass^k 指标 + 一票否决项 | N3 |
| 3. “已修复”的补丁：Agent 删了会失败的断言 | 只跑了“修复前失败的测试”，全绿；上线后另一功能坏掉 | FAIL_TO_PASS + PASS_TO_PASS 双重验证（含 flaky 排除） | N5 |
| 4. 同一个任务第二次就被背答案 | 评估集用固定任务文本，Agent 回放固定动作序列即满分；换参数后立刻失败 | 参数化任务模板 + canary 标识 | N6 |
| 5. 评判模型偏爱长答案 | 两份内容等价的回答，长的稳定得高分；Rubric 加长度上限与配对交换顺序后分数才一致；幻觉回答在无 Veto 时仍拿高分 | Rubric（含 Veto、陷阱项）+ 交换顺序配对 + 多源评判 | N9、N10 |
| 5b. 记账 Agent 凭空造出开销 | 32 步零报错，Agent 在第 8 步自述“看不到图片内容”，第 11 步却有四条开销数据；验收发现记录不存在 | 失败归因（首错定位、事实锚点比对）+ 补图像观察通道（而非换模型） | N11 |
| 6. 修了首错，却回归了 | 修复后端到端通过率不变，但同一前缀处仍选错动作；冻结前缀并设“可接受动作集合”后才能量出修复效果 | 轨迹前缀回归任务 | N12 |

## 容易讲错的地方
- **评估对象是“模型+Harness”**，不只是模型；换模型分数不涨说明瓶颈在 Harness（L17–19）。model swap 与消融是两种方法，别混（L19）。换弱模型分数大跌也只说明“主要由模型决定”，还要区分是任务难还是 Harness 过度依赖先验（L19）。
- **Pass@k 不是更好的指标**：它衡量能力上限（“技术奇观”），业务可靠性要看 Pass^k；两者在 p=0.6 时可差 99.0% 对 7.8%（L133–160）。公式仅在每次运行独立时成立（L151）。
- **二元奖励的代价不是疏漏**：满分轨迹里仍可能有违规（一次发两个工具调用），因为 `reward_basis` 只看终态；这是以过程颗粒度换跨模型可比（L123）。
- **确定性验证器不是落后**：向 Rubric/LLM 判官移动不等于放弃断言，能断言的仍应断言，更便宜更稳定（L302）。
- **公开基准不用于产品决策**，只用于粗筛和借鉴设计手法（L276–280）。GAIA +2 点与退款成功率无必然关系。
- **混合方案不会自然胜出**：混合记忆系统总体 66.7%，低于纯 JSON Cards 68.3%；与每题最佳单一方案相比平均反而更低（L394）。
- **同源评判会被 Goodhart**：越用某评分系统训练/调优越会钻它的漏洞（L400）。
- **选参考答案/参考音频本身就是评估设计**：用 Fish S1 参考音色比较音色天然偏袒 Fish；该实验每家仅 4 条音频，不能用来判断谁更好（L426–428）。
- **归因对象是“首个”错误，不是最后一个报错**；三次重试不是三个根因（L436、L458）。失败归因反映产品问题，不能完全交给 LLM（L440）。
- **根因归属容易记错**：expenses.jpg 案例不是“模型不会 OCR”，而是 T3A 观察里根本没有图像像素（观察通道缺失）；记成模型问题就会去换模型或做 OCR 训练（L468、L480）。
- **“获得一条信息”和“正确用于当前决策”是两种能力**；换上下文表示（JSON/Markdown/Python-like）不自动修复策略，三者都是 6/11（L535、L858）。
- **小样本结论不能外推**：Wi-Fi 子集 4/4 不能写成系统整体 100%，必须进入 116 任务×5 种子的标准环境复测，并要求 token ≤75%、延迟 ≤1.5×（L744、L758）。
- **提示写得再详细也补不回 Agent 没看到的信息**，遇到这类失败先查输入；但输入也不是越多越好（L754）。
- **看到分数下降应先检查评测系统，再动 Agent**：资源不足被杀、验证器 bug、测试集与生产脱节在数字上都和模型退化一模一样，只有审轨迹能区分（L726）。
- **成本优化的节省比例不能直接相加**：稳定前缀 28.3% + 压缩历史 17.5%，合用只有 30.0%，因为压缩缩短了可命中缓存的前缀（L626）。
- **异构模型组合不一定划算**：需验证收益是否超过复杂度，并检查“9.9 vs 9.11”之类被当作简单题的回退（L581）。
- **行动阈值差异不等于孰优孰劣**：两个模型最终测试均 100% 通过，实验只支持“行动策略随模型而变”（L597）。
- **机制指标不等于目标指标**：缩短计划文件长度（机制）可能反而增加编辑-检查循环、提高总成本（L793）。
- **“并列”而非“递进”的部分**：选型、成本、可观测性、内部评估基础设施（N15–N18）是并列话题，只有统计显著性（N13）对选型决策有明确依赖（L652）。
